# 03 — “复杂的极简”提示词哲学

[日本語](README.ja.md) · [English](README.md) · **简体中文**

## 提示词工程的本质

提示词工程经常被理解为一组措辞、模板和技巧，仿佛掌握它们就能解锁更好的输出。

我的看法不同。

**好的提示词既不是为了复杂而复杂，也不是极端简短，而是一种“复杂的极简”。**

## 什么是“复杂的极简”

高质量提示词需要同时满足两个相反的条件。

**1. 具有足够复杂度，提供完整的工作上下文**

Agent 需要知道项目结构、技术选择、规范、修改目的、边界和验收标准。缺少这些信息时，它往往会生成“普遍看来合理、但在当前项目中错误”的结果。

**2. 具有足够简洁性，排除无关噪声**

信息越多不一定越好。旧讨论、无关设计笔记、失败尝试和其他任务的残留会争夺注意力，让结果逐渐偏离。

## 提示词质量的四个维度

### 1. 信息密度

删除不影响执行的客套和填充语，提高每句话中与任务有关的信息量。

```text
差：“如果可以的话，能不能稍微调整一下样式？”

好：“在 UserTable 中，将表头背景改为 #f5f5f5，字号改为 14px。
    不要修改其他样式。”
```

### 2. 任务边界

同时说明“做什么”和“不做什么”。

```text
只实现客户端排序。
不要增加服务端排序，也不要修改 API 响应结构。
```

### 3. 上下文质量

只提供会直接影响当前任务的信息。删除已经解决的问题、无关功能、废弃方案和会话残留。

### 4. 约束清晰度

把隐含期待转成明确规则。

```text
保持现有测试通过。遵守 TypeScript strict mode。
不要新增依赖。
```

## 提示词是执行接口

提示词不是为了打动人类读者而写的普通文章，而是模型接收任务的接口。

因此以下做法更有效：

- 删除仪式性的开场；
- 只保留会影响执行的背景；
- 使用列表和明确结构；
- 用显式约束替代对意图的猜测。

提示词设计中最重要的工作，是把隐含期待转化为明确、可验证的约束。

## 实践检查

发送任务前，检查三个问题：

1. **Agent 只依靠这段提示词和引用文件，能否开始工作？** 如果不能，说明上下文不足。
2. **是否包含与当前任务无关的信息？** 如果有，应删除噪声。
3. **哪些解释空间可能实质性改变结果？** 用明确决策、边界或问题替代它。

通过这三项检查后，提示词就接近“复杂的极简”。
