# 11 — 验证与证据

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续演化（Evolving）**

---

# 为什么需要验证与证据

Agent 很擅长产生结果。

它可以：

- 修改代码。
- 生成测试。
- 解释自己的实现。
- 总结变更。
- 说明为什么任务已经完成。

但这些内容都不能单独证明：

> 结果真的正确。

因此，Agent 软件工程必须把两个问题分开：

> Agent 做了什么？

以及：

> **我们凭什么相信它做对了？**

---

# 完成是一项需要证明的结论

一个任务进入“完成”状态，本质上代表系统接受了一个结论：

> 这个任务已经满足预期要求。

这个结论可能包含：

- 代码已经实现。
- 行为符合需求。
- 现有功能没有被破坏。
- 相关约束仍然成立。
- 没有发生越界修改。
- 风险已经处于可接受范围。

因此：

> **“完成”不是一个简单状态。它是一项需要证据支撑的工程结论。**

---

# 声明、验证与证据

可以把验证体系拆成三个部分：

```text
声明
验证
证据
```

## 声明

声明是系统想要接受的结论。

例如：

- Token 刷新失败问题已经修复。
- 退款金额不会超过已支付金额。
- 这次修改没有改变公共 API。
- 迁移脚本不会破坏已有数据。
- Agent 没有修改任务边界之外的文件。

## 验证

验证是判断声明是否成立的过程。

例如：

- 运行自动化测试。
- 复现原始问题。
- 检查 Git 差异。
- 进行静态分析。
- 执行集成测试。
- 检查运行日志。
- 重新调用真实 API。
- 让独立 Agent 审查实现。

## 证据

证据是验证过程中留下的、可以支持后续判断的信息。

例如：

- 测试结果。
- 日志。
- Git 差异。
- 运行截图。
- 数据库查询结果。
- 性能测量数据。
- 构建结果。
- API 返回值。
- 客户确认。
- 代码路径分析。

因此：

```text
声明告诉我们要证明什么。
验证告诉我们怎样检查。
证据告诉我们为什么可以相信这个结论。
```

---

# “已经做完了”不是证据

Agent 可能回复：

- 已经完成。
- 所有问题已经修复。
- 代码现在可以正常工作。
- 实现符合需求。

这些内容属于：

> 自我声明。

它们可以帮助 Human 理解工作结果。

但它们无法独立证明任务完成。

同样：

> 一段逻辑非常完整的解释也不能自动成为事实证明。

因此：

> **Agent 的说明可以成为验证入口。不能代替验证本身。**

---

# 验证应该在执行前开始设计

验证最容易犯的错误之一，是等 Agent 完成以后才问：

> 现在应该怎么证明它做对了？

这时候验证很容易被当前实现方式影响。

例如 Agent 已经写完实现。

随后它再根据自己的实现写测试。

很可能出现：

- 实现假设 A。
- 测试也假设 A。
- 实现和测试完全一致。
- 全部通过。

但 A 本身可能就是错误理解。

因此，更可靠的方式是：

```text
需求
↓
定义完成声明
↓
定义验收条件
↓
确定需要哪些证据
↓
开始实现
↓
执行验证
↓
产生证据
↓
判断是否完成
```

这样验证从一开始就是工程控制的一部分。

---

# 验证对象应该先明确

一个任务可能包含多个不同声明。

例如：

> “修复 Token 刷新失败问题”

可能实际包含：

```text
声明 1：
过期 Token 可以成功刷新。

声明 2：
刷新失败时返回正确错误。

声明 3：
原有登录流程没有受到影响。

声明 4：
没有修改用户数据结构。

声明 5：
没有改变 OAuth 配置。
```

每一个声明需要的证据都可能不同。

因此：

> 任务完成不能只依赖一个笼统的“测试通过”。

应该先把需要成立的关键声明拆出来。

---

# 不同声明需要不同证据

- 代码是否可以编译，可以通过构建结果验证。
- 业务行为是否正确，需要行为测试。
- 性能是否改善，需要测量数据。
- 数据库迁移是否安全，需要迁移前后状态比较。
- API 契约是否保持，需要契约检查。
- 没有发生越界修改，需要 Git 差异检查。
- 客户需求是否理解正确，可能需要客户确认。

因此：

> **验证方式需要匹配声明类型。一种证据很少能够证明所有事情。**

---

# 证据必须连接现实

高质量证据应该尽可能接近真实系统。

常见来源包括：

- 代码仓库。
- Git 差异。
- 自动化测试。
- 集成测试。
- 运行时行为。
- 数据库状态。
- 日志。
- 监控指标。
- 真实 API 返回。
- 官方文档。
- 外部系统实际契约。
- 客户确认。
- 具备对应能力的 Human 判断。

证据越接近真实运行环境，对现实行为的解释能力通常越强。

但不同证据仍然有不同适用范围。

---

# 测试通过意味着什么

测试通过能够证明：

> 在测试所覆盖的条件下，当前实现得到了预期结果。

它无法自动证明：

- 需求理解一定正确。
- 测试本身没有错误。
- 所有重要场景都被覆盖。
- 生产环境和测试环境完全一致。
- 没有隐藏的跨模块影响。
- 没有共同错误前提。

因此：

> **测试是重要证据。测试通过不等于整个工程结论自动成立。**

---

# 静态验证与运行时验证

有些问题可以通过静态分析发现。

例如：

- 类型错误。
- 明显空指针风险。
- 未使用变量。
- 依赖关系。
- 接口变化。
- 某些安全问题。

但很多工程行为只有系统真正运行以后才能观察。

例如：

- 并发问题。
- 网络异常。
- 超时。
- 重试。
- 数据库事务。
- 缓存一致性。
- 外部 API 行为。
- 资源消耗。
- 生产配置差异。

因此，一个可靠的验证体系通常需要同时考虑：

```text
静态验证
和
运行时验证
```

它们覆盖不同类型的风险。

---

# 自我验证

让执行 Agent 自己进行测试非常有价值。

例如：

```text
开发 Agent
↓
实现
↓
构建
↓
测试
↓
静态检查
↓
自检
```

这样可以快速发现大量明显错误。

自我验证适合：

- 低成本问题。
- 局部实现错误。
- 构建失败。
- 测试失败。
- 代码格式问题。
- 明显逻辑错误。

但它存在天然限制：

> 执行者通常已经形成了自己的问题理解。它的验证很容易继承同一个假设。

---

# 独立验证

当风险提高以后，需要增加独立验证。

例如：

```text
开发 Agent
↓
实现
↓
产生结果

独立验证 Agent
↓
读取任务契约
↓
读取实现结果
↓
检查行为
↓
寻找反例
↓
产生验证结论
```

独立验证的价值在于：

> 验证者没有参与原始实现路径。

它更容易发现：

- 遗漏场景。
- 边界越界。
- 错误假设。
- 局部优化。
- 测试盲区。

因此：

> **执行独立和验证独立是两个不同概念。**

---

# 独立 Agent 不一定代表独立验证

即使使用两个不同 Agent，也可能存在共同盲区。

例如：

- 开发 Agent 使用设计文档 A。
- 验证 Agent 同样把设计文档 A 当作唯一真相。

如果 A 本身存在错误：

```text
错误前提
↓
开发 Agent 正确实现
↓
验证 Agent 正确验证
↓
全部通过
```

两个 Agent 是独立的。

验证路径却依然高度相关。

因此：

> **独立执行不能自动保证独立验证。**

---

# 验证多样性

高风险问题需要考虑验证路径是否足够多样。

例如：

```text
需求解释
+
代码分析
+
自动化测试
+
运行时行为
+
数据库状态
+
独立 Agent 审查
```

这些证据从不同角度观察同一个声明。

如果多个验证路径彼此高度独立，并且最终支持同一个结论，可信度通常会更高。

因此：

```text
验证数量很重要。
验证多样性同样重要。
```

---

# 共同盲区

多个 Agent 可能：

- 使用同一个文档。
- 依赖同一套训练知识。
- 共享同一个错误假设。
- 忽略同一个领域规则。

这会产生一种危险情况：

- 所有验证都通过。
- 所有 Agent 都认为正确。
- 真实系统仍然错误。

这种风险可以理解为：

> **相关性验证失败。**

验证过程看起来很多。

实际却都建立在同一条认知路径上。

因此，高风险验证需要主动寻找：

- 不同数据源。
- 不同推理路径。
- 不同验证方式。
- 不同领域视角。

---

# 反证优先

验证经常会问：

> 有什么证据说明这个方案是对的？

另一个同样重要的问题是：

> **什么结果可以证明它是错的？**

例如：

- 如果退款金额超过已支付金额，这个实现就失败。
- 如果重复请求产生两次扣款，这个实现就失败。
- 如果旧版本客户端无法继续调用 API，这个修改就失败。
- 如果数据库迁移后记录数量减少，这个迁移就需要停止。

提前定义失败条件，可以帮助验证从：

```text
寻找支持当前实现的证据
```

转向：

```text
主动寻找能够推翻当前结论的证据
```

这种方式尤其适合高风险工程。

---

# 证据覆盖

有证据，不代表证据覆盖了整个声明。

例如：

任务要求：

> 修复刷新 Token 问题，并保证旧登录流程不受影响。

如果只有：

> 刷新成功测试通过。

那么：

- 刷新逻辑有证据。
- 旧登录流程没有证据。

因此，验证需要检查：

- 声明有哪些？
- 每个声明需要哪些证据？
- 实际收集到了哪些证据？
- 还有哪些声明没有覆盖？

这可以称为：

> **证据覆盖。**

---

# 证据闭环

一个完成声明真正进入可信状态，需要形成证据闭环。

可以简单理解成：

```text
声明
+
所需证据
+
实际证据
+
覆盖完整
+
证据仍然有效
+
不存在未解决冲突
=
证据闭环
```

这里并不是数学公式。

它是一种检查模型。

只要存在：

- 关键证据缺失。
- 证据已经失效。
- 重要冲突仍然没有解决。
- 高风险声明只能依赖自我申报。

就不能认为已经形成完整证据闭环。

---

# 证据时效

证据也会过期。

例如：

```text
昨天：

代码版本 A
↓
测试全部通过
```

```text
今天：

代码版本 B
↓
依赖版本变化
↓
配置变化
```

昨天的测试结果仍然存在。

但它已经不能完整证明今天的代码仍然正确。

因此证据最好能够绑定：

- 代码版本。
- 项目真相版本。
- 运行环境。
- 依赖状态。
- 配置。
- 时间。
- 验证条件。

这样当相关状态发生变化时，系统可以判断：

```text
证据仍然有效。
```

或者：

```text
证据已经过期，需要重新验证。
```

---

# 证据失效

一些变化可能直接让旧证据失效。

例如：

- 任务依赖的业务规则改变。
- 公共 API 契约改变。
- 数据库结构改变。
- 关键依赖升级。
- 相关代码重新修改。
- 运行环境切换。
- 项目真相更新。

因此：

```text
证据存在
和
证据仍然有效
```

是两个不同问题。

成熟工作流需要能够识别过期证据。

---

# 证据粒度

证据也需要合适的粒度。

假设一个大型任务包含十个独立声明。

如果只有一份非常巨大的“最终测试报告”，以后某一个局部规则改变时，就很难判断：

- 哪些证据需要重新执行？
- 哪些证据仍然有效？

因此，一个更好的方式是：

让证据尽量绑定到最小稳定声明。

例如：

```text
声明 A
→ 证据 A

声明 B
→ 证据 B

声明 C
→ 证据 C
```

这样当 B 发生变化时：

- A 仍然可信。
- B 重新验证。
- C 如果不依赖 B，也无需全部重新验证。

因此：

> **证据粒度会直接影响后续重新验证成本。**

---

# 证据持久化

如果验证结果只存在于某一次聊天中：

- 会话结束以后。
- Agent 更换以后。
- 模型更换以后。
- Human 再次调查以后。

系统可能无法回答：

> 当时为什么认为这个任务已经完成？

因此，高价值证据需要持久化。

例如：

- 测试报告。
- 构建结果。
- 验证摘要。
- 运行日志。
- 关键截图。
- 测量结果。
- 状态快照。
- 客户确认。
- 重要 Git 提交。

证据持久化使系统能够重新回答：

> 当时接受这个结论的依据是什么？

---

# 失败证据也需要保存

成功结果通常很容易被记录。

失败信息更容易被丢掉。

例如：

- 某次 API 调用失败。
- 某个恢复动作失败。
- 某个测试曾经暴露竞态问题。

Agent 修复以后最终通过。

如果中间失败证据完全消失，后续可能无法理解：

- 为什么这里存在这个保护逻辑？
- 为什么这个异常路径需要特殊处理？

因此，高价值失败证据也需要被保存。

失败证据可能包括：

- 发生了什么。
- 什么时候发生。
- 当时系统状态是什么。
- 怎样复现。
- 怎样恢复。
- 问题是否已经解决。

失败信息也是工程知识的一部分。

---

# 证据不是越多越好

证据也会制造成本。

如果每次任务都保存：

- 所有日志。
- 所有命令输出。
- 完整聊天记录。
- 全部中间文件。
- 所有截图。

最终系统会形成一个巨大的证据垃圾场。

这会导致：

- 真正重要的证据更难寻找。
- 验证成本提高。
- 上下文再次被噪声污染。

因此，高质量证据需要满足：

- 和明确声明有关。
- 能够重新检查。
- 来源清楚。
- 适用范围清楚。
- 有足够信息支持结论。

同时尽量减少无关内容。

---

# 证据与真相的关系

第 08 章讨论过：

- 证据可以支持真相。
- 证据也可以推翻旧真相。
- 但证据本身不能自动成为项目真相。

例如：

> 一次测试失败

可能意味着：

- 代码存在问题。
- 测试存在问题。
- 运行环境异常。
- 依赖异常。
- 原有项目真相错误。

因此：

```text
证据负责连接现实。
真相治理负责解释证据最终意味着什么。
```

两者承担不同职责。

---

# 验证错误真相

一种非常危险的情况是：

```text
错误真相
↓
正确任务
↓
正确实现
↓
正确测试
↓
正确 QA
↓
全部通过
```

验证体系可以证明：

> 实现与当前真相一致。

但它无法自动证明：

> 当前真相本身正确。

因此，验证与真相治理必须形成循环：

```text
项目真相
↓
任务
↓
实现
↓
验证
↓
证据
↓
如果一致
继续

如果冲突
↓
挑战当前真相
↓
重新分析
```

验证体系既检查实现。

也负责发现现实是否正在反驳项目真相。

---

# 完成判定

一个任务什么时候可以真正完成？

更可靠的判断方式可以是：

- 目标已经明确。
- 任务边界没有被破坏。
- 关键声明已经定义。
- 所需验证已经执行。
- 关键证据已经产生。
- 证据覆盖足够。
- 证据仍然有效。
- 没有未解决的高风险冲突。
- 剩余风险已经被明确接受。

然后：

> 任务才能进入完成状态。

因此：

> **完成应该是验证后的结论。**

---

# 风险决定验证强度

所有任务都使用同样强度的验证，会产生两个问题。

验证太弱：

> 高风险任务不可靠。

验证太强：

> 低风险任务成本过高。

因此，验证强度应该和风险匹配。

## 低风险任务

例如：

- 文案修改。
- 低影响 UI 调整。
- 内部工具的小功能。

可能只需要：

- Agent 自检。
- 构建。
- 局部测试。
- Git 差异检查。

## 中等风险任务

例如：

- 普通业务逻辑。
- API 调整。
- 数据库查询。

可能需要：

- 自动化测试。
- 独立 Agent 审查。
- 集成测试。
- 契约检查。

## 高风险任务

例如：

- 支付。
- 认证。
- 权限。
- 安全。
- 数据迁移。
- 不可逆操作。

可能需要：

- 多路径验证。
- 运行时验证。
- 独立推理。
- 强证据留存。
- 具备相应能力的 Human 判断。
- 必要时进行受控环境测试。

因此：

> **验证强度应该与失败成本相匹配。**

---

# Human 验证的价值

Human 仍然非常重要。

但 Human 也可能犯错。

如果一个复杂任务只给 Human：

- 几千行代码。
- 几十份文档。
- 大量日志。

然后要求：

> “请审核一下。”

Human 同样会面临认知过载。

更合理的方式是：

Agent 先完成：

- 自动化检查。
- 证据收集。
- 差异整理。
- 冲突发现。
- 风险分类。

然后把真正需要人判断的内容压缩成：

- 发生了什么？
- 为什么重要？
- 有哪些证据？
- 有哪些冲突？
- 还剩哪些不确定性？
- 需要 Human 决定什么？

这样 Human 的注意力才能用于高价值判断。

这一点会在下一章继续展开。

---

# 失败模式一：把 Agent 的声明当成证据

```text
Agent：
“已经全部完成。”

系统：
“任务完成。”
```

这里没有验证。

只有声明。

---

# 失败模式二：测试通过等于完成

所有自动化测试通过。

但：

- 需求理解错误。
- 测试覆盖不完整。
- 测试环境与生产不同。
- 跨模块影响没有验证。

因此：

> **测试通过只能证明测试所观察到的那部分世界。**

---

# 失败模式三：开发和验证共享同一错误假设

- 开发 Agent：依据假设 A 实现。
- 验证 Agent：依据同一个假设 A 验证。

全部通过。

但 A 本身错误。

这种情况下增加 Agent 数量并没有真正增加验证独立性。

---

# 失败模式四：证据已经过期

代码发生重大变化。

旧测试报告仍然被引用。

系统继续认为任务已经被验证。

```text
证据仍然存在。
可信度已经消失。
```

---

# 失败模式五：证据很多，但没有覆盖声明

系统保存了：

- 大量日志。
- 大量截图。
- 大量测试。
- 大量分析。

但没人能够回答：

> 这些证据到底证明了哪个声明？

```text
证据数量很多。
工程意义却很弱。
```

---

# 失败模式六：只保存成功，不保存失败

最终测试通过。

之前暴露的重要失败路径被完全丢弃。

几个月以后同类问题再次出现。

团队已经无法解释：

> 这个保护逻辑为什么存在。

---

# 一个可复用的验证流程

一个最小验证流程可以是：

1. 明确任务准备接受哪些完成声明。
2. 为每个关键声明定义所需证据。
3. 根据风险选择验证强度。
4. 在实现前定义主要验收条件。
5. Agent 执行并进行自检。
6. 对中高风险结论增加独立验证。
7. 对关键行为使用不同类型的验证路径。
8. 收集实际证据。
9. 检查证据覆盖。
10. 检查证据时效和适用范围。
11. 检查是否存在未解决冲突。
12. 如果证据挑战当前真相，进入真相挑战流程。
13. 如果证据闭环成立，接受完成结论。
14. 持久化高价值证据。

可以进一步表示为：

```text
任务目标
↓
关键声明
↓
所需证据
↓
验证设计
↓
Agent 执行
↓
自我验证
↓
独立验证
↓
运行时验证
↓
证据收集
↓
覆盖检查
↓
时效检查
↓
冲突检查
↓
├── 证据不足
│   ↓
│   继续验证
│
├── 实现错误
│   ↓
│   返回修改
│
├── 真相冲突
│   ↓
│   挑战当前真相
│
└── 证据闭环
    ↓
    接受完成
```

---

# 一个工作模型

可以把完成可信度理解成由几个因素共同决定：

- 当前真相是否可靠。
- 验证方式是否足够。
- 证据是否覆盖关键声明。
- 证据是否仍然有效。
- 验证路径是否过度相关。
- 是否存在未解决冲突。

其中任何一个关键部分过弱，都可能让“完成”失去可信度。

这个模型目前用于帮助设计验证流程。

它并不是数学意义上的精确公式。

---

# 仍在研究的问题

当前还有几个值得继续调查的问题。

第一，证据应该以什么粒度绑定到工程声明，才能同时兼顾可追溯性和维护成本。

第二，怎样自动判断证据已经失效。

第三，怎样衡量不同验证路径之间的独立程度。

第四，怎样自动发现多个 Agent 共享的错误前提。

第五，哪些运行时验证可以安全自动执行，哪些必须进入受控环境。

第六，怎样让失败证据长期保留，同时避免证据系统无限膨胀。

第七，如何让真相变化自动触发受影响证据重新验证。

这些问题仍然需要更多实际观察，会继续在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **完成是一项需要证明的工程结论。**

---

> **Agent 的自我声明不能代替证据。**

---

> **验证应该在执行之前开始设计。**

---

> **测试通过只能证明测试覆盖到的世界。**

---

> **独立执行不能自动保证独立验证。**

---

> **验证多样性和验证数量同样重要。**

---

> **证据必须能够连接现实。**

---

> **证据存在，不代表证据仍然有效。**

---

> **高质量证据应该绑定到明确声明。**

---

> **失败证据也属于工程知识。**

---

> **验证强度应该与失败风险相匹配。**

---

> **完成需要形成证据闭环。**

---

# 结语

随着 Agent 的执行能力越来越强，软件工程会越来越容易产生一种危险的错觉：

- 它做得很快。
- 代码很多。
- 测试通过。
- 解释完整。
- 所以应该已经完成。

但真正可靠的工程需要继续追问：

```text
它到底完成了什么？

哪些声明已经被证明？

证据来自哪里？

证据覆盖了什么？

这些证据现在还有效吗？

验证者和执行者是否共享同一个错误前提？

有没有现实证据正在反驳当前设计？

还有哪些风险没有真正关闭？
```

当这些问题都能够得到回答时：

> **“完成”**

才开始从一句 Agent 的回复，变成一个可以被工程系统接受的结论。
