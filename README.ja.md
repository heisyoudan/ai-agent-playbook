# AI Agent Playbook

**日本語** · [English](README.md) · [简体中文](README.zh-CN.md)

> *A practical methodology for AI-agent collaboration, distilled from 2 years of production use in large-scale payment systems.*

> AIを2年間、大規模決済プロジェクトで本格運用してきた実践知。  
> ツールの使い方ではなく、**AI と協業するための思考体系**をまとめたもの。

---

## これは何か

私はこの2年間、AI を集中的に業務へ投入してきた。

各種 AI Agent のサブスクリプションを試し、最終的には数千人規模の大型決済プロジェクトで、AI を本格的に開発プロセスに組み込む現場にいた。

その中で気づいたことがある。

**AI との協業で差がつくのは、ツールの選択でも Prompt の巧みさでもない。**

差がつくのは、タスクの分解力、コンテキストの設計力、制約の体系化、そしてワークフローを「製品」として設計できるかどうかだ。

この Playbook は、その実践知を体系的にまとめたものである。

---

## この Playbook が解決する問題

AI Agent が失敗する理由の多くは予測できる。タスクが大きすぎる、コンテキストにノイズが多い、責任者が曖昧、検収基準が弱い、引き継ぐべき状態が残っていない、といった問題である。

これらは個別のモデル障害ではなく、ワークフローの障害だ。この Playbook は、スコープ逸脱、手戻り、検証不能な出力へ発展する前に、それらを構造的に制御する方法を示す。

---

## 対象読者

- AI を業務で使い始めたが、安定した成果が出せていないエンジニア
- Agent を導入したが「結局自分で書いた方が早い」と感じている人
- AI 協業を組織レベルで推進したいリーダー
- 面接で「AI をどう使っているか」を聞きたい / 答えたい人

## 3行で伝える核心

```
AI は実行層に過ぎない。
プロセスこそが生産性である。
制約こそが安定性の源泉である。
```

コーディング能力は、今でも重要である。  
それは旧時代における最も鋭い武器であり、エンジニアの土台そのものだった。

ただ、AIが前提となる新しい時代では、それだけで十分とは言えない。  
火器の時代に剣だけを握っていては、新しい戦場で優位を取り続けることは難しい。

必要なのは、剣を捨てることではない。  
これまで磨いてきた基礎能力を保ちながら、AI協業、タスク設計、コンテキスト管理、検証、ワークフロー設計といった新しい武器を身につけることである。

古い武器を持ち続けながら、新しい武器も使えること。  
その両方を備えてこそ、これからの時代をより強く生き抜けると私は考えている。

## ひとつのループで見る方法論

1. **リスクを分類する。** Agentが実行できること、承認が必要なこと、人間が責任を持つことを決める。
2. **ひとつの目的を定義する。** 期待する結果、今回の実行、検収基準、境界を明示する。
3. **閉じたコンテキストを渡す。** タスクに必要なファイル、事実、決定、制約だけを含める。
4. **Agentに実行と自己検証を行わせる。** ビルド、テスト、Lintなど適用可能な証拠を要求する。
5. **差分をレビューする。** 変更ファイル、意図しない範囲、高リスクロジック、主張を支える証拠を確認する。
6. **記録して引き継ぐ。** 決定と証拠を構造化された正の情報源へ残し、次の責務では新しいコンテキストを使う。
7. **計測して改善する。** 出力量ではなく、手戻り、不具合、レビュー時間、費用、例外を追跡する。

## 最小タスク契約

```text
summary:             何を達成するか
currentAction:       今回具体的に何を実行するか
acceptanceCriteria:  どの観測可能な確認をもって完了とするか
boundaries:          何を変更・実行してはいけないか
```

ひとつでも欠けているなら、タスクはまだAgentへ渡せる状態ではない。

### 曖昧な依頼を実行可能なタスクへ変える

```text
悪い例:
認証システムを修正する。

良い例:
summary:
アクセストークン失効後に発生するリフレッシュトークン障害を修正する。

currentAction:
リフレッシュ処理を追跡し、トークン更新経路だけを修正する。

acceptanceCriteria:
- 失効したアクセストークンが正常に更新される
- 既存のログインフローが引き続き成功する
- 更新成功・失敗のテストが追加されている

boundaries:
- ユーザースキーマを変更しない
- OAuthプロバイダ設定を変更しない
```

後者は範囲が小さく、境界が明確で、独立して検証できる。Agent は製品上の判断を勝手に補わずに作業を開始できる。

## 適用範囲と責任

Agentは提案し、実行するが、人間の責任を取り除くものではない。セキュリティ、認可、決済、プライバシー、コンプライアンス、本番リリース、破壊的操作、不可逆な外部作用には、明確な責任者と承認規則が必要である。

複数モデルの合意は証拠ではない。検証可能な主張は、一次資料、ソースコード、テスト、実行結果、計測値へ戻って確認する。短期的な作業状態と、保持すべき監査・リリース証跡は分離する。

## 背景

この Playbook の内容は、単なる理論ではない。

私は実際にこれらの原則に基づいて、Agent 協業フレームワーク **Maestro** を設計・実装し、本番環境で検証してきた。Maestro は、タスク契約、コンテキスト分離、品質ゲート、構造化された引き継ぎを実行可能な形にする。

関係は明確である。**Playbook は方法論を定義し、Maestro はそれを実行可能にする。** 方法論自体は、特定のモデルやAgentプラットフォームに依存しない。
