# 09 — 有效推理范围

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续演化（Evolving）**

---

# 为什么需要“有效推理范围”

随着 AI 的上下文窗口越来越大，一个很自然的想法会出现：

> 只要把足够多的信息全部交给 AI，它就可以理解整个项目。

在小型项目中，这种方式有时可以工作。

但随着系统规模扩大，会逐渐出现另一个问题：

> **能够输入多少信息，并不等于能够可靠推理多少信息。**

一个模型也许可以一次读取几十万甚至更多 Token。

但真正的软件工程问题还包括：

- Agent 能不能识别真正重要的信息？
- 能不能持续维持关键约束？
- 能不能正确理解不同模块之间的依赖？
- 能不能发现多个文档之间的冲突？
- 能不能记住推理开始时的重要条件？
- 能不能在长推理链中保持自洽？
- 能不能验证最终结论有没有遗漏重要影响？

因此，我们需要区分两个概念：

```text
上下文容量
与
有效推理范围
```

---

# 上下文容量

上下文容量描述的是：

> 模型理论上能够在一次交互中接收多少信息。

这些信息可能包括：

- 源代码
- 设计文档
- API 规格
- 数据库结构
- 日志
- 测试
- 架构文档
- 任务说明
- 历史决策

只要总量没有超过模型允许的上下文窗口，它们理论上都可以被输入。

上下文容量回答的是：

> 模型能不能接收到这些信息？

这是一个输入容量问题。

---

# 有效推理范围

有效推理范围描述的是：

> **Agent 在一次有效推理中，能够可靠维持、关联、理解并验证的相关现实范围。**

它关注的重点包括：

- Agent 能否识别当前真正重要的信息。
- Agent 能否同时维持多个约束。
- Agent 能否正确理解依赖关系。
- Agent 能否发现跨文档冲突。
- Agent 能否判断哪些信息已经过期。
- Agent 能否保持架构和业务逻辑的一致性。
- Agent 能否在长推理过程中持续记住早期条件。
- Agent 能否判断最终结果是否违反其他规则。

因此：

```text
上下文容量决定 AI 能看到多少信息。
有效推理范围决定 AI 能可靠理解多少信息。
```

---

# 能放进上下文，不等于能够可靠推理

假设一个大型系统包含：

- 300 份设计文档
- 200 个 API
- 1000 个数据结构
- 数百个契约
- 数千个测试
- 大量历史决策
- 运行时约束
- 运维规则

即使未来 AI 可以一次读取全部内容，也仍然存在几个问题。

## 有效信息被稀释

上下文越大，和当前任务真正相关的信息占比可能越低。

例如：

```text
总上下文：500000 Token

当前任务真正相关的信息：20000 Token
```

这时 Agent 需要先解决一个额外问题：

> 到底哪些内容和当前任务有关？

随着无关信息增加，真正重要的约束会越来越容易被埋没。

因此：

> **更多上下文不一定带来更多理解。**

---

## 依赖复杂度

大型系统真正困难的地方，经常存在于依赖关系中。

例如：

```text
支付服务
↓
支付网关
↓
外部支付系统
↓
账本
↓
清结算
```

一次局部修改可能沿着依赖关系影响多个模块。

Agent 需要理解的内容已经不只是：

> 有哪些文件？

还包括：

- 这些文件之间为什么有关？
- 哪个模块依赖哪个模块？
- 一个规则变化会传播到哪里？

真正增加推理难度的，经常是关系数量和关系复杂度。

---

## 跨文档冲突

大型项目中的文档很难永远保持完全同步。

可能出现：

- 基本设计写的是 A。
- 详细设计写的是 B。
- 源代码实际实现的是 C。
- 运行时真正表现出来的是 D。

此时 Agent 需要判断：

- 哪个来源更加可信？
- 哪些是历史遗留？
- 哪些已经过期？
- 当前现实到底是什么？

当输入材料越来越多时，这类冲突也会越来越多。

---

## 推理链越来越长

有些决策需要跨越很长的逻辑链。

例如：

```text
需求
↓
业务规则
↓
架构
↓
API 契约
↓
服务逻辑
↓
数据库约束
↓
外部系统
↓
失败恢复
↓
验证
```

推理链越长，就越容易出现：

- 遗漏约束
- 错误假设
- 错误依赖
- 上下文遗忘
- 局部结论与早期条件不一致

因此，大型问题的困难不只来自信息数量。

还来自推理路径本身。

---

## 验证范围也会扩大

即使 Agent 成功生成了解决方案，还需要继续回答：

> 怎样证明这个方案没有破坏其他部分？

系统越大：

- 潜在影响范围越大。
- 需要验证的内容越多。
- 需要收集的证据越多。

因此，推理范围扩大以后，验证范围通常也会一起扩大。

---

# 相关现实

解决这个问题的关键之一，是先回答：

> 完成当前决策，到底需要知道哪些现实？

这里可以引入一个概念：

> **相关现实**

相关现实指：

> 完成当前任务和判断所必须知道的那部分真实世界。

例如，一个支付服务 Agent 可能需要知道：

- 当前 API 契约
- 相关支付规则
- 支付实体
- 订单网关
- 支付数据访问层
- 错误处理规则
- 事务规则
- 相关全局约束
- 相关测试

它可能完全不需要读取：

- 后台管理页面
- 无关国家配置
- 报表模块
- 其他支付方式的内部实现
- 与当前任务无关的历史讨论

因此：

> **AI 不需要看见整个系统。它需要看清完成当前决策所必须知道的完整相关世界。**

---

# 一个基础条件

可以暂时把可靠执行的一个基础条件写成：

```text
相关问题范围
≤
有效推理范围
```

当这个条件大致成立时，Agent 更有机会：

- 理解问题。
- 维持重要约束。
- 正确处理依赖。
- 发现明显冲突。
- 验证自己的结果。

当：

```text
相关问题范围
>
有效推理范围
```

就更容易出现：

- 遗漏约束。
- 局部理解。
- 设计不一致。
- 假设漂移。
- 验证不完整。
- 输出看起来非常自信，但实际并不可靠。

因此，大型项目中的一个重要工程任务是：

> **持续把问题调整到 Agent 可以可靠理解的范围内。**

---

# 小型项目

当一个项目规模足够小：

```text
整个相关项目范围
≈
Agent 的有效推理范围
```

AI 有机会同时理解：

- 需求
- 代码仓库
- 架构
- 运行状态
- 约束
- 测试

这时 AI 可以承担更多工作：

- 架构分析
- 任务规划
- 实现
- 验证
- 文档整理

Human 更关注：

- 现实是否准确。
- 关键决策是否合理。
- 风险是否可接受。
- 最终结果是否可以批准。

这类项目是当前 AI Agent 非常有优势的区域。

---

# 大型系统

大型企业系统则完全不同。

通常会出现：

```text
整个系统
远大于
单个 Agent 的有效推理范围
```

例如一个大型支付系统可能包含：

- 数百份设计文档。
- 多个业务域。
- 大量外部系统。
- 复杂历史背景。
- 运维约束。
- 合规要求。
- 复杂失败行为。
- 大量数据和接口契约。

此时，如果直接要求一个 Agent：

- 理解整个系统。
- 设计整个系统。
- 正确实现。

这种工作方式的可信度很低。

更合理的方式是：

```text
全局架构
↓
业务域
↓
模块
↓
API 或用例
↓
相关上下文
↓
有边界的任务
↓
Agent 执行
```

大型系统需要不断把全局问题转换成局部问题。

---

# 推理范围控制

大型 Agent 工作流需要具备一种重要能力：

> **推理范围控制**

它负责回答：

- Agent 当前需要理解什么？
- Agent 当前不需要理解什么？
- 哪些全局约束必须进入当前上下文？
- 哪些依赖必须包含？
- 哪些资料缺失以后必须停止？
- 哪些信息可以通过引用获得，而无需全部复制进入上下文？

推理范围控制的目标是：

> **让 Agent 看到的世界足够完整，同时保持足够小。**

---

# 上下文压缩

上下文压缩是推理范围控制的一种重要方法。

这里的“压缩”不能简单理解成：

> 把长文档总结成短文档。

因为简单摘要很可能删除真正重要的约束。

更可靠的方法应该是：

```text
当前任务
↓
分析相关依赖
↓
寻找必要信息来源
↓
提取已经确认的事实
↓
保留信息来源
↓
构建局部上下文
```

因此，上下文压缩更接近：

> **面向当前任务，对现实信息进行选择。**

它需要回答：

- 为什么这条信息和当前任务有关？
- 它来自哪里？
- 它是否仍然有效？
- 它适用于什么范围？
- 如果 Agent 对它产生怀疑，能不能回到原始来源？

---

## 压缩不能切断来源

假设上下文构建过程告诉 Agent：

> 退款金额不能超过实际支付金额。

这条规则最好能够继续追踪到：

- 业务需求
- 系统规则
- 设计文档
- 源代码约束
- 测试
- 或者客户确认

否则 Agent 只能相信一个经过二次加工的摘要。

因此，一个高质量的上下文事实最好能够包含：

- 事实
- 来源
- 版本
- 适用范围
- 决策权

这样 Agent 才能够在必要时：

- 追踪。
- 验证。
- 提出挑战。
- 升级处理。

---

# 真相投影

大型系统中的上下文构建，还可以进一步理解为：

> **真相投影**

一个大型系统可能拥有：

- 全局真相
- 局部真相
- 系统不变量
- 架构边界
- 关键契约
- 依赖关系
- 历史决策

当前 Agent 不需要同时读取全部内容。

工作流可以根据当前任务：

```text
全局真相
+
当前任务
+
当前边界
+
依赖关系
↓
筛选相关内容
↓
构建局部上下文
```

最终 Agent 获得：

```text
局部真相
+
相关全局约束
+
相关契约
+
相关依赖
```

这样可以同时满足两个目标：

- Agent 不需要理解整个系统。
- 局部执行仍然受到全局规则约束。

---

# 上下文完整性

缩小上下文也会产生新的风险。

最危险的问题是：

> 我们是不是把真正需要的信息也删掉了？

因此，在执行前需要考虑：

> 上下文是否完整？

也就是：

> 完成当前任务所需要的关键事实和来源是否已经齐全？

例如一个 API 任务可能至少需要：

- API 规格。
- 相关业务规则。
- 实体定义。
- 网关契约。
- 错误规则。
- 事务规则。
- 外部接口。
- 相关全局约束。

如果缺少关键资料：

```text
发现上下文缺失
↓
停止关键执行
↓
寻找缺失信息
↓
重新构建上下文
↓
继续执行
```

Agent 不应该在关键上下文缺失时，自行把猜测填进世界。

---

# 先确定变更范围

有效推理范围也解释了为什么：

> **先确定变更范围**

非常重要。

面对一个大型需求变更，如果直接要求 Agent 重新理解整个系统，推理范围会迅速扩大。

更可靠的过程是：

```text
需求变化
↓
确认差异
↓
影响分析
↓
受影响业务域
↓
受影响模块
↓
受影响 API
↓
受影响工程产物
↓
构建局部上下文
↓
Agent 执行
```

这样可以把一个：

```text
全局变化
```

逐渐转换成：

```text
局部推理问题
```

---

## 先看差异

因此，差异优先还有一个更深的价值。

它不只是减少工作量。

它还在主动缩小推理范围。

例如：

```text
旧设计
+
新设计
↓
差异
↓
变化规则
↓
受影响对象
↓
相关依赖
↓
局部上下文
```

Agent 不需要重新理解全部历史。

它主要需要回答：

- 发生了什么变化？
- 哪些内容依赖这次变化？
- 哪些成果需要重新验证？

先确定变化范围，有助于保护推理可靠性。

---

# 任务切分

当问题超过有效推理范围时，一个自然方法是继续切分。

例如：

```text
支付平台
↓
支付业务域
↓
支付模块
↓
创建支付用例
↓
支付服务
```

随着切分：

- 相关上下文减少。
- 推理复杂度下降。
- 局部可靠性提高。

但切分也会产生新的成本：

- 边界数量增加。
- 契约数量增加。
- 交接增加。
- 协调增加。
- 集成风险增加。

因此：

> **问题不能无限切分。**

下一章会继续讨论：

> **到底应该切到哪里？**

---

# AI 不需要成为整个系统的上帝

大型系统中，很容易产生一个目标：

> 希望 AI 一次理解整个项目。

但大型软件工程本身也很少依赖某一个人理解所有细节。

成熟的软件架构会通过：

- 边界
- 契约
- 模块所有权
- 分层
- 接口
- 依赖方向
- 系统不变量

把一个巨大世界拆成多个可以管理的区域。

Agent 软件工程同样可以使用这种思想。

例如：

```text
系统架构
↓
业务域边界
↓
模块契约
↓
相关上下文
↓
局部 Agent
```

Agent 可以成为自己局部世界中的高能力执行者。

它没有必要成为整个企业系统唯一的全局认知者。

---

# 失败模式一：上下文倾倒

一个常见失败模式是：

Agent 看起来很强。

于是不断给它更多信息：

- 更多文件。
- 更多文档。
- 更多日志。
- 更多历史对话。
- 更多设计资料。

最后出现：

- 上下文规模增加。
- 有效信息占比下降。
- 推理复杂度上升。
- 验证难度上升。

这种方式很容易给 Human 一种安全感：

> 我已经把所有信息都告诉 AI 了。

但：

> **完整输入并不会自动产生完整理解。**

---

# 失败模式二：有损摘要

另一个极端是：

项目太大。

于是把所有内容强行总结成一份非常短的摘要。

如果摘要过程中删除了：

- 关键约束。
- 例外条件。
- 重要依赖。
- 历史决策。
- 失败规则。

Agent 得到的局部世界就会变得不完整。

因此：

> **上下文压缩需要减少噪声，同时保护关键事实。**

---

# 失败模式三：局部优化

上下文太窄，同样会产生问题。

例如：

```text
局部任务
↓
局部方案
↓
局部测试全部通过
```

但：

> 全局契约被破坏。

例如，一个服务为了提高可靠性增加了自动重试。

局部测试完全通过。

但外部 API 不支持幂等。

结果产生重复请求。

局部方案是合理的。

全局系统却因此产生错误。

因此：

> 推理范围控制追求的目标并不是最小上下文。

真正需要寻找的是：

> **最小但完整的相关上下文。**

---

# 一个可复用的实践流程

可以暂时使用下面这套流程：

1. 明确当前要做出的决策。
2. 确认完成这个决策需要了解哪些现实。
3. 找出相关依赖。
4. 找出必须保持的全局约束。
5. 找到原始信息来源。
6. 检查上下文是否完整。
7. 构建有边界的局部上下文。
8. 让 Agent 执行推理或实现。
9. 验证结果。
10. 如果执行过程中发现新的依赖，重新评估推理范围。

---

# 一个工作假设

目前可以暂时使用一个非常简单的思考模型：

```text
决策可靠性
≈
相关现实覆盖程度
×
推理可靠性
×
验证强度
```

这个表达并不是经过数学验证的公式。

它只是一个工作假设。

它帮助我们持续问三个问题：

- Agent 看见了多少真正相关的现实？
- Agent 能否可靠推理这些现实？
- 我们能否验证最终结论？

其中任何一个环节非常弱，最终判断的可信度都会明显下降。

---

# 有效推理范围并不固定

有效推理范围不是一个固定数字。

它会受到很多因素影响：

- 模型能力。
- 任务类型。
- 上下文结构。
- 领域复杂度。
- 依赖密度。
- 工具能力。
- 证据质量。
- Prompt 质量。
- 验证支持。

例如：

同一个 Agent 处理一个明确的 CRUD 功能时，可能能够可靠理解很大的范围。

但处理一个复杂的支付架构决策时，可可靠推理的范围可能明显缩小。

因此：

> **任务大小不能只按照 Token 数量判断。还需要考虑推理复杂度。**

# 仍在研究的问题

当前还有几个值得继续调查的问题。

第一，怎样更客观地判断一个任务是否已经超过 Agent 的有效推理范围。

第二，上下文完整性是否可以形成自动质量门。

第三，上下文构建器怎样判断自己有没有漏掉关键依赖。

第四，当 Agent 在执行过程中发现范围外依赖时，应该怎样重新扩大或重建当前上下文。

第五，不同类型任务的有效推理范围到底差异有多大。

这些问题仍然需要更多实际观察，会继续在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **能放进上下文，不等于能够可靠推理。**

---

> **AI 应该看清完整的相关世界，而无需看见整个世界。**

---

> **相关问题范围应该尽量控制在有效推理范围内。**

---

> **上下文压缩必须保留关键事实和来源。**

---

> **先确定变更范围，可以保护推理可靠性。**

---

> **真正需要寻找的，是最小但完整的相关上下文。**

---

# 结语

随着 AI 的上下文窗口越来越大，很容易产生一种错觉：

> 总有一天，我们只需要把整个项目全部交给 AI。

但大型软件真正的复杂度，不只存在于信息数量中。

它还存在于：

- 依赖。
- 关系。
- 冲突。
- 历史。
- 时序。
- 失败。
- 所有权。
- 系统不变量。

因此，Agent 软件工程的一项核心能力，就是主动设计：

> **当前 Worker 到底需要看到多大的世界？**

一个可靠的 Agent 不需要知道所有事情。

它需要知道：

```text
当前要解决什么问题？

完成这个决策需要哪些现实？

哪些全局规则必须保持？

哪些依赖与当前任务有关？

缺少哪些信息时必须停止？

什么证据可以证明最终结果？
```

当这些问题得到良好设计以后，一个巨大的软件系统就可以不断被转换成：

> 一个个 Agent 真正能够看清的小世界。

大型 Agent 工程的重要能力之一，就是持续把一个超出 AI 推理范围的巨大世界，转换成多个可以被可靠理解、执行和验证的局部世界。
