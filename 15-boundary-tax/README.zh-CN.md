# 15 — 边界协调成本与最佳推理边界

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续研究（Research）** · **成熟度：工作假设（Working Hypothesis）**

---

# 为什么需要研究边界协调成本

在 Agent 软件工程中，一个非常自然的方向是：

- 任务尽量切小。
- 上下文尽量隔离。
- 职责尽量单一。
- 每个 Agent 只处理自己能看清的问题。

这些做法通常可以提高局部可靠性。

但当系统不断切分以后，会出现另一个问题：

- 边界越来越多。
- 每一个新边界都会带来新的成本。

因此，一个大型 Agent 系统最终需要同时回答两个问题：

> 当前任务是不是太大？

以及：

> **当前系统是不是已经切得太碎？**

---

# 局部推理复杂度

任务越大，Agent 需要同时理解的内容通常越多。

例如：

- 更多代码。
- 更多依赖。
- 更多业务规则。
- 更多系统约束。
- 更多历史决策。
- 更多测试。
- 更多异常路径。

这会提高：

> 局部推理复杂度。

当局部问题逐渐超过 Agent 的有效推理范围以后，可靠性开始下降。

可能出现：

- 遗漏约束。
- 错误理解依赖。
- 局部结论互相冲突。
- 验证覆盖不足。

因此：

> 任务过大，会产生推理风险。

---

# 边界协调成本

任务切小以后，局部推理复杂度会下降。

但系统会开始支付另一类成本：

> **边界协调成本。**

边界协调成本指：

> 由于问题被拆成多个局部世界以后，为了让这些局部结果重新组成一个完整系统而产生的额外成本。

它可能包括：

- 上下文重建。
- 任务交接。
- 契约维护。
- 依赖协调。
- 状态同步。
- 等待前置结果。
- 重复验证。
- 跨模块沟通。
- 冲突处理。
- 集成测试。
- 所有权协调。
- 真相传播。
- 证据重新绑定。

这些成本单独看可能很小。

但当边界数量不断增加以后，它们会逐渐成为系统主要成本之一。

---

# 一个简单例子

假设一个完整功能可以由一个 Agent 直接完成。

这个 Agent 需要理解：

- 需求。
- 相关代码。
- 业务规则。
- 测试。

然后一次闭合实现。

如果把它拆成：

- DTO 任务。
- Mapper 任务。
- Service 任务。
- Repository 任务。
- Controller 任务。
- Test 任务。
- Documentation 任务。

每个任务确实都更简单。

但系统现在需要：

- 7 次任务生成。
- 7 次上下文构建。
- 多次交接。
- 多次状态转换。
- 多组产物。
- 多次依赖等待。

最终还需要重新验证：

> 这些结果是否真的组成了一个完整功能。

局部可靠性提高了。

整体协调成本也上升了。

---

# 切分不会让复杂度消失

一个复杂问题可以大致包含两类复杂度：

```text
局部推理复杂度
和
边界协调复杂度。
```

任务越大：

> 局部推理复杂度通常越高。

任务越小：

> 边界协调复杂度通常越高。

因此：

> **切分不会让复杂度消失。它会重新分布复杂度。**

---

# 两个极端

可以把任务边界想象成一条连续轴。

左侧：

```text
一个巨大任务
↓
边界很少
↓
协调成本低
↓
推理复杂度高
```

右侧：

```text
大量极小任务
↓
局部推理简单
↓
边界很多
↓
协调成本高
```

两个极端都有问题。

## 极端一：单体任务

例如：

> “完成整个支付模块。”

优点：

- 边界少。
- 上下文切换少。
- 交接少。
- 局部协调简单。

问题：

> Agent 很可能无法完整理解整个世界。

因此容易产生推理失效。

## 极端二：原子任务

例如：

- “修改这一行字段。”
- “增加一个 Mapper。”
- “增加一个测试。”
- “修改一个错误码。”

优点：

> 每个任务非常容易。

问题：

> 整个系统需要大量协调才能重新形成完整结果。

Human 或上层 Agent 可能逐渐变成：

- 任务调度器。
- 上下文搬运工。
- 边界修复器。

这会抵消 Agent 带来的自动化收益。

---

# 最佳推理边界

因此，我们可以提出一个概念：

> **最佳推理边界。**

它表示：

> 在当前模型、任务、系统结构和风险条件下，让 Agent 能够可靠理解并闭合一个有意义结果，同时又不会产生过高边界协调成本的任务范围。

它不等于最小任务。

也不等于最大任务。

更接近：

> **最小完整任务。**

## 什么叫完整

一个任务要达到“完整”，通常需要满足：

- 目标闭合。
- 相关上下文完整。
- 关键依赖已知。
- 验证路径明确。
- 结果可以单独判断。
- 交付以后能够产生真实工程价值。

例如：

> “增加一个字段”

可能太小。

因为它本身不能闭合业务价值。

> “完成整个认证系统”

可能太大。

因为它超出有效推理范围。

而：

> “修复 access token 过期后 refresh token 无法续期的问题”

可能更加接近一个完整任务。

它拥有：

- 明确问题。
- 有限范围。
- 相关依赖。
- 清晰验证。
- 独立价值。

## 任务边界不是按文件数量决定

最佳推理边界不能简单根据：

- 修改几个文件。
- 多少行代码。
- 多少 Token。
- 多少函数。

来判断。

例如：

> 修改 3 行支付金额逻辑

可能风险非常高。

而：

> 新增 500 行内部工具代码

可能非常低风险。

因此，任务边界应该更多考虑：

- 认知复杂度。
- 依赖复杂度。
- 风险。
- 验证难度。
- 跨边界影响。
- 失败成本。

---

# 边界协调成本来自哪里

可以把边界协调成本进一步拆成几个主要来源。

## 上下文重建成本

每个新的 Worker 都需要重新理解：

- 任务。
- 背景。
- 边界。
- 依赖。
- 已有决定。

任务越碎：

> 重复构建上下文的次数越多。

## 交接成本

每一次交接都需要：

- 总结状态。
- 生成产物。
- 明确下一步。
- 传递风险。
- 解释未完成内容。

交接越多：

> 信息丢失概率越高。

## 契约成本

不同任务之间如果存在依赖：

就需要维护输入输出契约。

例如：

- 字段。
- API。
- 状态。
- 语义。
- 失败行为。

任务越碎：

> 契约数量通常越多。

## 等待成本

很多任务存在依赖关系。

例如：

> A 完成以后 B 才能开始。

如果拆得过细：

> 系统会产生大量等待。

这会降低整体吞吐。

## 集成成本

局部结果完成以后，需要重新检查：

- 是否可以组合。
- 是否破坏其他模块。
- 是否存在跨边界冲突。

任务越碎：

> 集成工作越多。

## 重复验证成本

如果一个完整功能被拆成多个任务：

每个任务需要局部验证。

最终功能还需要整体验证。

这会产生重复成本。

## 状态管理成本

每增加一个任务：

> 就多一个状态。

更多任务意味着：

- 更多 Task ID。
- 更多 Gate。
- 更多失败记录。
- 更多恢复路径。
- 更多运行时管理。

## 真相传播成本

当项目真相变化以后：

边界越多。

受影响的局部投影越多。

需要重新评估的任务和证据也可能越多。

---

# 边界数量并不是唯一变量

边界协调成本也不能简单理解成：

> 边界越多，成本一定线性增加。

真正影响成本的还有：

- 边界之间耦合程度。
- 依赖密度。
- 契约稳定性。
- 状态共享程度。
- 任务并行能力。
- 工具自动化程度。

例如：

```text
10 个完全独立的模块
```

可能比：

```text
3 个高度耦合模块
```

更容易协调。

因此：

> 边界数量只是一个表面指标。

更重要的是：

> **跨边界依赖结构。**

---

# 高耦合边界

如果两个任务之间需要频繁交换：

- 状态。
- 数据。
- 决策。
- 上下文。
- 验证结果。

那么即使它们被形式上拆成两个任务：

> 它们实际上仍然高度耦合。

这种情况下继续拆分，收益可能很低。

---

# 低耦合边界

如果两个任务：

- 输入清晰。
- 输出清晰。
- 依赖稳定。
- 可以独立验证。
- 几乎不共享状态。

那么拆分通常成本更低。

因此：

> 边界是否值得存在，和边界两侧的耦合程度高度相关。

---

# API 不是天然最佳边界

大型软件经常以 API 为自然边界。

这通常很有用。

但 API 也不是绝对最佳任务粒度。

有些任务可能需要同时修改：

- Controller。
- Service。
- Repository。
- Test。

如果它们共同形成一个完整业务行为：

> 拆成多个任务反而会增加协调成本。

因此：

```text
API 是常见边界。
并非永远是最佳推理边界。
```

---

# 领域边界

在复杂业务系统中：

领域边界往往比代码文件边界更加稳定。

例如：

- 支付。
- 退款。
- 订单。
- 账户。
- 结算。

如果任务边界和领域边界一致：

Agent 更容易获得：

- 完整业务规则。
- 清晰所有权。
- 稳定契约。

因此：

> 最佳推理边界通常应该尊重领域结构。

---

# 用例边界

某些任务更适合按业务用例切分。

例如：

- 创建订单。
- 退款。
- 刷新 Token。
- 重新计算账单。

这些任务拥有：

- 明确输入。
- 明确行为。
- 明确结果。
- 明确验证。

因此：

> 用例往往是非常实用的 Agent 任务边界。

---

# 依赖边界

还有一些场景需要按照依赖图切分。

例如：

当前需求会影响：

```text
Module A

Module B

Module C
```

其中：

- A 和 B 高度耦合。
- C 只通过稳定 API 依赖。

那么可能更合理的切法是：

```text
A + B

作为一个任务世界。

C

作为另一个独立任务。
```

因此：

```text
最佳边界应该尽量把强依赖留在边界内部。
把稳定依赖放在边界外部。
```

---

# 最佳边界的一个直觉

一个好的边界通常具有：

```text
边界内部：
高内聚。

边界外部：
低耦合。
```

Agent 软件工程可以继续沿用这个传统软件工程原则。

只是现在多了一层新的意义：

- 高内聚可以降低跨 Agent 协调成本。
- 低耦合可以减少上下文传播。

---

# 边界和有效推理范围之间的关系

第 09 章提出：

> 相关问题范围应该控制在有效推理范围内。

第 15 章进一步补充：

> 在满足这个条件以后，还应该尽量减少不必要的边界。

因此：

```text
先保证任务没有大到 Agent 看不清。
然后再避免为了“更小”继续拆分。
```

---

# 一个简单判断过程

对于一个候选任务，可以连续问：

```text
Agent 能完整理解这个问题吗？

如果不能：
继续切分。

如果可以：
再问：

这个任务内部是否存在多个几乎独立的结果？

如果存在：
可以考虑拆分。

如果不存在：
再问：

继续拆分是否会增加明显交接、契约和集成成本？

如果会：
应该停止继续切分。
```

---

# 边界和风险

最佳边界还受到风险影响。

低风险任务可以允许更大的任务范围。

因为：

- 即使出现错误。
- 容易发现。
- 容易回滚。
- 损失有限。

高风险任务通常需要更严格边界。

因为：

- 支付。
- 安全。
- 权限。
- 数据迁移。
- 生产操作。

错误成本很高。

因此：

> 高风险区域可能值得支付更高边界协调成本，换取更强局部控制。

---

# 边界和可逆性

如果一个任务高度可逆：

可以允许 Agent 在更大范围内探索。

例如：

- 本地代码生成。
- 内部重构。
- 实验性功能。

如果任务不可逆：

边界通常需要更严格。

例如：

- 生产删除。
- 真实资金操作。
- 外部资源创建。

因此：

> 失败可逆性会影响最佳边界。

---

# 边界和验证能力

如果一个任务拥有：

- 强自动化测试。
- 可靠静态分析。
- 清晰运行时验证。

那么 Agent 可以安全处理更大的范围。

如果验证能力非常弱：

即使任务看起来很小，也需要更加谨慎。

因此：

> 最佳边界会随着验证能力变化。

---

# 边界和模型能力

随着模型能力提升：

有效推理范围可能扩大。

一些今天必须拆分的任务：

未来可能可以直接作为一个整体交给 Agent。

因此：

> 最佳推理边界不是永久固定的工程常量。

它会随着：

- 模型。
- 工具。
- 上下文系统。
- 验证能力。
- 工作流成熟度。

持续变化。

---

# 边界和工具能力

如果 Agent 可以使用：

- 代码搜索。
- 依赖分析。
- 类型系统。
- 测试工具。
- 数据库检查。
- 运行时调试。

那么它可以更可靠地理解较大问题。

如果 Agent 只能阅读 Prompt：

最佳边界通常需要更小。

因此：

> Agent 能调用的工具会直接影响任务粒度。

---

# 边界和自动化协调

边界协调成本也可以被工具降低。

例如：

- 自动上下文构建。
- 自动生成任务契约。
- 自动依赖追踪。
- 自动状态转换。
- 自动证据绑定。
- 自动集成验证。

这些能力越成熟：

> 系统就越可以承受更细的任务切分。

因此：

> 最佳边界由 Agent 能力和工作流能力共同决定。

---

# Human 边界协调成本

边界成本最终也可能落到 Human 身上。

例如：

- Agent 负责开发。
- Agent 负责 QA。
- Agent 负责架构。
- Agent 负责文档。

如果每个 Agent 都需要 Human 手动：

- 复制内容。
- 传递信息。
- 确认状态。
- 决定下一步。

那么系统的自动化程度其实仍然有限。

Human 变成：

> 边界协调器。

因此：

> 一个成熟的 Agent Workflow 应该尽量自动处理稳定的边界交接。

---

# 边界协调自动化

稳定的边界交接可以逐渐编码成：

- 结构化产物。
- 状态机。
- Gate。
- 标准契约。
- 自动路由。
- 上下文构建器。
- 证据映射。

这样：

> Human 不需要每次重新设计交接。

---

# 任务合并

当发现任务切得过细以后：

系统应该允许重新合并。

例如：

```text
Task A

Task B

Task C
```

长期表现出：

- 总是一起执行。
- 总是共享上下文。
- 总是相互等待。
- 总是需要一起验证。

这说明：

> 它们可能属于同一个更自然的任务边界。

---

# 任务拆分

反过来：

如果一个任务长期出现：

- 上下文过大。
- 多次遗漏。
- 验证困难。
- 反复返工。
- 跨多个不同业务责任。

就说明：

> 当前边界可能太大。

应该继续拆分。

---

# 执行数据可以帮助调整边界

最佳边界不一定只能由架构师提前设计。

工作流本身也可以收集历史数据。

例如：

- 任务返工次数。
- QA 回退次数。
- 上下文大小。
- 执行时间。
- 验证成本。
- 跨任务依赖数量。
- 失败率。
- Human 介入次数。

这些数据可以帮助判断：

> 某类任务是否切得太大。

> 或者太小。

---

# 一个可学习的任务粒度

长期来看，可以设想：

工作流根据历史执行结果，逐渐学习某个项目最合适的任务粒度。

例如：

- 某类 API 任务：通常一个完整用例直接交付最稳定。
- 某类数据库迁移：需要拆成设计、实现、验证三个阶段。
- 某类 UI 修改：无需单独 QA Agent。

这些经验可以逐渐进入：

- 任务模板。
- 工作流规则。
- 自动切分策略。

---

# 边界成本与治理成本

边界增加以后：

治理成本也会上升。

因为：

- 更多 Task。
- 更多状态。
- 更多 Gate。
- 更多证据。
- 更多真相投影。
- 更多权限边界。

因此，切分策略也需要考虑：

> 系统有没有能力管理这些边界。

---

# 边界税

可以把所有这些额外成本统称为：

> **边界税。**

这个词用于提醒我们：

> 每创建一个边界，系统就需要支付维护费用。

边界税可能由：

- Agent 支付。
- 工作流系统支付。
- Human 支付。
- 运行时支付。
- 验证系统支付。

因此：

> 边界越多，并不天然代表工程越成熟。

---

# 边界税的主要组成

可以暂时分成：

- 上下文税。
- 交接税。
- 契约税。
- 状态税。
- 验证税。
- 集成税。
- 等待税。
- 真相同步税。
- Human 注意力税。

这些名字目前主要用于帮助分析。

它们并不是精确测量模型。

---

# 一个工作模型

可以暂时把总工程成本理解成：

```text
总成本
≈
局部推理成本
+
边界协调成本
+
验证成本
+
治理成本
```

任务过大：

> 局部推理成本上升。

任务过小：

> 边界协调和治理成本上升。

因此最佳边界位于中间某个区域。

这个模型目前主要用于思考。

还没有足够证据把它当成精确公式。

---

# 一个更简单的表达

也可以简化成：

```text
大任务的问题：

Agent 看不清。

小任务的问题：

系统接不起。

真正好的边界：

Agent 看得清。

系统接得起。
```

---

# 最佳推理边界的判断维度

当前可以从几个维度判断一个边界是否合适。

第一：Agent 是否能够完整理解当前问题。

第二：任务是否闭合一个真实工程结果。

第三：任务能否独立验证。

第四：跨边界依赖是否清晰。

第五：是否需要频繁共享状态。

第六：边界两侧契约是否稳定。

第七：失败以后是否容易定位责任。

第八：重新执行是否容易。

第九：Human 是否需要频繁手工协调。

第十：当前粒度是否产生过多重复验证。

---

# 失败模式一：无限细分

每个 Task 都非常小。

每个 Agent 都非常稳定。

但系统有几百个任务。

大量成本消耗在：

- 交接。
- 等待。
- 集成。
- 状态同步。

这种系统：

```text
局部成功。
整体低效。
```

---

# 失败模式二：为了减少边界而保持巨大任务

系统害怕协调成本。

于是把复杂需求全部交给一个 Agent。

Agent 上下文巨大。

推理可靠性下降。

最终返工成本可能远大于节省的协调成本。

---

# 失败模式三：按代码结构机械切分

Controller 一个任务。

Service 一个任务。

Repository 一个任务。

Test 一个任务。

但真实业务行为跨越全部层。

结果：

> 任务边界和问题边界完全错位。

---

# 失败模式四：按组织结构切分

Team A 一个任务。

Team B 一个任务。

但当前工程问题高度跨团队耦合。

> 组织边界不能自动等于最佳推理边界。

---

# 失败模式五：边界很多，但契约不稳定

系统切得很细。

API 和契约却频繁变化。

结果：

- 大量任务不断失效。
- 大量 Agent 重做。

这种系统会产生非常高的边界税。

---

# 失败模式六：Human 成为边界总线

每个 Agent 都需要 Human 手工传递上下文。

Human 实际承担：

- 消息路由。
- 状态同步。
- 冲突协调。
- 任务合并。

这说明：

> 工作流的边界还没有被真正系统化。

---

# 失败模式七：只关注 Token 成本

系统认为：

> 任务 Token 很少。

所以任务粒度很好。

但忽略：

- 验证成本。
- 集成成本。
- 依赖复杂度。
- Human 注意力。

最终整体成本反而更高。

---

# 一个可复用的边界评估流程

对于一个候选任务，可以使用下面的流程。

1. 明确任务要闭合的真实结果。
2. 识别当前任务必须同时理解的相关现实。
3. 判断是否超过 Agent 有效推理范围。
4. 找出任务内部的强依赖。
5. 找出任务外部的跨边界依赖。
6. 判断外部契约是否稳定。
7. 判断任务是否能够独立验证。
8. 判断失败以后是否容易恢复。
9. 评估继续切分会增加多少：
   - 交接。
   - 契约。
   - 状态。
   - 验证。
   - 等待。
10. 如果当前任务仍然过大：继续切分。
11. 如果任务已经足够可靠：停止继续切分。
12. 如果多个任务长期高度耦合：重新考虑合并。

可以表示为：

```text
候选任务
↓
评估推理复杂度
↓
超过有效推理范围？
↓
├── 是
│   ↓
│   继续切分
│
└── 否
    ↓
评估边界协调成本
    ↓
继续切分是否明显增加协调？
    ↓
├── 是
│   ↓
│   保持当前边界
│
└── 否
    ↓
根据独立性和并行价值决定是否继续拆分
```

---

# 一个边界优化循环

长期运行以后：

```text
任务执行
↓
收集结果
↓
观察：

返工率。

QA 回退。

执行时间。

上下文规模。

交接次数。

依赖冲突。

Human 介入。

验证成本。

↓
判断：

边界太大？

边界太小？

↓
调整任务模板
↓
下一轮执行
```

这样任务粒度可以逐渐从：

```text
人工直觉
```

演化为：

```text
基于执行证据的工程策略。
```

---

# 边界并非越稳定越好

边界也需要允许变化。

随着：

- 系统重构。
- 业务变化。
- Agent 能力提升。
- 验证能力增强。

过去合理的边界可能不再合理。

因此：

> **边界本身也属于可以被重新设计的工程对象。**

---

# 与第 10 章的关系

第 10 章回答：

> 复杂问题怎样被切分，并通过边界、契约和工程产物重新组合。

第 15 章进一步回答：

> 切分本身需要支付多少成本，以及什么时候应该停止继续切分。

可以理解成：

```text
第 10 章关注：
怎样切。

第 15 章关注：
切到哪里。
```

---

# 与第 09 章的关系

第 09 章提出：

> 相关问题范围应该控制在有效推理范围内。

第 15 章补充：

> 满足有效推理范围只是下限条件。

真正优秀的边界还需要控制：

- 协调成本。
- 验证成本。
- 治理成本。

---

# 与第 16 章的关系

任务边界越多：

- 决策越多。
- Gate 越多。
- 证据越多。
- Human 潜在审批越多。

因此：

> 边界税最终会继续转化成治理成本。

下一章会进一步讨论：

> 当 Agent 数量和工作流规模持续扩大以后，治理本身怎样避免成为新的系统瓶颈。

---

# 仍在研究的问题

当前还有几个重要问题尚未解决。

第一，边界协调成本能否形成可实际测量的指标。

第二，怎样区分“正常协调成本”和“过度切分产生的浪费”。

第三，跨边界依赖复杂度应该怎样表示。

第四，是否可以根据历史执行数据自动建议任务合并或拆分。

第五，不同模型的最佳推理边界差异有多大。

第六，风险等级应该怎样进入边界选择。

第七，验证能力增强以后，任务边界到底可以扩大多少。

第八，怎样判断一个边界已经从保护机制变成治理负担。

第九，并行 Agent 增加以后，边界税会怎样变化。

第十，是否存在一套通用边界评估方法，还是不同领域必须拥有完全不同的经验模型。

这些问题仍然需要更多真实工程验证，会继续在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **任务太大会产生推理风险。**

---

> **任务太小会产生边界协调成本。**

---

> **切分不会消灭复杂度，它会重新分配复杂度。**

---

> **每一个边界都需要支付协调成本。**

---

> **边界数量本身不重要，跨边界依赖复杂度更重要。**

---

> **强依赖应该尽量留在边界内部。**

---

> **稳定依赖更适合跨越边界。**

---

> **最佳推理边界会随着模型、工具、风险和验证能力变化。**

---

> **Agent 看得清，只解决了一半问题。**

---

> **系统还需要接得起。**

---

> **真正需要寻找的，是最小但完整、可靠且协调成本可接受的问题世界。**

---

# 结语

Agent 软件工程很容易形成一种简单直觉：

> 任务越小，越安全。

这条规律只成立到某一个位置。

当任务继续缩小以后：

局部推理越来越简单。

整个系统却开始承担更多：

- 边界。
- 契约。
- 交接。
- 状态。
- 验证。
- 等待。
- 治理。

最终，复杂度并没有消失。

它只是从：

```text
一个 Agent 的推理内部
```

转移到了：

```text
大量 Agent 之间的协调关系中。
```

因此，一个成熟的 Agent 系统需要持续寻找平衡。

任务不能大到 Agent 看不清。

也不能小到系统接不起。

真正优秀的边界应该让一个 Worker 能够：

- 理解完整问题。
- 闭合真实结果。
- 独立验证。
- 清晰交接。

同时尽量减少不必要的跨边界依赖。

这就是最佳推理边界真正想解决的问题：

```text
AI 看得清。

系统接得起。

工程整体仍然可控。
```
