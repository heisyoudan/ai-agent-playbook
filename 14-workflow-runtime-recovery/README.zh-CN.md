# 14 — 工作流运行时与恢复

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续研究（Research）** · **成熟度：观察模式（Observed Pattern）**

---

# 为什么需要工作流运行时

一个简单 Agent 任务通常可以在一次会话里完成。

例如：

- 读取代码。
- 修改实现。
- 运行测试。
- 输出结果。

但真实工程很少一直这么简单。

一个完整工作流可能经历：

- 需求分析。
- 设计。
- 开发。
- 测试。
- 审查。
- 返工。
- 重新验证。
- 等待外部信息。
- 人工确认。
- 发布。
- 回滚。
- 恢复。

这意味着任务会跨越：

- 多个 Agent。
- 多个会话。
- 多个工具。
- 多个时间点。
- 多个状态。

此时就会出现一个基本问题：

> **系统怎么知道自己现在在哪里？**

---

# 状态不能只存在于对话里

很多 Agent 工作流早期会依赖聊天记录维持状态。

例如：

```text
上一次对话说：

“开发已经完成，下一步进入 QA。”
```

下一次会话开始时，Agent 再读取历史记录，然后继续。

这种方式在简单场景中可以工作。

但随着工作流变长，会越来越脆弱。

因为：

- 会话可能被截断。
- 上下文可能被清理。
- 模型可能更换。
- Agent 可能更换。
- 历史消息可能非常长。
- 状态可能分散在多个聊天里。
- 不同 Agent 对当前阶段可能理解不同。

因此：

> **工作流状态不能只存在于某一个 Worker 的记忆中。**

---

# 什么是工作流运行时

工作流运行时指：

> 负责维护任务在执行过程中的当前状态、允许变化和恢复路径的工程机制。

它至少需要回答：

- 现在处于什么阶段？
- 当前由谁负责？
- 上一步是什么？
- 下一步允许去哪里？
- 当前为什么停在这里？
- 哪些条件已经满足？
- 哪些条件还没有满足？
- 是否发生过失败？
- 是否允许重试？
- 是否允许重新执行？
- 当前产物是否仍然有效？
- 中断以后应该从哪里恢复？

---

# 运行时与工作流定义的区别

工作流定义描述：

> 理论上任务应该怎样流转。

例如：

```text
设计
↓
开发
↓
QA
↓
完成
```

运行时描述：

> 某一个真实任务现在实际处于哪里。

例如：

```text
Task K42

当前状态：
QA

上一步：
Dev

最近结果：
QA FAIL

失败原因：
缺少边界测试

当前责任：
Dev

下一步：
重新实现后再次进入 QA
```

因此：

```text
工作流定义是规则。
运行时状态是现实。
```

---

# 状态

状态描述：

> 当前执行位于哪里。

例如：

- 待处理。
- 分析中。
- 开发中。
- 等待验证。
- 验证失败。
- 等待 Human。
- 暂停。
- 完成。
- 取消。
- 需要重新打开。

状态应该是显式的。

不能只靠：

> “从对话来看应该已经进入 QA 了。”

来推断。

---

# 状态必须有唯一可信来源

如果：

- Agent A 认为任务在开发。
- Agent B 认为任务在 QA。
- 项目看板认为任务已完成。
- Git 分支仍然没有提交。

那么工作流已经失去一致性。

因此，运行时应该存在一个：

> **权威状态来源。**

可以是：

- 数据库记录。
- 结构化 JSON。
- 任务系统。
- 工作流引擎。
- 版本化状态文件。

具体实现并不重要。

重要的是：

系统必须能够回答：

> 当前状态到底是什么？

而且只能有一个最终可信答案。

---

# 状态和证据不同

第 11 章已经讨论过：

证据说明：

> 发生了什么。

状态说明：

> 现在在哪里。

例如：

```text
测试报告 PASS

属于证据。
```

```text
任务状态 QA Passed

属于状态。
```

两者不能混在一起。

因为测试报告可能仍然存在，但：

- 代码已经变化。
- 证据可能失效。
- 状态也可能重新打开。

因此：

> **证据不能自动代替状态。**

---

# 状态和真相也不同

真相描述：

> 当前项目被允许继续依赖什么。

状态描述：

> 任务执行到哪里。

例如：

```text
“退款不得超过已支付金额”

属于项目真相。
```

```text
“退款修复任务正在 QA”

属于执行状态。
```

两者之间有关联。

但不是同一个东西。

---

# 状态转换

工作流运行时真正重要的能力之一，是控制状态怎样变化。

例如：

```text
Dev
↓
QA
```

不能只是任何 Agent 想切就切。

状态转换应该有明确条件。

例如：

```text
Dev → QA

需要：

实现完成。

构建通过。

必要测试完成。

产物已保存。

开发总结已生成。

边界没有被突破。
```

只有满足这些条件，转换才有效。

---

# 转换应该是显式事件

一个高质量工作流最好能够记录：

- 从什么状态。
- 转换到什么状态。
- 什么时候。
- 由谁触发。
- 为什么。
- 基于什么证据。

例如：

```text
2026-09-20 21:43

Task K42

Dev
→
QA

触发者：
Dev Agent

依据：
Build PASS
Unit Test PASS
Implementation Summary 已生成
```

这样以后系统可以追踪：

> 任务为什么进入了当前状态。

---

# 状态转换不是自然语言约定

如果 Agent 只是说：

> “我认为现在可以进入 QA。”

这只是一个建议。

真正的状态变化应该由：

> 运行时

执行转换。

否则：

```text
语言输出
和
工程状态
```

会混在一起。

---

# 质量门

一些状态转换需要经过质量门。

例如：

```text
Dev
↓
QA Gate
↓
PASS → QA
FAIL → Dev
```

质量门负责检查：

> 是否满足转换条件。

它可以基于：

- 测试。
- 证据。
- 契约。
- 风险等级。
- Human 决策。
- 自动检查。

---

# Gate 和 Verdict 不同

这里还需要区分两个概念：

```text
Gate
和
Verdict。
```

Gate 是：

> 是否允许通过某个状态边界的机制。

Verdict 是：

> 验证者给出的判断。

例如：

QA Agent 给出：

```text
FAIL
```

这是 Verdict。

工作流根据规则：

```text
FAIL → 返回 Dev
```

这是 Gate 行为。

因此：

```text
Verdict 是判断结果。
Gate 是状态控制机制。
```

---

# 失败

Agent 工作流中的失败非常正常。

例如：

- 构建失败。
- 测试失败。
- 工具超时。
- 上下文不足。
- 依赖不可用。
- 权限不足。
- 验证不通过。
- 外部系统异常。
- Human 拒绝。

真正的问题不是：

> 能不能避免所有失败。

更重要的是：

> 失败以后系统是否知道发生了什么。

---

# 失败需要成为显式状态

如果一个 Agent 执行失败以后，只是在聊天里说：

> “这里有问题。”

然后重新尝试。

系统很容易失去：

- 失败次数。
- 失败原因。
- 之前尝试过什么。
- 当前恢复到了哪里。

因此，高价值失败应该进入结构化状态。

例如：

```text
execState：dev
previousState：qa
latestVerdict：FAIL

失败类型：
Missing Boundary Test

失败时间：
2026-09-20

失败来源：
QA Agent

恢复动作：
Return to Dev
```

这样失败不会随着会话结束消失。

---

# 失败证据应该持久存在

第 11 章已经讨论过：

失败证据也属于工程知识。

运行时需要进一步保存：

- 哪次执行失败。
- 失败发生在哪个状态。
- 当时使用了什么版本。
- 进行了什么恢复。
- 恢复是否成功。

这样以后系统可以判断：

> 当前任务是不是反复失败在同一位置。

---

# 重试

重试指：

> 同一个执行步骤，在相同目标和基本条件下再次尝试。

例如：

外部 API 暂时超时。

第一次调用失败。

稍后再次执行同一调用。

这属于重试。

重试通常假设：

- 任务目标没有变化。
- 输入基本没有变化。
- 当前状态仍然有效。
- 失败可能是暂时性的。

---

# 重新执行

重新执行和重试不同。

重新执行指：

> 重新评估当前真实状态以后，再次执行某个任务。

例如：

开发 Agent 上次修改失败。

之后：

- 代码已经变化。
- 依赖已经变化。
- 其他 Agent 已经修改相关模块。

此时再次运行开发任务。

不能假设：

> 上次停在哪里，这次就从那里继续。

更安全的方式是：

```text
重新读取当前状态。
重新读取当前真相。
重新计算差异。
然后执行。
```

因此：

```text
重新执行
≠
简单重试。
```

---

# 恢复

恢复指：

> 工作流在中断、失败或暂停以后，重新进入一个有效可继续状态。

恢复可能包含：

- 重新读取状态。
- 重新验证已有产物。
- 重新构建上下文。
- 检查证据是否仍然有效。
- 判断哪些步骤可以跳过。
- 判断哪些步骤必须重做。

恢复重点在于：

> 重新建立一个可信执行起点。

---

# 恢复和继续不同

“继续上次会话”

并不等于：

恢复工作流。

会话继续只说明：

> 聊天上下文可能仍然存在。

工作流恢复需要重新确认：

- 状态是否仍然有效？
- 代码是否变化？
- 真相是否变化？
- 证据是否过期？
- 依赖是否变化？
- 任务是否仍然应该继续？

因此：

```text
会话恢复
≠
工作流恢复。
```

---

# 重新执行和断点继续不同

一个常见误解是：

> Agent 上次做到步骤 7。

> 这次就从步骤 8 开始。

这个逻辑只有在以下条件都成立时才安全：

- 步骤 1～7 的结果仍然有效。
- 相关代码没有变化。
- 依赖没有变化。
- 任务目标没有变化。
- 项目真相没有变化。
- 证据没有失效。

否则：

```text
继续步骤 8
```

可能建立在已经失效的前提上。

因此：

```text
TODO 列表
≠
可靠恢复点。
```

---

# 检查点

检查点指：

> 系统确认某个阶段的结果已经达到可以安全保存和恢复的状态。

例如：

- 架构决策已批准。
- 任务契约已冻结。
- 实现已完成并通过构建。
- QA 已通过。
- 发布包已生成。

一个有效检查点应该能够回答：

- 这里保存了什么？
- 为什么可信？
- 依赖什么版本？
- 恢复以后可以从这里继续吗？

---

# 检查点需要有效条件

检查点不能永远有效。

例如：

```text
QA 已通过。
```

后来：

- 项目真相变化。
- 相关代码变化。
- 外部契约变化。

这时原 QA 检查点可能已经失效。

因此一个检查点最好知道：

- 依赖哪些真相。
- 依赖哪些代码。
- 依赖哪些证据。
- 哪些变化会使它失效。

---

# 持久执行状态

如果工作流需要跨越：

- 多个会话。
- 多个 Agent。
- 多天甚至数周。

那么执行状态需要持久保存。

持久状态可能包括：

```text
任务 ID。

当前阶段。

当前负责人。

当前任务契约。

最近一次有效转换。

失败历史。

重试次数。

关联产物。

关联证据。

阻塞原因。

等待条件。

当前真相版本。

依赖关系。
```

具体字段可以根据系统变化。

核心目标是：

```text
Worker 可以替换。
执行状态仍然存在。
```

---

# Worker 是可替换的

一个健康的 Agent 工作流应该允许：

- Dev Agent A 消失。
- Dev Agent B 接手。
- QA Agent 更换模型。
- Human 更换设备。
- 会话结束。

只要项目状态和必要产物仍然存在：

工作就可以继续。

因此：

> **Worker 不应该成为执行连续性的唯一来源。**

---

# 恢复需要重新建立当前现实

一个可靠恢复流程首先应该问：

> 现在的世界和中断前还是同一个世界吗？

例如：

任务中断前：

```text
Commit A

Project Truth v10

Contract C4
```

恢复时：

```text
Commit D

Project Truth v12

Contract C5
```

这时候：

```text
直接从原步骤继续
```

显然是不安全的。

因此恢复应该从：

> **现实重建**

开始。

---

# 状态感知的重新执行

可以把一种更可靠的方法称为：

> **状态感知的重新执行。**

它的过程是：

```text
读取当前任务
↓
读取权威状态
↓
读取当前真相
↓
读取当前代码和依赖
↓
读取已有产物与证据
↓
比较上次执行条件
↓
判断：

哪些仍然有效？

哪些已经失效？

哪些需要重新执行？

↓
继续工作
```

这种方式不强求：

> 从精确机器断点恢复。

它更关注：

> 从当前真实世界安全重新进入执行。

---

# 幂等性

恢复和重新执行会带来一个危险：

> 同一个操作如果重复执行，会不会产生副作用？

例如：

生成文件

通常容易重复执行。

但：

- 发送真实支付请求。
- 删除生产数据。
- 提交外部订单。
- 发送客户邮件。
- 执行不可逆迁移。

这些操作不能简单重跑。

因此工作流需要知道：

> 哪些步骤是幂等的。

> 哪些步骤不是。

## 幂等步骤

可以安全重复执行。

例如：

- 重新运行静态分析。
- 重新读取代码。
- 重新生成临时报告。
- 重新运行只读查询。

## 非幂等步骤

重复执行可能产生新的现实结果。

例如：

- 扣款。
- 退款。
- 发送通知。
- 提交订单。
- 生产删除。
- 创建外部资源。

这类步骤需要更严格的恢复保护。

## 不可逆步骤

还有一些动作即使只执行一次，也很难恢复。

例如：

- 永久删除数据。
- 执行无法回滚的迁移。
- 对外发布敏感信息。

这类操作应该在运行时拥有：

- 更高权限。
- 更强 Gate。
- 更明确检查点。
- 更完整证据。

---

# 重试策略

重试不能无限进行。

例如：

```text
Agent 失败
↓
自动重试
↓
失败
↓
自动重试
↓
失败
↓
继续重试
```

这可能：

- 浪费资源。
- 反复制造相同错误。
- 掩盖真实问题。

因此运行时需要定义：

- 最大重试次数。
- 哪些错误允许重试。
- 等待多久。
- 什么时候升级。
- 什么时候安全停止。

## 可重试错误

例如：

- 临时网络超时。
- 工具偶发失败。
- 服务短期不可用。

## 不可重试错误

例如：

- 需求冲突。
- 权限不足。
- 关键证据缺失。
- 当前真相不确定。
- 架构冲突。

这种问题继续重试没有意义。

它们需要：

- 升级。
- 补充信息。
- 重新决策。

---

# 失败分类

运行时可以逐渐形成失败分类。

例如：

- 暂时性失败。
- 验证失败。
- 上下文缺失。
- 权限失败。
- 真相冲突。
- 外部依赖失败。
- 不可恢复失败。

每类失败可以拥有不同恢复路径。

---

# 暂停

有些任务不是失败。

只是暂时无法继续。

例如：

- 等待客户确认。
- 等待外部系统。
- 等待 Human 决策。
- 等待上游任务。
- 等待部署窗口。

这时候状态应该是：

```text
暂停 / 等待
```

而不是：

```text
失败。
```

---

# 等待状态需要明确条件

一个等待状态至少应该知道：

- 在等什么？
- 谁负责解除？
- 什么条件满足以后可以继续？
- 最长等多久？
- 超时以后怎么办？

否则：

```text
Waiting
```

很容易变成：

```text
永久遗忘。
```

---

# 恢复游标

很多系统会尝试记录：

> 上次做到哪里。

这个信息可以有价值。

但它只能作为：

> 恢复参考。

不能自动成为：

> 恢复真相。

因为：

> 上次位置没有说明当前世界是否仍然有效。

因此：

```text
恢复游标
≠
恢复依据。
```

---

# 产物和状态

产物可以帮助恢复。

例如：

- 设计文档。
- 任务契约。
- 代码提交。
- 测试结果。
- QA 报告。

但产物存在：

不代表运行时状态一定可以从它们自动推出。

例如：

一个 QA 报告 PASS。

系统可能已经：

- 重新打开任务。
- 修改代码。

因此：

```text
Artifact
≠
State。
```

产物是输入。

状态仍然需要独立管理。

---

# 证据和恢复

恢复时不能只问：

> 有哪些产物？

还要问：

> 这些产物现在仍然值得相信吗？

因此恢复流程需要调用第 11 章的证据逻辑：

- 证据覆盖。
- 证据时效。
- 证据版本。
- 失效条件。
- 未解决冲突。

---

# 真相和恢复

第 13 章讨论过：

真相变化可能让下游任务和证据失效。

因此工作流恢复时还需要判断：

> 当前 Project Truth 是否和上次执行一致。

如果真相已经变化：

可能需要：

- 重新生成上下文。
- 重新打开任务。
- 重新验证。
- 甚至重新设计。

---

# 状态转换需要审计

对于高价值工作流，状态变化应该可追踪。

例如：

```text
Task K12

Created
→ Ready
→ Dev
→ QA
→ Dev
→ QA
→ Human Gate
→ Completed
```

如果以后出现问题：

可以回顾：

- 哪个状态变化开始偏离？
- 谁触发？
- 当时依据什么？
- 为什么允许进入下一阶段？

---

# 回滚

回滚指：

> 把系统恢复到一个已知可信的之前状态。

例如：

- 代码回滚。
- 配置回滚。
- 部署回滚。
- 工作流状态回滚。

但回滚不能被简单理解成：

> 把状态字段改回去。

真正回滚还需要考虑：

> 真实世界中的副作用有没有撤销？

例如：

代码可以回滚。

已经发出的支付请求无法通过 Git 回滚。

因此：

```text
状态回滚
和
现实回滚
```

需要分开考虑。

---

# 补偿

对于无法真正撤销的操作，可能需要补偿。

例如：

```text
支付已执行。
```

不能“取消历史”。

只能通过：

```text
退款
```

形成新的现实结果。

因此 Agent 工作流在处理现实操作时，需要考虑：

失败以后是：

```text
回滚
```

还是：

```text
补偿。
```

---

# 安全停止

有些情况下，最正确的行为是停止。

例如：

- 项目真相冲突。
- 证据不足。
- 权限不够。
- 连续失败超过阈值。
- 外部系统状态不明。
- 不可逆步骤前验证失败。

此时 Agent 应该：

```text
停止传播不确定性。
保留状态。
记录证据。
升级问题。
```

---

# 安全停止本身也是能力

强大的 Agent 不应该只会：

> 继续尝试。

成熟工作流还需要让 Worker 能够明确说：

> 当前不能安全继续。

并把任务停在一个：

- 可解释。
- 可恢复。
- 可调查。

的状态。

---

# 失败模式一：状态只存在聊天里

会话结束。

所有人重新猜：

> 上次做到哪里。

结果：

```text
状态漂移。
```

---

# 失败模式二：TODO 被当成检查点

Agent：

> 步骤 1～7 已完成。

> 下次直接从步骤 8 开始。

但中间：

- 代码已经变化。
- TODO 仍然原样存在。

结果：

```text
旧执行计划被错误继续。
```

---

# 失败模式三：重跑被当成恢复

任务失败以后：

重新执行同一个 Prompt。

系统认为：

> 已经恢复。

但它没有重新检查：

- 当前真相。
- 当前代码。
- 当前证据。
- 当前状态。

这只是重跑。

---

# 失败模式四：无限重试

同一个错误反复出现。

系统持续自动重试。

没有升级。

最终浪费大量时间和资源。

---

# 失败模式五：非幂等操作被重复执行

网络超时以后：

系统不知道第一次真实请求是否成功。

于是直接重试。

最终产生重复现实操作。

---

# 失败模式六：恢复时使用失效证据

上次 QA PASS。

代码已经变化。

恢复流程仍然直接认为 QA 有效。

最终跳过必要验证。

---

# 失败模式七：状态和产物混为一谈

存在 QA 报告。

所以认为任务仍然在 QA Passed。

但实际任务已经重新打开。

系统出现状态冲突。

---

# 失败模式八：等待状态没有解除条件

任务进入：

```text
Waiting
```

但没有记录：

- 等待谁。
- 等待什么。
- 什么时候检查。

最终任务永久停留。

---

# 一个最小运行时模型

一个任务可以拥有：

```text
Task ID

Current State

Previous State

Owner

Current Action

Dependencies

Artifacts

Evidence

Failure History

Retry Count

Blocking Reason

Waiting Condition

Truth Version

Last Transition

Next Allowed Transitions
```

这些字段并非固定规范。

它们说明：

> 一个工作流运行时需要保存哪些类型的信息。

---

# 一个最小状态转换流程

状态变化可以经过：

```text
当前状态
↓
请求转换
↓
检查允许路径
↓
检查 Gate
↓
检查必要证据
↓
检查权限
↓
执行转换
↓
记录：

旧状态

新状态

时间

触发者

原因

证据

↓
进入新状态
```

# 一个最小恢复流程

1. 读取任务 ID。
2. 读取当前权威状态。
3. 读取最近有效转换。
4. 读取当前项目真相。
5. 读取当前代码和依赖状态。
6. 读取已有工程产物。
7. 检查已有证据是否仍然有效。
8. 检查当前任务范围是否变化。
9. 判断之前哪些结果仍然可信。
10. 判断哪些步骤需要重新执行。
11. 检查是否存在非幂等或不可逆操作。
12. 构建新的局部上下文。
13. 恢复到一个有效执行点。
14. 继续执行。

可以表示成：

```text
中断
↓
读取权威状态
↓
读取当前现实
↓
读取当前真相
↓
读取产物与证据
↓
比较上次执行条件
↓
├── 全部仍然有效
│   ↓
│   继续
│
├── 部分失效
│   ↓
│   局部重执行 / 重新验证
│
├── 真相变化
│   ↓
│   重新推导任务
│
└── 无法安全判断
    ↓
    停止并升级
```

# 一个最小重试流程

```text
失败
↓
分类错误
↓
是否可重试？
↓
├── 否
│   ↓
│   升级 / 停止
│
└── 是
    ↓
检查重试次数
    ↓
是否超过上限？
    ↓
├── 是
│   ↓
│   升级
│
└── 否
    ↓
等待 / 重试
    ↓
记录结果
```

# 状态感知的重新执行的适用范围

对于很多 Agent 软件工程任务，真正实用的方法不一定是复杂的断点恢复。

一个更现实的方案是：

> 状态感知的重新执行。

它依赖几个原则：

- 每次执行前重新读取当前现实。
- 不盲信上次会话状态。
- 已有产物可以复用。
- 已有证据需要重新确认有效性。
- 已经完成的步骤，如果前提仍然成立，可以跳过。
- 已经失效的步骤重新执行。

这样可以避免设计一个过度复杂的：

> 精确指令级恢复系统。

---

# 运行时和 Human

Human 也需要能够理解当前工作流状态。

一个好的运行时应该让 Human 快速回答：

- 哪些任务正在执行？
- 哪些等待我决定？
- 哪些失败？
- 哪些正在重试？
- 哪些证据已经失效？
- 哪些任务刚刚重新打开？
- 哪些操作即将进入高风险阶段？

这样 Human 才能真正拥有系统级治理能力。

# 运行时和 Maestro

像 Maestro 这样的工作流框架，本质上可以被理解成：

> 把一部分工作流运行时原则编码成可执行系统。

例如：

- 显式任务状态。
- 角色边界。
- 状态转换。
- Gate。
- QA 回退。
- Human Override。
- 结构化交接。
- 持久化任务真相。

但这一章讨论的方法不依赖 Maestro。

具体实现可以是：

- CLI。
- 数据库。
- 任务系统。
- JSON。
- 工作流引擎。
- 其他 Agent Framework。

核心原则保持不变。

---

# 工作流运行时不是聊天管理器

这里需要特别强调：

```text
Agent Workflow Runtime
```

并不只是：

- 保存聊天。
- 切换会话。
- 重新打开对话。

真正的运行时管理的是：

> 工程执行状态。

例如：

- Task K7 现在在 QA。
- QA 为什么失败。
- 哪些证据支持失败。
- 下一步应该回 Dev。
- Dev 修改以后哪些测试需要重跑。
- Human 是否需要介入。

这些才属于：

```text
工作流状态。
```

# 一个工作假设

可以暂时把可靠恢复理解成：

```text
当前权威状态
+
当前现实
+
当前项目真相
+
仍然有效的工程产物
+
仍然有效的证据
+
允许的状态转换规则
```

共同决定：

> 现在应该从哪里继续。

这个模型强调：

```text
恢复不是读取历史聊天以后“接着说”。
恢复是重新确认一个可信执行起点。
```

---

# 另一个工作假设

随着 Agent 执行越来越自动化：

工作流真正稀缺的可能逐渐从：

```text
执行能力
```

转向：

```text
状态连续性。
```

因为：

- Worker 可以替换。
- 模型可以替换。
- 会话可以替换。
- 工具可以替换。

但如果系统失去：

- 任务做到哪里。
- 为什么停。
- 哪些结果可信。
- 下一步允许做什么。

整个自动化体系仍然会失去连续性。

# 核心原则

本章可以浓缩成几句话：

> **状态不能只存在于聊天记录中。**

---

> **工作流需要唯一可信的执行状态来源。**

---

> **状态、证据和真相必须保持分离。**

---

> **状态转换应该显式、受控并可追踪。**

---

> **Verdict 是判断，Gate 是状态控制。**

---

> **重试、重新执行和恢复属于不同概念。**

---

> **会话恢复不等于工作流恢复。**

---

> **恢复游标不等于恢复依据。**

---

> **TODO 不等于检查点。**

---

> **工程产物不等于执行状态。**

---

> **恢复前需要重新确认当前现实。**

---

> **非幂等和不可逆操作必须受到更强保护。**

---

> **失败应该留下持久状态和证据。**

---

> **等待需要明确解除条件。**

---

> **安全停止也是成熟 Agent 的能力。**

---

> **Worker 可以替换，执行状态必须持续存在。**

---

# 结语

当 Agent 只处理一次性小任务时，聊天记录似乎足够。

当 Agent 开始承担真正的软件工程流程以后：

- 任务会跨越多个会话。
- 多个 Agent。
- 多个失败。
- 多个验证阶段。
- 多个 Human Gate。
- 多个现实变化。

这时候，系统最重要的问题之一就会变成：

```text
现在到底在哪里？

为什么在这里？

哪些东西仍然可信？

哪些东西已经失效？

下一步允许去哪里？

如果现在中断，明天还能不能可靠继续？
```

一个成熟的 Agent 工作流，不应该依赖某个 Worker 记住整个历史。

Worker 可以消失。

会话可以结束。

模型可以替换。

但：

- 任务状态。
- 工程产物。
- 验证证据。
- 项目真相。
- 状态变化历史。

必须持续存在。

只有这样，Agent 工作流才真正拥有：

```text
连续性。

恢复能力。

和工程意义上的运行时。
```
