# 12 — 决策权、人类质量门与决策压缩

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续演化（Evolving）**

---

# 为什么需要决策权

当 Agent 开始承担越来越多的软件工程工作以后，一个很自然的问题会出现：

> 谁有权做决定？

Agent 可以：

- 分析需求。
- 修改代码。
- 执行测试。
- 生成设计。
- 提出架构方案。
- 判断风险。
- 甚至协调其他 Agent。

但：

```text
能够提出一个决定
和
有权让整个项目依赖这个决定
```

属于两个不同层级的问题。

因此，Agent 软件工程需要显式设计：

> **决策权。**

---

# 决策权是什么

决策权指：

> 某个角色可以在什么范围内，让一个判断直接影响后续工程行为。

例如：

- 开发 Agent 可以决定局部变量命名。
- 开发 Agent 可以选择某个局部实现方式。
- QA Agent 可以拒绝不满足验收条件的任务。
- 架构角色可以调整模块边界。
- Human 可以批准高风险业务规则变化。

这些决定的影响范围完全不同。

因此，决策权不能简单表达成：

> Agent 有权限。

或者：

> Human 有最终权限。

更合理的方式是：

> **不同决策拥有不同等级的决策权。**

---

# 能力和权限需要分开

一个 Agent 很可能有能力完成某项工作。

这不代表它应该自动拥有对应决策权。

例如：

Agent 可能可以修改生产数据库。

从技术能力上，它做得到。

但这并不意味着它应该拥有：

> 直接执行不可逆数据变更的权限。

同样：

Human 拥有“批准”按钮。

也不意味着这个 Human 一定有能力判断当前架构是否安全。

因此需要始终区分两个问题：

> 它能不能做？

以及：

> **它有没有权决定？**

```text
能力描述执行可能性。
决策权描述工程授权范围。
```

---

# 决策权不能超过验证能力

这里可以形成一条非常重要的原则：

> **决策权不能超过验证能力。**

一个角色拥有越大的决策权，就越需要具备：

- 理解问题的能力。
- 识别风险的能力。
- 验证结果的能力。
- 理解失败后果的能力。

例如：

- 一个局部 UI 文案修改，可以让 Agent 直接完成。
- 一个普通业务逻辑调整，可以由 Agent 完成，再由独立验证确认。
- 一个跨模块架构调整，需要更高层级的工程判断。
- 一个支付规则变化，需要具备支付领域能力的人确认。
- 一个生产数据库不可逆迁移，需要更高强度的验证和明确责任人。

因此：

> 权限等级应该和验证能力、影响范围、失败成本共同匹配。

---

# 决策范围

可以把决策大致分成几个层级。

## 局部实现决策

例如：

- 局部算法选择。
- 变量命名。
- 内部函数拆分。
- 低风险重构。
- 测试辅助代码。

只要不违反既有边界和契约，这类决策通常可以直接交给 Agent。

## 任务级决策

例如：

- 当前任务应该怎样实现。
- 需要增加哪些测试。
- 局部错误应该怎样处理。

这类决策可以由执行 Agent 提出，并通过验证流程确认。

## 契约级决策

例如：

- API 行为变化。
- 数据结构变化。
- 重试语义变化。
- 错误码变化。
- 模块之间责任变化。

这些决定会影响多个 Worker 或模块，因此需要更高等级的验证。

## 跨边界决策

例如：

- 修改模块所有权。
- 改变依赖方向。
- 调整数据一致性策略。
- 重新划分业务域。

这类决策已经接近架构层。

## 全局高风险决策

例如：

- 资金规则。
- 认证规则。
- 权限模型。
- 安全策略。
- 隐私规则。
- 合规要求。
- 数据迁移。
- 生产删除。
- 不可逆外部操作。

这类决定需要明确的 Human 责任和更强证据。

---

# Human Gate

Human Gate 指：

> 某个工程结论需要由具备相应能力的人确认以后，才能继续传播。

这里有一个重要前提：

> **Human Gate 的价值来自判断能力。**

如果一个人：

- 不了解问题。
- 没有阅读证据。
- 无法判断风险。
- 只是点击 Approve。

那么系统虽然形式上存在 Human Gate，实际上并没有增加多少可信度。

因此：

> Human Gate 需要具备真实判断能力。

---

# 人类参与并不自动等于安全

Agent 系统很容易出现一种表面安全模式：

> 所有重要操作都需要 Human 审批。

看起来风险很低。

但如果 Agent 每天产生大量决策：

- 100 个任务。
- 200 个验证结果。
- 50 个风险提示。
- 30 个异常升级。

Human 很快会进入一种状态：

- 快速浏览。
- 凭经验判断。
- 机械批准。
- 忽略重复内容。

最终：

```text
Human Gate 仍然存在。
真实判断却逐渐消失。
```

这种现象可以理解成：

> **审批疲劳。**

---

# Human 也有有效推理范围

第 09 章讨论了 Agent 的有效推理范围。

Human 同样存在认知边界。

一个人无法可靠审查：

- 无限多代码。
- 无限多任务。
- 无限多日志。
- 无限多证据。

如果系统把所有 Agent 结果原样交给 Human：

```text
大量代码
+
大量日志
+
大量任务
+
大量风险
+
大量测试
↓
Human Review
```

Human 也会发生：

- 信息过载。
- 重要信号被淹没。
- 机械审批。
- 遗漏异常。

因此：

> **Human Gate 本身也需要被工程化。**

---

# Human 注意力是稀缺资源

随着 Agent 执行成本下降，Human 注意力会逐渐成为系统中的高价值资源。

因此一个重要原则是：

> **Human 注意力应该随着决策权和风险扩展，而不应该随着 Agent 吞吐量线性扩展。**

Agent 完成更多任务，并不意味着 Human 必须阅读更多原始信息。

更合理的方式是：

- Agent 自动处理低风险工作。
- 自动化系统过滤确定性问题。
- 验证 Agent 处理可以独立判断的问题。
- 只有真正需要高层判断的内容进入 Human Gate。

---

# 分层决策

一个可扩展的系统可以形成类似结构：

```text
低风险局部决策
↓
执行 Agent 自主处理

中等风险任务决策
↓
独立验证

契约变化
↓
更高层 Agent 或领域审查

跨边界问题
↓
架构层处理

高风险或全局问题
↓
具备相应能力的 Human
```

这样可以让：

```text
低成本决定自动完成。
高价值决定保留人工判断。
```

---

# 什么时候应该升级

Agent 不应该只根据：

> 我能不能继续做

来判断是否升级。

更重要的是：

> **当前决策是否已经超出我的授权范围？**

一些常见升级条件包括：

- 发现需求冲突。
- 发现项目真相可能错误。
- 发现跨模块影响。
- 发现需要修改公共契约。
- 发现安全风险。
- 发现资金风险。
- 发现不可逆操作。
- 验证结果互相冲突。
- 关键证据缺失。
- Agent 对结论存在高不确定性。
- 当前任务已经超出原始边界。

此时更安全的行为是：

```text
停止继续传播。
收集证据。
明确问题。
升级决策。
```

---

# 不确定性应该停止传播

Agent 系统中一个非常危险的现象是：

> 不确定性被不断向下传播。

例如：

```text
需求可能是 A。

↓
Agent 暂时假设 A。

↓
下一个 Agent 把 A 当成确定事实。

↓
后续实现全部依赖 A。

↓
最终系统已经无法区分：

A 是事实。

还是最开始的一次猜测。
```

因此可以形成一个重要原则：

> **未解决的不确定性不应该静默传播。**

当一个判断会影响多个下游任务时：

```text
不确定
↓
标记
↓
收集证据
↓
升级
↓
确认
↓
再继续传播
```

这样可以避免：

> 假设逐渐伪装成项目真相。

---

# 决策压缩

随着 Agent 数量增加，很多判断会重复出现。

例如：

- 什么情况下需要 Human 审批？
- 什么类型修改必须增加测试？
- 哪些目录不能修改？
- 什么风险等级需要独立验证？
- 什么情况下需要停止？

如果每一次都重新交给 Human 判断：

> Human 会不断重复相同决策。

因此可以引入：

> **决策压缩。**

---

# 什么是决策压缩

决策压缩指：

> 把已经反复出现、边界稳定的判断，编码成可以重复执行的工程规则。

例如：

原来：

```text
每次 Agent 修改数据库结构
↓
询问 Human
↓
Human 判断是否需要迁移审查
```

后来：

```text
规则定义：

数据库结构变化
→ 自动升级到迁移审查流程
```

这时 Human 不再重复做：

> “这种情况需不需要升级？”

这个判断已经被压缩成工作流规则。

---

# 决策压缩的形式

决策可以被压缩成很多形式。

## 规则

例如：

```text
修改公共 API
→ 必须执行契约验证
```

## 默认值

例如：

```text
普通内部重构
→ 默认允许 Agent 自主执行
```

## 模板

例如：

```text
所有数据库迁移任务必须包含：

影响范围

回滚方案

验证步骤

数据备份状态
```

## 检查清单

例如：

```text
发布前自动检查：

构建

测试

配置

迁移

兼容性

证据
```

## 质量门

例如：

```text
QA 未通过
→ 禁止进入发布状态
```

## 工作流状态

例如：

```text
开发
↓
QA
↓
失败
↓
返回开发
```

Human 不需要每次手动决定任务应该流向哪里。

---

# 决策压缩的价值

决策压缩可以减少：

- 重复判断。
- Human 注意力消耗。
- 不同时间做出不一致决定。
- 不同 Agent 得到不同规则。
- 临时口头约定。

它还可以让工程经验逐渐进入系统。

过去一次复杂判断：

```text
Human 分析
↓
做出决定
```

经过多次重复以后，可以逐渐变成：

```text
工程规则
↓
自动执行
```

这意味着经验开始被固化进工作流。

---

# 决策压缩不能丢失原因

决策压缩也存在风险。

如果系统只保留规则：

> 禁止 X。

但完全不知道：

> 为什么禁止 X。

几年以后：

- 环境变化。
- 架构变化。
- 风险变化。
- 模型能力变化。

团队仍然机械执行旧规则。

因此，高价值压缩决策最好保留：

- 规则。
- 适用范围。
- 形成原因。
- 相关风险。
- 来源。
- 重新打开条件。

这样未来才能判断：

> 这个规则还成立吗？

---

# 规则也需要边界

一条规则不能无限扩张。

例如：

> “数据库变化必须人工审批”

可能只适用于：

> 生产数据库结构变化。

不一定适用于：

> 测试数据库中的临时表。

因此，决策压缩需要明确：

- 适用范围。
- 例外条件。
- 风险等级。
- 触发条件。

否则规则本身会变成新的治理负担。

---

# 什么时候应该重新打开压缩决策

一些变化应该触发旧规则重新评估。

例如：

- 项目架构发生变化。
- 业务风险发生变化。
- 外部法规变化。
- 模型能力发生明显变化。
- 验证能力增强。
- 工具能力变化。
- 旧规则频繁产生误报。
- 旧规则已经无法解释现实。

这时：

```text
压缩决策
↓
重新打开
↓
重新验证
↓
更新规则
```

> 决策压缩需要可逆。

---

# 最小权限原则

决策权设计还可以遵循一个简单方向：

> **默认给 Worker 完成当前任务所需要的最小决策权。**

例如：

一个测试 Agent 需要：

- 读取代码。
- 执行测试。
- 读取日志。
- 提出失败结论。

它不一定需要：

- 直接修改生产配置。
- 发布代码。
- 修改业务规则。
- 改变项目真相。

权限越大：

> 潜在影响范围越大。

因此：

> Worker 的权限应该和当前职责匹配。

---

# 角色和权限

一个简单角色模型可能是：

## 开发 Agent

可以：

- 实现。
- 局部设计。
- 自检。
- 产生证据。
- 提出风险。
- 提出真相挑战。

不能：

- 私自修改高层业务规则。
- 批准自己的高风险变更。

## 验证 Agent

可以：

- 验证。
- 拒绝。
- 寻找反例。
- 产生独立证据。
- 提出冲突。

不能：

- 为了让测试通过而修改验收标准。

## 架构角色

可以：

- 处理跨边界冲突。
- 分析全局影响。
- 调整候选架构。
- 提出高层决策方案。

## Human

负责：

- 高风险现实授权。
- 重要业务判断。
- 不可逆决定。
- 无法自动验证的领域判断。
- 承担最终现实责任的决定。

---

# Human Gate 前应该发生什么

一个高质量 Human Gate 不应该直接收到：

> “请审核这 3000 行代码。”

更合理的输入应该经过压缩。

例如：

- 需要决定的问题
- 当前背景
- 候选方案
- 影响范围
- 关键证据
- 已执行验证
- 已发现风险
- 仍然存在的不确定性
- 需要 Human 做出的具体决定

可以形成：

```text
原始工程世界
↓
Agent 分析
↓
验证
↓
证据整理
↓
风险分类
↓
决策压缩
↓
Human Gate
```

Human 看到的是：

> **真正需要 Human 判断的问题。**

---

# Human Gate 的输入应该是决策包

可以把这种输入理解成：

> **决策包。**

一个最小决策包可以包含：

- 需要决定什么？
- 为什么现在需要决定？
- 有哪些候选方案？
- 每个方案影响什么？
- 哪些证据已经存在？
- 还有哪些不确定性？
- 如果不决定会发生什么？
- 建议下一步是什么？

这样 Human 的工作从：

```text
重新理解整个项目
```

变成：

```text
判断一个已经被压缩好的高价值问题。
```

---

# Human 不应该重复 Agent 已经可以可靠完成的工作

如果 Agent 已经可以稳定完成：

- 代码格式检查。
- 静态分析。
- 常规测试。
- 文件边界检查。
- 简单风险分类。

那么 Human 没有必要每次重新手工做一遍。

Human 应该主要集中在：

- 难以自动化的判断。
- 高风险决策。
- 模糊现实。
- 价值权衡。
- 领域责任。
- 不可逆选择。

这可以让 Agent 和 Human 的能力形成互补。

---

# 失败模式一：所有事情都交给 Human

工作流：

```text
Agent 做任何事情
↓
Human 审批
↓
继续
```

早期看起来非常安全。

随着吞吐量增加：

- 审批数量增加。
- Human 负担增加。
- 审批质量下降。

最后系统形成机械批准。

> 这种系统无法真正扩展。

---

# 失败模式二：Agent 拥有过大权限

Agent 负责一个局部任务。

但同时可以：

- 修改公共契约。
- 调整数据库结构。
- 改变生产配置。
- 修改项目真相。
- 直接发布。

这会让一个局部执行错误迅速扩大成系统级风险。

因此：

> **权限应该跟随职责边界。**

---

# 失败模式三：Human 有权批准，但没有能力验证

例如：

```text
复杂安全设计
↓
不熟悉安全领域的人点击 Approve
```

形式上完成了 Human Gate。

实际上没有增加有效判断。

因此：

> **Human Gate 需要匹配对应领域能力。**

---

# 失败模式四：不确定性继续传播

Agent 发现：

> 这个需求可能有两种解释。

但它没有升级。

而是选择一个更合理的解释继续开发。

后续所有 Agent 都把这个解释当成事实。

最终形成：

```text
假设
↓
实现
↓
测试
↓
文档
↓
项目真相
```

这会直接产生真相漂移。

---

# 失败模式五：决策压缩变成僵化规则

过去因为某次事故形成：

> 所有情况都必须人工审批。

后来系统已经拥有：

- 更好的自动验证。
- 更安全的回滚。
- 更明确的边界。

旧规则仍然从未重新评估。

结果治理成本持续存在。

因此：

> **压缩后的决策也需要生命周期。**

---

# 失败模式六：规则存在，但例外不可见

工作流通常要求 A。

某次特殊情况 Human 允许 B。

但没有记录原因。

以后其他 Agent 看到 B：

> 不知道这是合法例外。

> 还是系统错误。

因此：

例外也应该留下：

- 原因。
- 适用范围。
- 授权者。
- 有效期限。
- 后续处理。

# 一个可复用的决策流程

可以暂时使用下面的流程。

1. 明确当前需要做出的决定。
2. 判断影响范围。
3. 判断失败成本。
4. 判断是否可逆。
5. 判断当前角色是否具备足够验证能力。
6. 判断是否超出当前角色授权边界。
7. 如果属于低风险局部决定，直接执行。
8. 如果需要独立验证，进入验证层。
9. 如果影响跨边界契约，升级到更高层。
10. 如果属于高风险、不可逆或现实授权问题，进入 Human Gate。
11. Human Gate 前先压缩信息和证据。
12. 记录最终决定和适用范围。
13. 如果同类决定不断重复，评估是否可以压缩成规则。
14. 定期检查压缩规则是否仍然有效。

可以表示为：

```text
需要决策
↓
风险判断
↓
影响范围
↓
可逆性
↓
验证能力
↓
授权边界
↓
├── 局部低风险
│   ↓
│   Agent 决定
│
├── 需要独立验证
│   ↓
│   验证层
│
├── 跨边界
│   ↓
│   架构层
│
└── 高风险 / 不可逆 / 现实授权
    ↓
    Human Gate
        ↓
    决策记录
        ↓
    重复出现？
        ↓
    决策压缩
```

# 一个工作假设

Agent 系统的治理能力，可以暂时理解成在三个变量之间寻找平衡：

```text
决策风险

Human 注意力

自动化能力
```

如果所有风险都交给 Agent：

> 系统速度很快。治理不足。

如果所有决定都交给 Human：

> 治理看起来很强。吞吐量迅速下降。

更合理的方向是：

```text
自动化处理低风险和高确定性问题。
Human 处理高风险、高不确定性和高责任问题。
```

因此：

> **Human 注意力应该集中在系统无法可靠自动判断的区域。**

# 仍在研究的问题

当前还有几个问题值得继续研究。

第一，怎样更客观地衡量一个决定应该拥有多高等级的决策权。

第二，怎样自动识别“当前 Agent 已经超出授权范围”。

第三，Human Gate 输入应该压缩到什么程度，才能同时避免信息过载和关键事实丢失。

第四，决策压缩规则应该怎样版本化和失效。

第五，怎样发现 Human 已经进入机械审批状态。

第六，怎样衡量治理成本。

第七，当多个 Human 拥有不同领域决策权时，怎样处理交叉领域冲突。

这些问题会继续进入后续的规模化治理研究，并会在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **能力不等于权限。**

---

> **决策权不能超过验证能力。**

---

> **权限应该和职责边界匹配。**

---

> **未解决的不确定性不应该静默传播。**

---

> **Human Gate 的价值来自真实判断能力。**

---

> **Human 注意力应该随着风险和决策权扩展，而不应该随着 Agent 吞吐量线性扩展。**

---

> **重复出现的稳定判断可以被压缩成工程规则。**

---

> **决策压缩需要保留原因、范围和重新打开条件。**

---

> **高价值 Human Gate 应该接收经过整理的决策问题，而不是整个原始工程世界。**

---

# 结语

随着 Agent 越来越强，工程系统最终会遇到一个新的瓶颈：

```text
执行已经很快。
验证也可以自动化。
但重要决定仍然需要判断。
```

如果这些判断全部依赖少数 Human：

```text
Agent 越多。
Human 越忙。
最终系统仍然无法扩展。
```

因此，成熟的 Agent 软件工程需要设计一套清晰的决策结构：

```text
哪些决定可以自动完成？

哪些需要独立验证？

哪些必须升级？

哪些问题必须由具备相应能力的人负责？

哪些重复决策可以固化成规则？

什么情况下需要重新挑战过去的规则？
```

最终目标，是让：

- Agent 在明确授权范围内高速执行。
- 验证系统过滤大部分确定性问题。
- Human 把有限注意力集中在真正需要承担责任的高价值判断上。

当决策权、验证能力和责任范围能够彼此匹配时，Human 才不会成为 Agent 系统唯一的控制节点。

他会成为：

> **真正重要决策的治理者。**
