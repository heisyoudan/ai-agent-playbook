# 17 — 能力边界

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续研究（Research）** · **成熟度：工作假设（Working Hypothesis）**

---

# 为什么需要能力边界

Agent 的能力正在快速提高。

它可以：

- 阅读代码。
- 修改代码。
- 运行命令。
- 分析日志。
- 生成测试。
- 调用工具。
- 处理数据库。
- 阅读文档。
- 规划任务。
- 协调其他 Agent。
- 完成越来越长的工程流程。

这很容易让我们产生一个问题：

> 到底还有哪些工作不能交给 Agent？

但这个问题本身还不够准确。

工程真正需要回答的是：

> **在什么条件下，我们可以可靠地依赖 Agent 完成某一类工作？**

---

# 能够实现，不代表能够可靠交付

这是本章最重要的起点。

一个 Agent 也许能够：

- 写出某段代码。
- 生成某个页面。
- 实现某个算法。
- 修改某个接口。
- 完成某个视觉效果。

但工程交付还包括：

- 需求是否理解正确。
- 边界是否明确。
- 结果是否能够验证。
- 失败是否容易发现。
- 风险是否可控。
- 异常情况是否覆盖。
- 结果是否可以重复得到。
- 出现问题以后是否能够恢复。

因此：

```text
能够实现
```

只说明：

> Agent 有可能产生一个看起来正确的结果。

```text
能够可靠交付
```

要求更高。

---

# 可靠交付

可以暂时把可靠交付理解成：

> 在明确条件下，一个任务能够被重复委托，并且最终结果可以被验证、接受和追责。

这通常需要：

- 问题可以被理解。
- 任务可以被定义。
- 相关现实可以被获取。
- 边界可以被建立。
- 结果可以被验证。
- 失败可以被观察。
- 风险可以被控制。
- 必要时存在可靠判断者。

其中任意一个关键条件缺失：

> Agent 即使偶尔成功，也很难形成可靠交付能力。

---

# 能力不能只根据一次成功判断

一个非常常见的错误是：

Agent 成功完成了一次任务。

于是我们得出：

> Agent 会做这类事情。

例如：

- 一次成功修复认证问题，不代表 Agent 已经可靠掌握所有认证系统。
- 一次成功修改数据库，不代表 Agent 可以安全处理所有数据迁移。
- 一次成功完成视觉效果，不代表 Agent 可以稳定交付所有主观视觉任务。

因此：

> **单次成功首先是一条能力证据。还不能自动升级成稳定能力结论。**

---

# 宣称能力与已证明能力

可以区分两个概念：

```text
宣称能力
和
已证明能力。
```

## 宣称能力

来自：

- 模型说明。
- Benchmark。
- 工具文档。
- Agent 自己的解释。
- 通用能力描述。

例如：

- “这个模型擅长代码。”
- “这个 Agent 可以完成复杂重构。”

这些信息有参考价值。

但它们很难直接回答：

> 在当前项目、当前仓库、当前工具、当前风险条件下，它是否可靠。

## 已证明能力

来自真实任务结果。

例如：

- 在当前仓库中。
- 使用当前工具。
- 按照当前任务契约。
- 在明确边界内。
- 连续完成多个同类任务。
- 通过独立验证。
- 没有出现不可接受的逃逸缺陷。

这种证据对真实工程判断更有价值。

---

# 能力需要绑定条件

Agent 能力不能脱离环境讨论。

同一个模型：

- 在不同工具条件下。
- 不同上下文质量下。
- 不同仓库下。
- 不同任务类型下。

能力可能完全不同。

因此：

> 能力最好理解成一个条件化结论。

例如：

在：

```text
当前代码仓库
+
可使用代码搜索、构建和测试工具
+
任务边界清晰
+
存在可靠自动化测试
```

的条件下，

Agent 可以可靠完成：

```text
普通业务逻辑修改。
```

这比一句：

> “Agent 可以写后端。”

更有工程意义。

---

# 能力是任务相关的

Agent 很难拥有一个简单的：

```text
能力强 / 能力弱
```

标签。

更合理的方式是按任务类型判断。

例如：

- 代码生成
- 代码理解
- 缺陷修复
- 架构设计
- 性能调查
- 数据库迁移
- 安全审查
- 视觉设计
- 需求分析
- 客户沟通

这些任务需要的能力完全不同。

因此：

> **能力边界应该以任务类型为单位建立。**

---

# 任务类型

一个简单任务类型可以包含：

- 问题类型。
- 输入形式。
- 需要使用的工具。
- 风险等级。
- 验收方式。
- 依赖领域。

例如：

```text
普通后端 Bug 修复
```

和

```text
支付账本一致性修复
```

即使都属于：

```text
Java Backend
```

能力边界也可能完全不同。

---

# 能力来自哪些维度

Agent 是否能够可靠交付一个任务，通常受到多个因素共同影响。

## 模型能力

包括：

- 推理。
- 代码理解。
- 语言。
- 规划。
- 错误识别。
- 长上下文能力。

## 工具能力

例如：

- 代码搜索。
- 终端。
- 测试。
- 数据库。
- 浏览器。
- 日志。
- 调试器。
- 静态分析。

## 上下文质量

Agent 是否得到：

- 正确需求。
- 相关代码。
- 当前真相。
- 必要契约。
- 重要边界。
- 完整依赖。

## 任务结构

任务是否：

- 目标明确。
- 范围有限。
- 可以独立验证。
- 拥有清晰完成条件。

## 领域知识

例如：

- 支付。
- 安全。
- 金融。
- 医疗。
- 税务。
- 底层系统。

某些领域拥有大量隐藏规则。

模型通用能力很强，也可能缺少关键领域现实。

## 验证能力

系统是否能够判断结果正确。

这个因素尤其重要。

如果我们无法验证：

> 能力就很难被可靠建立。

## 恢复能力

如果 Agent 失败：

- 是否容易重新执行。
- 是否可以回滚。
- 是否可以安全停止。

## 风险

错误发生以后：

- 影响有多大。

这些因素共同决定：

> 一个任务能不能被可靠委托。

---

# 验证能力决定可委托边界

一个非常重要的规律是：

> **能否验证，往往决定能否可靠委托。**

假设 Agent 可以生成一个非常复杂的结果。

但系统没有任何方法判断：

> 它到底好不好。

那么 Human 最终只能依赖：

- 直觉。
- 外观。
- Agent 自己的解释。

这会显著降低可靠交付能力。

因此：

> 如果一个结果缺少可靠判断标准，Agent 的能力边界会明显收缩。

## 可验证任务

例如：

- 编译是否成功。
- 测试是否通过。
- API 返回是否正确。
- 数据库结果是否符合约束。
- 性能是否达到指标。

这些任务拥有相对明确的验证方式。

因此 Agent 更容易形成可靠能力。

## 弱可验证任务

例如：

- “让这个 UI 更高级。”
- “做一个很震撼的粒子效果。”
- “写得更有感染力。”

这里没有天然唯一答案。

结果高度依赖：

- 审美。
- 个人偏好。
- 客户感觉。
- 隐性期待。

Agent 也许可以产生优秀结果。

但可靠交付难度更高。

---

# 没有 Oracle 的问题

这里可以引入一个概念：

> **Oracle。**

它代表：

> 判断结果是否正确的可靠机制。

例如：

- 单元测试可以成为部分 Oracle。
- 业务规则可以成为 Oracle。
- 数据库约束可以成为 Oracle。
- 具备领域能力的 Human 也可以成为 Oracle。

如果一个任务缺少任何可靠 Oracle：

> 我们就很难建立稳定能力结论。

---

# 主观任务

主观任务并不等于：

> Agent 做不了。

更准确的说法是：

> 它们的可靠交付边界更依赖最终判断者。

例如视觉设计任务：

Agent 可能产生 10 个版本。

其中某一个非常好。

但如果系统无法明确判断：

> 什么叫“符合客户预期”

交付风险仍然很高。

因此：

```text
实现能力可以很强。
可靠交付能力仍然有限。
```

---

# Human 作为 Oracle

有些领域最终仍然需要 Human 判断。

例如：

- 审美。
- 品牌语气。
- 战略选择。
- 高层产品判断。
- 复杂业务权衡。

此时能力边界会受到：

```text
Human 判断能力
和
Human 可用性
```

影响。

如果最终判断者：

- 有能力。
- 有时间。
- 能够明确反馈。

Agent 可以处理更大范围。

如果没有可靠判断者：

> 任务风险会明显上升。

---

# 问题闭合

一个任务能否可靠委托，还取决于：

> 问题是否可以闭合。

问题闭合意味着：

- 任务拥有明确起点。
- 有限范围。
- 可以观察的结果。
- 可以判断的完成状态。

例如：

> “修复 refresh token 失败”

通常容易闭合。

而：

> “把整个产品体验做好”

问题范围可能长期开放。

---

# 验证能力与问题闭合

因此可以暂时形成一个工作模型：

```text
可靠交付能力
依赖：

问题闭合程度
+
验证能力
```

一个任务：

```text
范围明确。
结果可验证。
```

通常更容易进入 Agent 的可靠能力范围。

---

# 能力边界和任务边界

第 10 和第 15 章已经讨论：

> 任务需要落在合适的推理边界内。

这也意味着：

> 能力边界并不是固定的。

一个 Agent 可能无法可靠完成：

> “重构整个认证系统”。

但可以可靠完成：

> “修复 Token 刷新失败路径”。

因此：

> 改变任务边界，本身就可以改变 Agent 的可靠能力范围。

---

# 能力可以被工程系统放大

Agent 原始能力不是最终能力。

工程系统可以放大它。

例如：

原始 Agent

可能只能可靠处理较小任务。

加入：

- 任务切分。
- 上下文隔离。
- 真相投影。
- 独立验证。
- 自动测试。
- 运行时状态。
- 失败恢复。
- Human Gate。

以后：

整个 Human + Agent 系统可以可靠完成更复杂工作。

因此：

> 真正需要评估的不只是模型能力。

还需要评估：

```text
模型 + 工具 + 工作流 + 验证
```

组成的系统能力。

---

# 单个 Agent 能力与系统能力

可以区分：

```text
单 Agent 能力
和
Agent 系统能力。
```

例如：

一个 Agent 无法同时可靠完成：

- 需求分析。
- 架构。
- 开发。
- 测试。
- 风险判断。

但系统可以使用：

- 分析 Agent。
- 开发 Agent。
- QA Agent。
- 架构角色。
- Human Gate。

共同完成。

因此：

> 复杂工程能力可以通过组织结构获得。

---

# 能力边界和权限边界

第 12 章已经讨论过一个重要区分：

> 能力不等于权限。

例如：

Agent 有能力修改数据库。

不代表它拥有生产数据库修改权限。

Agent 有能力提出架构方案。

不代表它可以自行批准全局架构变化。

因此：

```text
能力边界回答：
它可以被依赖做到什么？

权限边界回答：
它被允许决定或执行什么？
```

---

# 能力高于权限

这是完全正常的。

例如：

Agent 可以写生产迁移脚本。

但：

只能生成脚本。

不能执行。

这种结构可以显著降低风险。

---

# 权限高于能力

这种情况更加危险。

例如：

Agent 可以直接部署生产环境。

但系统没有证据证明：

> 它可以可靠判断生产风险。

这意味着：

> **权限已经超过验证后的能力。**

---

# 能力需要证据

如果我们说：

> “Agent 可以可靠完成这类任务。”

应该能够回答：

> 依据是什么？

能力证据可能包括：

- 历史任务成功率。
- QA 通过率。
- 返工次数。
- 逃逸缺陷。
- 独立验证结果。
- Human 纠正次数。
- 失败类型。
- 恢复成功率。
- 证据覆盖。

---

# 能力证据应该来自相似任务

如果评估的是：

```text
数据库迁移能力。
```

最有价值的证据应该来自：

```text
数据库迁移任务。
```

而不是：

```text
前端页面生成能力。
```

因此：

> 能力证据需要和任务类型匹配。

---

# 能力证据需要足够近

模型能力会快速变化。

工具也会变化。

项目也会变化。

因此：

```text
一年前的能力证据
```

未必仍然适用于：

- 当前模型。
- 当前工具。
- 当前代码仓库。
- 当前工作流。

> 能力证据同样存在时效性。

---

# 能力漂移

Agent 能力会发生变化。

可以称为：

> **能力漂移。**

变化可能来自：

- 模型升级。
- 模型降级。
- 工具变化。
- Prompt 变化。
- 上下文系统变化。
- 仓库复杂度变化。
- 依赖变化。
- 任务类型变化。

## 正向能力漂移

例如：

- 新的模型版本。
- 更好的代码搜索工具。
- 更完整自动测试。

可能让 Agent 可以可靠处理更大任务。

## 负向能力漂移

例如：

- 模型切换。
- 工具不可用。
- 上下文质量下降。
- 仓库复杂度快速增加。

都可能让过去安全的任务：

```text
现在变得不可靠。
```

---

# 能力需要重新校准

因此：

> 能力边界不能建立一次以后永久使用。

当关键条件发生变化时，需要重新校准。

---

# 校准

能力校准指：

> Agent 对自己能够完成任务的判断，和真实结果之间是否一致。

例如：

Agent 对十个任务都表示：

```text
高信心。
```

但其中五个最终被 QA 拒绝。

那么它的：

```text
自我信心
和
实际能力
```

明显不匹配。

---

# Agent 的自信不能作为能力证明

模型可能非常流畅地说：

> “这个修改已经完全正确。”

语言上的确定性：

> 不能证明工程能力。

因此：

> Agent 自信可以作为辅助信号。不能成为权限升级的主要依据。

---

# 能力校准可以看什么

可以观察：

- 高信心任务最终通过率。
- 低信心任务最终失败率。
- Agent 主动升级问题的准确性。
- Agent 是否能够识别：自己不知道。

---

# 知道什么时候停止

一个成熟 Agent 的能力还包括：

> 知道什么时候不能继续。

例如：

- 上下文不足。
- 领域规则不清。
- 需求冲突。
- 缺少验证 Oracle。
- 权限不足。
- 风险过高。

Agent 能够：

- 主动停止。
- 说明原因。
- 请求补充信息。

这本身就是可靠能力的一部分。

---

# “我不知道”也是能力

如果一个 Agent 在证据不足时：

选择继续猜测。

它可能显得非常能干。

工程可靠性却很差。

如果另一个 Agent 能够明确识别：

> 当前无法可靠判断。

它可能执行得更慢。

整体交付反而更可靠。

因此：

> **识别能力边界本身就是能力。**

---

# 能力边界应该允许 Unknown

能力模型不要只有：

```text
Can

Cannot。
```

还需要：

```text
Unknown。
```

例如：

- 已证明可靠。
- 已知不可靠。
- 当前证据不足。

这三个状态非常重要。

## 已证明可靠

存在足够相似任务证据。

验证结果稳定。

风险可控。

## 已知不可靠

历史上反复失败。

当前验证能力不足。

或任务明显超出有效推理范围。

## 未知

缺少足够真实数据。

这时最合理的策略可能是：

```text
小范围试验。
```

---

# 能力探索

对于 Unknown 区域：

可以进行受控探索。

例如：

- 选择低风险任务。
- 限制边界。
- 增加独立验证。
- 禁止不可逆操作。
- 观察真实结果。

然后逐步扩大范围。

---

# 能力扩张

一个安全的能力扩张过程可以是：

```text
未知任务
↓
低风险试验
↓
严格验证
↓
重复成功
↓
形成初步能力证据
↓
增加任务范围
↓
继续验证
↓
逐渐扩大可靠边界
```

这样 Agent 的权限和任务范围可以根据真实证据逐渐增加。

---

# 能力收缩

如果：

- 逃逸缺陷增加。
- 返工增加。
- 模型变化。
- 工具失效。
- 任务复杂度上升。

系统也应该允许：

> 缩小能力边界。

例如：

过去 Agent 可以自主完成某类任务。

现在恢复为：

```text
Agent 执行
+
独立 QA。
```

> 能力模型需要允许回退。

---

# 风险影响能力边界

同样能力水平：

在不同风险环境中。

可委托范围可以不同。

例如：

Agent 在本地开发环境中可以自由尝试大量操作。

在生产环境中：

```text
同样能力
```

只能获得更小权限。

因此：

> 风险越高，可靠能力证据要求通常越高。

---

# 可逆性影响能力边界

如果任务失败很容易恢复：

可以允许更多探索。

如果失败不可逆：

能力边界需要更加保守。

---

# 成本也影响能力边界

有些任务技术上可以由 Agent 完成。

但验证成本极高。

例如：

```text
Agent 10 分钟生成。

Human 需要两天审核。
```

从系统角度看：

> 这可能并不是有效的 Agent 化。

因此：

> 能力边界还应该考虑验证和治理成本。

---

# 可交付性

可以引入一个更工程化的概念：

> **可交付性。**

它关注：

任务不仅能做。

还可以：

- 稳定验收。
- 可靠证明。
- 安全失败。
- 合理恢复。
- 控制成本。

因此：

> 一个任务适合 Agent，往往意味着它拥有足够高的可交付性。

---

# 能力评估不能只看成功率

例如：

Agent 完成 100 个任务。

成功 95 个。

看起来非常优秀。

但如果失败的 5 个全部是：

- 支付错误。
- 安全漏洞。
- 数据损坏。

这个能力结论就完全不同。

因此能力评估需要考虑：

```text
失败类型。
失败严重程度。
```

而不只是平均成功率。

---

# 逃逸缺陷

一个很重要的能力指标是：

> **逃逸缺陷。**

也就是：

Agent 和验证流程都认为任务完成。

问题却在后续阶段才被发现。

逃逸缺陷比：

```text
开发阶段主动发现失败
```

更能说明能力边界问题。

---

# 返工率

如果一类任务经常：

```text
Dev
→
QA
→
Dev
→
QA
```

大量回退。

说明：

> 当前能力或者任务边界可能不合适。

---

# Human 修正率

如果 Agent 每次都需要 Human：

- 重写方案。
- 修正关键假设。
- 重新定义任务。

说明当前自主能力仍然有限。

---

# 能力地图

长期可以建立：

> **能力地图。**

| 任务类型 | 当前能力状态 | 证据 | 默认权限 | 验证要求 |
|---|---|---|---|---|
| 普通 CRUD | 已证明可靠 | 大量历史任务 | Agent 自主 | 自动测试 |
| 公共 API 修改 | 条件可靠 | 需要强契约 | 独立验证 | 契约 + 测试 |
| 数据库迁移 | 受限 | 历史样本少 | Agent 生成 | Human Gate |
| 生产删除 | 不自动委托 | 高风险 | 只允许建议 | Human 执行 |

能力地图的价值在于：

> 让系统不再凭印象决定：“这个能不能交给 AI？”

---

# 能力地图需要局部化

大型项目中：

- 不同仓库。
- 不同模块。
- 不同业务域。

Agent 的能力可能不同。

因此：

> 一个全局统一能力标签往往过于粗糙。

更合理的是：

> 按任务类型和环境记录。

---

# 系统能力也需要地图

还可以记录：

整个工作流的能力。

例如：

| 工作 | 系统能力 |
|---|---|
| 代码修复 | 可靠 |
| 数据库调查 | 可靠 |
| 支付架构决策 | 需要 Human |
| 视觉审美验收 | 强依赖客户 |

这样 Human 可以更快判断：

> 什么工作适合进入 Agent 工作流。

---

# 能力边界与人类能力

能力边界并不只适用于 Agent。

Human 同样存在能力边界。

例如：

某个 Human 可能：

有权批准安全设计。

但并不具备安全知识。

这在第 12 章已经讨论。

因此，更完整的工程系统应该关注：

- Agent 能力。
- Human 能力。
- 工具能力。
- 验证能力。

共同组成：

```text
系统能力。
```

---

# 专家 Human 也是稀缺资源

如果一类任务最终永远需要：

> 同一个领域专家完整审核。

那么该专家就可能成为能力瓶颈。

这会进一步连接到第 16 章：

> 规模化治理。

因此：

能力边界最终影响：

- 授权结构。
- Human Gate。
- 治理成本。

---

# 主观性边界

有些任务长期很难完全工程化。

例如：

- 审美。
- 品牌风格。
- 战略创意。
- 复杂人际沟通。

这些任务可能仍然大量使用 AI。

但最终可靠性更依赖：

> Human 判断。

这并不意味着这些任务价值低。

只是它们的能力边界结构不同。

---

# 领域知识边界

一些任务拥有非常深的领域现实。

例如：

- 金融清结算。
- 医疗。
- 法律合规。
- 安全。

即使 Agent 通用推理很强：

缺少真实领域背景时，仍然可能产生合理但错误的结论。

因此：

> 领域知识是否可外部化，会直接影响 Agent 能力边界。

---

# 隐性知识

如果关键规则长期只存在于：

> 某个专家脑中。

Agent 很难形成稳定能力。

当隐性知识逐渐变成：

- 文档。
- 规则。
- 契约。
- 测试。
- 验证标准。

Agent 能力边界就可能扩大。

因此：

> **知识外部化也是扩大 Agent 能力的一种方式。**

---

# 能力与真相治理

第 08 章研究：

> Agent 应该相信什么。

如果项目真相质量很差：

Agent 能力会被严重限制。

因为：

```text
再强的 Agent
基于错误现实工作
仍然会产生错误结果。
```

因此：

> 能力边界受真相质量影响。

---

# 能力与有效推理范围

第 09 章研究：

> Agent 一次能可靠理解多少。

当任务超出有效推理范围：

能力会明显下降。

因此：

> 任务边界会改变能力表现。

---

# 能力与任务切分

第 10 和第 15 章说明：

合理切分可以扩大系统可交付能力。

一个大任务：

可能超出能力边界。

拆成几个自然闭合任务以后：

每个都可以进入可靠区域。

---

# 能力与验证

第 11 章说明：

如果无法验证：

可靠能力很难成立。

因此：

> 验证能力实际上是 Agent 能力体系的一部分。

---

# 能力与决策权

第 12 章说明：

能力不自动产生权限。

权限需要根据：

- 能力证据。
- 风险。
- 影响范围。
- 验证能力。

共同决定。

---

# 能力与真相投影

第 13 章说明：

一个 Agent 得到什么世界

会直接影响它的能力表现。

因此：

> 上下文构建质量也是能力条件。

---

# 能力与运行时

第 14 章说明：

可靠工程还需要处理：

- 失败。
- 恢复。
- 重新执行。
- 状态连续性。

一个 Agent 即使第一次执行成功率很高：

如果失败以后无法恢复。

系统能力仍然有限。

---

# 能力与边界税

第 15 章说明：

任务可以不断切小来提高局部可靠性。

但协调成本会增加。

因此：

```text
理论上能交给 Agent
和
工程上值得交给 Agent
```

也属于两个不同问题。

---

# 能力与规模化治理

第 16 章说明：

能力提高以后：

可以降低某些区域的治理强度。

能力不足或者证据不足的区域：

需要更强验证和 Human Gate。

因此：

> 能力模型可以成为治理强度的重要输入。

---

# 失败模式一：一次成功等于能力证明

Agent 成功完成一次复杂任务。

系统立即认为：

> 以后同类任务全部可以自主执行。

这会过度扩大能力边界。

---

# 失败模式二：Benchmark 等于真实项目能力

模型在公开 Benchmark 表现优秀。

于是默认：

> 当前仓库里的复杂领域任务同样可靠。

公开测试和真实环境之间可能存在巨大差异。

---

# 失败模式三：Agent 自信等于能力

Agent 表达非常确定。

系统因此降低验证。

语言自信无法替代工程证据。

---

# 失败模式四：只看输出质量，不看验证成本

Agent 可以生成漂亮结果。

但 Human 每次需要大量时间确认。

整体交付成本并没有下降。

---

# 失败模式五：能力和权限混在一起

因为 Agent 做得到：

所以直接给权限。

最终能力尚未稳定，影响范围已经扩大。

---

# 失败模式六：能力结论永不过期

过去某个模型版本表现可靠。

模型已经变化。

工具已经变化。

系统仍然沿用旧能力判断。

---

# 失败模式七：只记录成功

所有失败和 QA 回退都没有进入能力评估。

最终能力地图严重乐观。

---

# 失败模式八：所有任务使用统一能力标签

系统说：

> “这个 Agent 很会 Java。”

于是：

- 普通 CRUD。
- 支付系统。
- 并发。
- 安全。
- 迁移。

全部被认为同样可靠。

能力判断过于粗糙。

---

# 失败模式九：主观任务被当成确定性任务

Agent 产生一个视觉方案。

没有可靠验收标准。

系统仍然认为：

> “已经完成。”

这会把：

```text
输出
```

误认为：

```text
可交付结果。
```

---

# 失败模式十：Agent 不知道自己什么时候应该停

上下文缺失。

需求冲突。

仍然继续推理和实现。

这种 Agent 执行能力可能很强。

可靠工程能力却很弱。

---

# 一个最小能力评估流程

可以暂时使用下面的流程。

1. 明确任务类型。
2. 明确当前环境。
3. 明确可用工具。
4. 明确任务边界。
5. 检查相关现实是否可获得。
6. 检查问题是否可以闭合。
7. 定义完成声明。
8. 判断是否存在可靠验证方式。
9. 判断失败是否可观察。
10. 判断失败是否可恢复。
11. 判断风险和不可逆性。
12. 查找相似历史任务证据。
13. 判断当前能力状态：
    - 已证明可靠。
    - 已知不可靠。
    - 未知。
14. 根据能力状态决定：
    - 任务范围。
    - 验证强度。
    - 权限等级。
    - Human Gate。
15. 执行任务。
16. 收集实际结果。
17. 更新能力证据。
18. 必要时扩大或收缩能力边界。

可以表示为：

```text
候选任务
↓
任务类型
↓
相关现实可获得？
↓
问题可闭合？
↓
结果可验证？
↓
风险可控制？
↓
相似能力证据？
↓
├── 证据充分
│   ↓
│   已证明能力范围
│
├── 历史反复失败
│   ↓
│   已知能力外
│
└── 证据不足
    ↓
    Unknown
        ↓
    受控试验

↓

执行
↓
验证
↓
现实结果
↓
更新能力边界
```

---

# 一个能力扩张流程

```text
Unknown
↓
选择低风险实例
↓
缩小边界
↓
提高验证强度
↓
执行
↓
结果通过
↓
重复验证
↓
形成能力证据
↓
逐步增加：

任务复杂度
自主权限
任务范围

↓

持续观察逃逸缺陷和返工
```

这样能力扩张来自现实证据。

# 一个能力收缩流程

```text
当前能力范围
↓
观察到：

QA 回退增加
领域变化
模型变化
工具失效
验证能力下降

↓
重新评估
↓
缩小：

任务范围
自主权限

↓
增加：

独立验证
Human Gate

↓
重新积累证据
```

# 一个工作模型

可以暂时把可靠委托能力理解成：

```text
Agent 原始能力
+
工具能力
+
上下文质量
+
任务结构
+
验证能力
+
恢复能力
```

受到：

```text
领域复杂度
风险
不可逆性
```

的约束。

这个模型不是数学公式。

它主要用于提醒：

> “模型有多强”只是能力问题的一部分。

---

# 另一个工作模型

一个任务能否可靠交给 Agent，可以优先检查三个问题：

```text
能不能看清？

能不能做完？

能不能证明？
```

其中：

```text
看清
```

对应：

> 真相、上下文、有效推理范围。

```text
做完
```

对应：

> 执行能力、工具、任务边界。

```text
证明
```

对应：

> 验证、证据和可靠 Oracle。

如果第三个问题无法回答：

> 可靠交付能力通常很难成立。

---

# 能力成熟度

未来可以把某类能力简单分为几个阶段。

```text
未知

缺少真实数据。
```

```text
试验中

已经开始受控执行。

验证强度较高。
```

```text
条件可靠

在明确条件和边界内表现稳定。
```

```text
稳定能力

大量相似任务持续通过验证。
```

```text
退化

过去可靠，但当前环境变化导致重新评估。
```

```text
暂停

发现高风险问题以后，暂时停止自动委托。
```

这些状态可以帮助工作流根据现实动态调整。

---

# 能力边界不是永久边界

这里需要特别强调：

> **能力边界不会永远固定。**

随着：

- 模型提高。
- 工具增强。
- 工作流改进。
- 知识外部化。
- 验证增强。

原来不能可靠交付的问题：

可能逐渐进入可靠区域。

同样：

- 项目复杂度提高。
- 环境变化。
- 领域要求提高。

也可能让过去安全的任务重新退出可靠区域。

因此：

> 能力边界需要持续校准。

---

# 能力边界的真正意义

研究能力边界的目标，并不在于证明：

> AI 可以做什么。

更重要的是建立一种工程能力：

知道：

- 什么可以放心交给 AI。
- 什么可以在严格验证下尝试。
- 什么仍然需要 Human。
- 什么当前根本无法可靠判断。

这比一个简单的：

```text
AI 能不能做？
```

更有实际意义。

# 仍在研究的问题

这一章目前仍然存在大量工作假设。

第一，应该怎样用真实工程数据建立能力边界。

第二，多少次成功才足以把 Unknown 提升为条件可靠。

第三，不同任务类型的能力证据能否互相迁移。

第四，模型版本变化以后，旧能力证据应该保留多少。

第五，怎样衡量 Agent 自信和真实结果之间的校准程度。

第六，怎样把逃逸缺陷、返工率、Human 修正率结合成更可靠的能力信号。

第七，怎样评估主观任务的可靠交付能力。

第八，Human 作为 Oracle 时，怎样衡量 Human 自身判断可靠性。

第九，怎样让 Agent 自动识别自己已经超出能力边界。

第十，如何让能力边界自动影响权限和治理强度。

第十一，能力地图应该以什么粒度维护，才能避免维护成本失控。

第十二，系统能力是否可以通过多 Agent 组合产生超过任何单 Agent 的稳定能力。

这些问题仍然需要持续实践，会继续在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **能够实现，不代表能够可靠交付。**

---

> **一次成功只能形成能力证据，不能自动证明稳定能力。**

---

> **能力需要绑定任务类型、环境、工具和上下文。**

---

> **能力是条件化的。**

---

> **能力不等于权限。**

---

> **权限不能领先于已经验证的能力。**

---

> **可靠能力必须能够被验证。**

---

> **缺少可靠 Oracle 的任务，需要更谨慎的能力判断。**

---

> **Agent 自信不能代替能力证据。**

---

> **能够识别“我现在无法可靠判断”，本身就是重要能力。**

---

> **能力边界应该包含：已证明可靠、已知不可靠、未知。**

---

> **Unknown 区域应该通过受控试验探索。**

---

> **能力可以扩大，也必须能够收缩。**

---

> **模型能力只是系统能力的一部分。**

---

> **工具、工作流、验证和 Human 共同决定最终可交付能力。**

---

> **能力边界需要随着现实持续校准。**

---

# 结语

当 AI 变得越来越强以后：

```text
“它能不能做？”
```

会逐渐成为一个越来越容易得到“可以”答案的问题。

真正困难的问题会变成：

```text
它能不能稳定做？

它失败以后我们能不能发现？

我们能不能证明结果正确？

失败会不会产生不可接受后果？

它什么时候应该停止？

我们有什么现实证据说明这类任务已经可以依赖它？
```

这些问题决定的：

> 才是真正的工程能力边界。

一个成熟的 Agent 系统不会因为某个模型看起来很强，就把所有工作直接交出去。

它会根据真实结果：

- 建立能力。
- 校准能力。
- 扩大能力。
- 收缩能力。

并让能力证据继续影响：

- 任务边界。
- 验证强度。
- 决策权。
- Human Gate。
- 治理成本。

最终，真正值得追求的并不是：

```text
让 AI 什么都做。
```

更有价值的是：

```text
清楚知道哪些工作已经可以可靠交给 AI。

哪些仍然需要严格验证。

哪些需要 Human 承担判断。

哪些暂时还没有足够证据做出结论。
```

当一个系统能够持续回答这些问题时：

Agent 才开始从一个拥有强大潜力的执行者，变成一个拥有明确工程能力边界的可靠 Worker。
