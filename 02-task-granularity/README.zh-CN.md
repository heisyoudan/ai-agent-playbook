# 02 — 任务粒度决定一切

[日本語](README.ja.md) · [English](README.md) · **简体中文**

## 任务设计比 Agent 性能更重要

围绕 AI 开发的讨论经常集中在“哪个 Agent 最强、应该使用哪个工具”。但在环境已经安装并连接之后，最常见的限制并不是模型能力不足。

**再优秀的 Agent，也无法从设计糟糕的任务中稳定地产出结果。**

真正缺少的通常是一种合适的任务形态，让 Agent 能理解、执行、验证并完成工作，而不会失去焦点。

## 任务过大时

“完成整个后台管理系统”听起来很高效，但它隐藏了需求、边界、接口、页面行为、约束和验收决策。

为了安全执行这类任务而准备上下文，其成本甚至可能超过实现本身。上下文不断膨胀后，Agent 会失去焦点，输出开始波动，返工增加，最后仍需要人重新整理整个工作。

## 任务过小时

过度拆分会产生另一类问题。本来一次交互可以闭环的工作，需要三四次交接。沟通和判断成本开始超过执行成本。

拆分任务本身也是设计工作。如果每个极小修改都成为独立任务，人就会开始服务于工作流，而不是从工作流中获益。

## 找到合适的粒度

合适的任务同时满足两个条件：

- **足够小**：Agent 可以独立完成并自我验证。
- **足够大**：一次会话能够闭合一个有价值的循环。

| 粒度 | 示例 | 结果 |
|---|---|---|
| **过大** | “完成整个管理页面。” | 上下文膨胀，容易越界和返工。 |
| **合适** | “按照以下 API 契约实现带排序和分页的用户表格组件。” | 可以在一个循环中完成并验证。 |
| **过小** | “先做表头”，再“做表体”，再“加分页”。 | 交接成本超过执行。 |

## 问题发生了变化

过去我反复问：“AI 能不能完成这个任务？”

现在我会问：**“应该怎样设计这个任务，才能让 AI 稳定完成？”**

关注点从评价模型转向设计工作。Agent 的能力固然重要，但目标、边界、上下文和完成证据仍由人来设计。

## 五条实践规则

1. **一个任务，一个目标**——不要混合无关结果。
2. **定义完成**——写清哪些可观察证据代表完成。
3. **定义边界**——写清哪些内容不在范围内、不得修改。
4. **保证可验证**——选择 Agent 能测试或检查的工作单元。
5. **闭合上下文**——把所需信息集中在一起。

---

> **实践笔记**
> Maestro 要求任务执行前具备四个字段：`summary`、`currentAction`、`acceptanceCriteria` 和 `boundaries`。它们分别代表结果、本次执行、完成证据和非目标。任务契约不完整时，工作不会开始。
