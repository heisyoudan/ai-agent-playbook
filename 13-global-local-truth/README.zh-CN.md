# 13 — 全局真相、局部真相与真相投影

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续研究（Research）** · **成熟度：工作假设（Working Hypothesis）**

---

# 为什么需要全局真相与局部真相

第 09 章已经讨论过一个事实：

大型软件系统通常远远超过单个 Agent 的有效推理范围。

因此，我们需要把大型系统转换成多个可以被局部理解和执行的问题世界。

例如：

```text
整个支付平台
↓
支付业务域
↓
退款模块
↓
退款 API
↓
当前任务
```

这种切分可以降低局部推理复杂度。

但它同时产生了一个新的问题：

> **如果每个 Agent 都只理解自己的局部世界，它们怎样继续属于同一个系统？**

例如：

- 退款 Agent 认为某个状态可以修改。
- 账本 Agent 认为这个状态只能由账本负责。
- API Agent 认为某个字段可以删除。
- 兼容性规则却要求这个字段长期保留。

局部来看，每个 Agent 都可能拥有合理解释。

放回整个系统以后，它们却可能互相冲突。

因此，大型 Agent 系统需要同时维护两个层级：

```text
全局真相
和
局部真相。
```

---

# 全局真相

全局真相描述的是：

> 整个系统必须共同遵守的高影响事实、约束和关系。

它不需要包含整个项目中的所有信息。

真正值得成为全局真相的内容，通常包括：

- 系统不变量。
- 核心业务规则。
- 架构边界。
- 模块所有权。
- 关键契约。
- 关键依赖关系。
- 安全与权限规则。
- 一致性要求。
- 不可逆操作规则。
- 关键失败处理原则。
- 跨模块生命周期。
- 高影响历史决策。

例如：

```text
退款金额不能超过实际支付金额。

账本状态只能由账本服务最终确认。

公共 API 必须保持向后兼容。

生产数据库删除需要额外授权。

支付操作必须满足幂等要求。
```

这些事实会同时影响多个局部世界。

因此，它们不能只存在于某一个任务的上下文中。

---

# 全局真相不是所有文档的总和

这里需要避免一个误区：

全局真相并不等于：

```text
所有文档
+
所有代码
+
所有需求
+
所有聊天记录
+
所有历史决策
```

如果把整个项目中的所有内容都称为全局真相，那么这个概念很快会失去实际意义。

全局真相应该保持相对有限。

它主要回答：

- 整个系统有哪些不能被局部任务随意改变的规则？
- 哪些边界必须被所有相关 Worker 尊重？
- 哪些关系一旦发生变化，会影响大量下游工作？

因此：

> 全局真相更接近系统的不变量、关键契约和高影响决策。

它应该尽量保持：

- 有限。
- 明确。
- 可追踪。
- 有负责人。
- 可以被挑战。
- 可以被版本化。

---

# 局部真相

局部真相描述的是：

> 在某个明确范围内，当前任务或模块被允许依赖的事实和决策。

例如退款模块可能拥有自己的局部真相：

- 退款状态机。
- 退款错误规则。
- 退款服务内部数据结构。
- 退款模块自己的实现决策。
- 当前任务已经确认的约束。

这些内容没有必要成为整个项目的全局规则。

它们只需要在自己的局部范围内保持一致。

---

# 局部真相需要有明确归属

局部真相不能变成：

> 每个 Agent 自己脑中的一套理解。

它仍然需要回答：

- 这个局部真相属于哪个范围？
- 谁负责维护？
- 它依赖哪些全局真相？
- 它有哪些外部契约？
- 它的变化会影响谁？

因此，一个局部真相至少应该绑定到某种稳定范围。

例如：

- 业务域。
- 模块。
- API。
- 工作流阶段。
- 数据所有权。
- 某个明确的工程责任。

这样才可以知道：

> 一条局部真相发生变化以后，应该通知谁。

---

# 全局真相与局部真相的关系

可以简单理解成：

```text
全局真相
↓
定义系统必须共同遵守的世界

局部真相
↓
定义某一个范围内部可以依赖的世界
```

例如：

全局真相：

> 退款金额不能超过已支付金额。

退款模块局部真相：

> 退款服务通过 PaymentSnapshot 查询当前已支付金额。

另一个退款实现可能使用不同内部方式。

只要最终仍然遵守全局规则，就可以拥有自己的局部设计。

因此：

```text
全局真相负责约束。
局部真相负责在约束内部形成可执行世界。
```

---

# 局部真相不能重定义全局规则

假设某个局部 Agent 发现：

> 如果允许退款超过已支付金额，实现会简单很多。

它不能因为局部实现方便，就修改：

> 退款金额不能超过实际支付金额

这条全局规则。

局部世界可以：

- 实现。
- 优化。
- 解释。
- 增加局部约束。

但它没有权限自行重定义高层系统不变量。

如果局部现实证明全局规则存在问题：

> 局部 Agent 可以提出挑战。

然后进入第 08 章定义的真相治理流程。

---

# 为什么需要真相投影

单个 Agent 无法可靠读取全部全局真相和全部局部真相。

因此工作流需要做一件事情：

> 根据当前任务，把相关高层真相投影到当前局部世界中。

这个过程可以称为：

> **真相投影。**

例如：

```text
全局真相
├── 系统不变量
├── 架构边界
├── 模块所有权
├── 关键契约
├── 安全规则
└── 依赖关系

退款模块局部真相
├── 状态机
├── 内部模型
└── 当前实现规则

当前任务
↓
识别相关范围
↓
生成真相投影
↓
当前 Agent 获得：

退款局部真相
+
相关支付规则
+
相关账本契约
+
相关 API 兼容规则
+
相关安全约束
+
相关依赖
```

---

# 真相投影是什么

真相投影可以理解为：

> 针对一个明确范围，从项目当前可信真相中构造出的受控局部视图。

这里有几个关键词：

- 明确范围。
- 当前可信。
- 受控。
- 局部视图。

真相投影并不只是把文档搜索结果复制给 Agent。

它需要知道：

- 为什么这条信息需要进入当前任务？
- 它来自哪里？
- 它属于全局还是局部？
- 它当前是否仍然有效？
- 谁有权改变它？
- 它和当前任务是什么关系？

---

# 真相投影和普通摘要的区别

普通摘要的目标通常是：

> 把长内容变短。

真相投影的目标是：

> **让当前局部世界在缩小以后，仍然保持工程意义上的正确约束。**

例如，摘要可能写：

> “退款服务负责退款。”

这句话很短。

但对工程执行而言可能缺少：

- 退款不能超过已支付金额。
- 账本拥有最终金额真相。
- 重复退款必须满足幂等。
- 外部支付系统存在异步回调。
- 退款状态不能由当前模块单方面最终确认。

如果这些内容被摘要过程删除：

```text
文本变短了。
工程世界也被破坏了。
```

因此：

> **真相投影的目标是缩小世界，同时保护相关约束。**

---

# 投影应该由谁负责

这是一个重要治理问题。

如果执行 Agent 可以自己决定：

- 我要看哪些真相。
- 我要忽略哪些真相。

那么它可能在开始执行之前，就已经删除了自己没有意识到的重要条件。

因此，高风险工作中：

> 真相投影最好不要完全由执行者自由决定。

一种可能的结构是：

```text
项目真相
↓
依赖关系
↓
任务范围
↓
上下文构建或协调层
↓
候选真相投影
↓
完整性检查
↓
执行 Agent
```

这里的投影机制可以由：

- 工作流规则。
- 领域配置。
- 依赖图。
- 任务模板。
- 架构元数据。
- 上层 Agent。
- Human 定义的关键约束。

共同完成。

具体实现可以变化。

核心原则是：

> **投影本身属于工程决策。**

---

# 投影也有所有权

一个真相投影应该能够回答：

- 谁生成了它？
- 它基于哪个真相版本？
- 它面向哪个任务？
- 它覆盖哪些范围？
- 它依赖哪些来源？
- 什么时候需要重新生成？

如果这些信息完全不存在：

Agent 只能看到一个局部上下文。

却无法知道这个上下文是否还值得相信。

因此，投影最好拥有自己的最小元数据。

---

# 投影契约

可以把一个真相投影理解成一种契约。

一个最小投影契约可以包含：

- 目标范围
- 当前任务
- 相关全局真相
- 相关局部真相
- 相关契约
- 相关依赖
- 来源
- 版本
- 失效条件
- 升级路径

例如：

```text
当前任务：
修改退款重试逻辑

投影范围：
Refund Service

相关全局真相：
退款不能超过已支付金额
支付操作必须保持幂等

相关依赖：
Ledger API
Payment Gateway

来源：
Project Truth v18
Refund Contract v7

失效条件：
退款契约变化
账本契约变化
支付幂等规则变化
```

这样 Agent 不只知道：

> 现在相信什么。

还知道：

> 这些事实在什么情况下可能失效。

---

# 投影的一致性保证

真相投影存在以后，一个新的问题出现：

> 局部视图能够和全局世界保持多强的一致性？

理想情况下：

```text
全局真相发生变化
↓
所有受影响投影立即更新
```

但真实工程系统很难永远做到零延迟传播。

因此需要诚实地区分不同一致性程度。

## 强一致投影

对于非常关键的真相：

> 任何变化发生以后，旧投影立即失效。

相关任务必须停止或者重新构建上下文。

例如：

- 资金上限规则。
- 认证策略。
- 关键安全规则。
- 生产数据库兼容契约。

这种情况下：

> 旧投影几乎不能继续使用。

## 延迟一致投影

一些低风险信息可以允许短时间不同步。

例如：

- 非关键内部实现建议。
- 低风险文档结构。
- 局部命名规则。

这时系统可以允许：

```text
全局变化发生
↓
局部投影稍后刷新
```

只要这个窗口不会产生不可接受风险。

## 陈旧窗口

这就产生一个概念：

> **陈旧窗口。**

它表示：

> 一个投影在全局真相变化以后，允许继续使用多长时间或多少执行步骤。

这个窗口不一定按时间计算。

也可以按：

- 提交次数。
- 任务次数。
- 版本变化。
- 依赖变化。
- 发布阶段。

来判断。

例如：

高风险支付规则：

```text
陈旧窗口 = 0
```

发生变化以后立即失效。

普通开发约定：

> 可以允许直到下一次上下文重建时再刷新。

因此：

> 投影时效应该和风险匹配。

---

# 投影失效

真相投影不能被创建以后无限使用。

一些事件应该明确触发失效。

例如：

- 相关全局真相变化。
- 相关局部真相变化。
- 依赖契约变化。
- 任务范围扩大。
- 模块所有权变化。
- 架构边界变化。
- 安全规则变化。
- 相关代码出现重大结构调整。
- 新的证据推翻投影中的某个事实。
- Agent 发现此前没有记录的跨边界依赖。

这些事件都可能意味着：

> 当前 Agent 所看到的世界已经不完整。

---

# 失效以后应该发生什么

一个投影失效以后，更安全的流程是：

```text
检测到失效条件
↓
暂停依赖旧投影的关键执行
↓
确认变化范围
↓
重新读取当前可信真相
↓
重新计算相关依赖
↓
生成新投影
↓
重新检查任务
↓
判断已有实现和证据是否仍然有效
↓
恢复执行
```

这里不能只做：

> 刷新 Prompt。

因为真相变化可能已经影响：

- 任务本身。
- 已经完成的实现。
- 测试。
- 证据。
- 下游任务。

---

# 真相变更传播

这就是大型 Agent 系统中的另一个重要问题：

> **一次真相变化，应该传播多远？**

例如：

```text
项目真相 v10：

退款可以在 Captured 状态执行。
```

后来新的业务确认产生：

```text
项目真相 v11：

只有 Settled 状态才允许执行某类退款。
```

这次变化可能影响：

- 退款服务。
- 退款状态机。
- 退款 API。
- 相关测试。
- 设计文档。
- 已经完成的任务。
- 相关验证证据。
- 后续依赖退款行为的模块。

如果系统只更新：

> 一份 Project Truth 文档

而不重新评估下游产物：

项目就会进入一种危险状态：

```text
高层真相已经更新。
局部世界仍然生活在旧版本里。
```

---

# 变更传播需要依赖关系

要判断真相变化影响什么，需要知道：

> 谁依赖这个真相？

因此，真相治理最终会自然需要某种依赖追踪。

例如：

```text
Truth T17
├── Architecture A3
├── Contract C8
├── Task K21
├── Test V14
└── Evidence E9
```

如果 T17 发生变化：

系统就可以进一步判断这些对象是否受到影响。

---

# 影响分类

一次真相变化以后，下游结果不一定全部失效。

可以大致分类成：

```text
未受影响

变化与当前产物没有实际关系。

无需重新验证。
```

```text
可能受影响

存在依赖关系，但无法仅靠静态信息判断影响。

需要重新评估。
```

```text
直接失效

产物明确建立在已经改变的真相上。

需要重新生成或重新验证。
```

例如：

```text
全局真相变化
↓
依赖追踪
↓
├── 未受影响
│   ↓
│   保留
│
├── 可能受影响
│   ↓
│   重新评估
│
└── 直接失效
    ↓
    重新打开任务或证据
```

---

# 真相变更不等于所有工作重新开始

传播机制的目标不能是：

> 只要全局真相变化，所有任务全部重做。

这种方式虽然简单，但成本无法扩展。

真正需要的是：

> 只重新打开受到影响的部分。

这也是为什么：

- 真相粒度。
- 依赖粒度。
- 证据粒度。
- 任务粒度。

会互相影响。

如果所有东西都绑定在一个巨大整体上：

> 任何局部变化都会导致大范围重新验证。

如果绑定粒度合理：

> 系统可以进行更精确的失效和恢复。

---

# 真相版本与证据版本

第 11 章已经讨论：

证据也有时效。

现在可以进一步看到：

> 证据最好知道自己依赖哪个真相版本。

例如：

```text
Evidence E102

证明：
Refund Rule Test PASS

基于：
Project Truth v18
Contract v7
Code Commit abc123
Environment test-2026-09
```

当 Project Truth 更新到 v19：

系统就可以判断：

> E102 是否依赖发生变化的部分？

如果依赖：

> 重新验证。

如果不依赖：

> 证据可以继续有效。

---

# 任务也应该知道自己依赖什么

同样，一个任务最好知道：

> 它是基于哪些高层事实生成的。

例如：

```text
Task K32

依赖：
Truth T4
Truth T9
Contract C2
Architecture Boundary A3
```

这样当 T9 发生变化时：

系统可以知道：

> K32 需要重新评估。

否则 Truth 更新以后，旧任务仍然会继续执行。

---

# 局部真相与全局真相冲突

Agent 在局部执行中可能发现：

```text
当前局部真相
与
当前全局真相
```

存在冲突。

例如：

全局真相：

> 订单状态只能由 Order Domain 修改。

局部实现：

> Payment Service 长期直接更新订单状态。

此时可能存在几种情况：

- 全局真相已经过期。
- 局部实现错误。
- 历史兼容例外没有记录。
- 架构迁移尚未完成。
- 局部 Agent 缺少重要背景。

---

# 冲突不能由局部 Agent 自行裁决

一个危险处理方式是：

Agent 根据代码实际行为判断：

> 既然现在代码就是这样，那全局真相应该错了。

然后继续工作。

代码是重要证据。

但遗留实现也可能本身就是错误。

因此：

> **现实冲突应该产生真相挑战。**

而不能自动让任意一侧获胜。

---

# 冲突裁决流程

可以使用类似流程：

```text
发现冲突
↓
停止依赖该冲突的高风险执行
↓
记录：

全局真相是什么

局部真相是什么

代码实际行为是什么

有哪些证据

冲突影响什么

↓
提交真相挑战
↓
具备相应权限的角色分析
↓
产生新的授权结论
↓
更新全局或局部真相
↓
传播变化
↓
重新评估相关任务与证据
```

---

# 局部现实也可以推翻全局真相

全局真相拥有更高影响范围。

这不代表它永远正确。

局部执行往往是发现全局错误的重要来源。

例如：

架构文档认为：

> 服务 A 拥有某个数据。

开发 Agent 实际调查发现：

> 数据库和运行流量都证明服务 B 才是真正写入者。

这时候局部调查提供了重要证据。

它应该挑战全局真相。

因此：

```text
全局真相拥有更高决策权。
现实仍然拥有最终否决权。
```

---

# 局部真相不能自动合成为全局真相

还有一个非常重要的问题：

> 如果所有局部模块都正确，整个系统是不是就正确？

第 10 章已经说明：

> 不能。

同样：

```text
所有局部真相的集合
```

也不能自动等于：

```text
全局真相
```

因为全局系统还存在很多只在边界之间出现的问题。

例如：

- 两个模块都认为自己不拥有某个状态。
- 两个模块都认为另一个模块负责重试。

每个模块内部逻辑都正确。

系统整体却没有任何人负责恢复。

因此：

> **全局真相需要显式描述那些无法仅靠局部事实自动推导出来的跨边界关系。**

---

# 全局真相应该特别关注什么

大型系统中的全局真相应该优先记录：

- 系统不变量。
- 跨域业务规则。
- 状态所有权。
- 关键数据所有权。
- 公共契约。
- 依赖方向。
- 事务边界。
- 一致性模型。
- 失败恢复责任。
- 安全边界。
- 权限边界。
- 不可逆操作。
- 跨模块生命周期。

这些内容最容易在局部优化中被破坏。

---

# 真相投影与最小权限

真相投影还可以和权限设计结合。

一个 Agent 看到的真相范围，通常应该和它的执行权限匹配。

例如：

一个局部测试 Agent 可能只需要：

- 任务契约。
- 相关代码。
- 相关测试规则。
- 局部真相。
- 少量全局约束。

它不一定需要：

- 整个生产架构。
- 所有客户信息。
- 所有安全配置。

因此：

局部世界可以同时限制：

- 认知范围。
- 执行范围。
- 数据范围。
- 决策范围。

这样可以降低：

- 上下文噪声。
- 错误传播。
- 权限滥用。
- 敏感信息暴露。

---

# 真相投影与上下文隔离

第 04 章讨论了上下文隔离。

现在可以进一步理解：

上下文隔离解决的是：

> 不同职责之间不要长期混合全部历史。

真相投影解决的是：

> 一个隔离上下文启动以后，到底应该拿到哪些项目事实。

因此：

```text
上下文隔离
负责建立边界。

真相投影
负责给这个边界内部提供正确世界。
```

---

# 真相投影与有效推理范围

第 09 章讨论：

> Agent 不需要看见整个世界。

> 需要看清完成当前决策所需要的完整相关世界。

第 13 章进一步补充：

> 这个局部世界必须持续和项目当前可信真相保持可管理的一致性。

因此，一个高质量投影需要同时满足：

- 足够小。
- 足够完整。
- 来源明确。
- 版本明确。
- 归属明确。
- 失效条件明确。
- 可以重新生成。

---

# 真相投影与任务切分

第 10 章讨论：

> 切分决定 Agent 所看到的世界。

现在可以进一步得到：

> 每一个稳定任务边界，都应该对应一个可解释的真相投影。

如果一个任务无法回答：

- 我需要哪些全局约束？
- 我依赖哪些模块契约？
- 哪些真相变化会让我失效？

那么任务边界可能还不够成熟。

---

# 真相投影与决策权

第 12 章讨论：

> 不同角色拥有不同决策权。

真相投影也应该反映这种差异。

例如：

开发 Agent 可以看到：

- 当前授权真相。

它可以挑战。

但没有权限静默修改。

验证 Agent 可以：

- 读取任务使用的投影。
- 检查投影是否漏掉已知约束。
- 提出失效或冲突。

架构角色可以：

- 修改全局架构真相候选。

Human 或授权责任人：

- 批准高风险变化。

---

# 失败模式一：每个 Agent 自己理解全局世界

任务进入 Agent。

Agent 自己搜索代码。

自己读取文档。

自己判断哪些信息重要。

自己形成项目模型。

不同 Agent 最终拥有不同世界。

结果：

```text
Agent A 的系统
≠
Agent B 的系统
≠
真实项目
```

这会形成持续真相漂移。

---

# 失败模式二：投影变成静态摘要

项目一开始生成一份：

> “Agent 项目上下文摘要”

后来：

- 需求变化。
- 代码变化。
- 架构变化。
- 契约变化。

摘要长期不变。

所有 Agent 仍然使用它。

这会形成：

> 陈旧投影。

---

# 失败模式三：投影过窄

局部 Agent 只看到自己的模块。

它的修改在模块内部完全正确。

但违反了：

- 跨模块契约。
- 全局一致性规则。
- 状态所有权。

因此：

> 局部上下文必须包含相关全局约束。

---

# 失败模式四：投影过大

为了避免遗漏：

每个 Agent 都读取：

- 所有全局真相。
- 所有设计文档。
- 所有契约。
- 所有依赖。

最后重新回到第 09 章的问题：

```text
信息很多。
有效推理范围被突破。
```

因此：

> 投影的目标始终是最小但完整的相关真相。

---

# 失败模式五：全局真相变化，下游没有失效

```text
全局规则 v1
↓
生成任务
↓
实现
↓
测试
↓
证据
```

随后：

```text
全局规则 v2
```

但旧任务、旧测试和旧证据继续被当成有效。

这会产生一种非常危险的状态：

```text
每个产物单独都有依据。
整个系统的依据已经来自不同版本的世界。
```

---

# 失败模式六：所有变化导致全量重做

另一个极端是：

```text
任何全局真相变化
↓
所有任务失效
↓
所有测试重跑
↓
所有证据重建
```

这种系统维护成本会非常高。

因此：

> 变更传播需要尽量精确。

---

# 失败模式七：局部实现自动获得真相地位

Agent 发现：

> 代码现在就是这样。

于是得出：

> 项目规则就是这样。

这会把：

```text
现状
```

直接提升成：

```text
规范
```

但现有代码可能包含：

- 缺陷。
- 历史妥协。
- 临时兼容逻辑。
- 未完成迁移。

因此：

> 代码是证据来源。不能自动成为最高层真相。

---

# 一个最小真相投影流程

可以暂时使用下面的流程。

1. 明确当前任务范围。
2. 找出任务依赖的局部真相。
3. 找出相关全局不变量。
4. 找出相关架构边界。
5. 找出相关契约和依赖。
6. 记录这些信息的来源与版本。
7. 定义投影失效条件。
8. 检查当前投影是否完整。
9. 将投影交给执行 Agent。
10. 执行过程中持续允许提出：
    - 缺失依赖。
    - 真相冲突。
    - 陈旧信息。
    - 范围扩大。
11. 如果触发失效条件：暂停相关关键执行。
12. 重新生成投影。
13. 重新评估已有任务、实现和证据。
14. 恢复执行。

可以表示成：

```text
当前任务
↓
局部范围
↓
相关局部真相
+
相关全局真相
+
相关契约
+
相关依赖
↓
来源与版本
↓
完整性检查
↓
真相投影
↓
Agent 执行
↓
├── 正常
│   ↓
│   继续
│
├── 发现缺失信息
│   ↓
│   扩展投影
│
├── 发现冲突
│   ↓
│   真相挑战
│
└── 触发失效条件
    ↓
    重新生成投影
```

---

# 一个最小真相变更传播流程

当某条项目真相发生变化时：

1. 记录变化前后的差异。
2. 找出直接依赖这条真相的对象。
3. 找出间接依赖。
4. 对下游对象分类：
   - 未受影响。
   - 可能受影响。
   - 直接失效。
5. 对直接失效对象重新打开。
6. 对可能受影响对象重新评估。
7. 检查相关证据是否仍然有效。
8. 更新对应真相投影。
9. 通知仍在执行的相关任务。
10. 完成重新验证以后，再关闭传播流程。

可以表示为：

```text
Truth v1
↓
Truth v2
↓
计算变化
↓
依赖追踪
↓
├── 未受影响
│   ↓
│   保留
│
├── 可能受影响
│   ↓
│   重新评估
│
└── 直接失效
    ↓
    重新打开
        ↓
    重新执行 / 重新验证
        ↓
    新证据
```

---

# 真相传播与工作流状态

这里开始出现一个新的问题：

如果一条真相变化以后：

- 三个已经完成的任务需要重新打开。
- 两个正在执行的任务需要暂停。
- 一组证据已经失效。
- 一个下游任务暂时不能开始。

那么系统需要知道：

> 这些工作现在分别处于什么状态？

这会自然引出下一章：

> 工作流运行时与恢复。

因为当真相和证据开始拥有生命周期以后：

工程系统最终也需要一个能够持续保存执行状态的运行时。

---

# 一个工作假设

可以暂时把大型系统的一致性理解成三个层级：

```text
全局真相
↓
定义跨系统约束

真相投影
↓
把相关约束带入局部世界

局部真相
↓
让 Agent 在有限范围内可靠执行
```

其中任何一个层级出现问题，都可能产生不同失败。

全局真相错误：

> 所有局部世界可能一起错误。

投影错误：

> 某些局部世界缺少重要约束。

局部真相错误：

> 单个模块内部出现偏差。

因此，大型 Agent 工程需要同时治理：

- 全局层。
- 投影层。
- 局部层。

---

# 另一个工作假设

大型 Agent 系统真正需要保持的，不是所有 Worker 拥有相同上下文。

更重要的是：

> 不同 Worker 虽然拥有不同局部世界，但它们依赖的高影响事实来自同一个可追踪的项目真相体系。

可以表达成：

```text
上下文可以不同。

职责可以不同。

模型可以不同。

会话可以不同。

但关键真相来源需要保持一致。
```

---

# 仍在研究的问题

这一章目前仍然包含较多工作假设。

第一，真相投影应该由谁生成，怎样避免投影层本身成为单点错误来源。

第二，怎样自动判断一个局部投影是否完整。

第三，怎样定义不同类型真相的陈旧窗口。

第四，怎样自动建立真相与任务、代码、测试、证据之间的依赖关系。

第五，真相变化传播应该精确到什么粒度，才能兼顾正确性和维护成本。

第六，怎样避免依赖图本身逐渐过期。

第七，当多个全局规则同时变化时，怎样判断组合影响。

第八，局部 Agent 发现新依赖以后，怎样安全扩展自己的世界。

第九，怎样验证多个局部投影组合以后仍然保持全局一致。

第十，大型系统中是否需要专门的真相投影服务或上下文构建层。

这些问题仍然需要更多真实工程实践，会继续在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **全局真相描述系统共同遵守的高影响规则。**

---

> **局部真相描述明确范围内可以依赖的事实。**

---

> **全局真相不应该成为所有文档的总和。**

---

> **局部真相必须拥有明确范围和归属。**

---

> **局部世界不能自行改写全局规则。**

---

> **真相投影负责把相关全局约束带入局部世界。**

---

> **投影需要来源、版本和失效条件。**

---

> **投影缩小世界的同时，必须保护关键约束。**

---

> **全局真相发生变化以后，受影响的局部投影、任务和证据需要重新评估。**

---

> **真相变化应该精确传播，而不应该默认全量重做。**

---

> **局部正确不能自动推出全局正确。**

---

> **局部现实可以挑战全局真相，但不能静默覆盖它。**

---

> **Worker 可以拥有不同上下文，但关键真相需要来自同一个可追踪体系。**

---

# 结语

大型 Agent 系统不可能让每一个 Worker 都理解整个项目。

真正可扩展的方向，是允许不同 Worker 拥有不同的局部世界。

但这些局部世界不能彼此独立地发明现实。

它们需要共同依赖一套可以追踪、授权、挑战和更新的项目真相。

因此，大型 Agent 软件工程最终需要解决几个问题：

```text
哪些规则属于全局？

哪些事实只属于局部？

当前任务到底需要看到哪些高层约束？

这个局部世界来自哪个真相版本？

什么变化会让它失效？

全局规则变化以后，哪些任务需要重新打开？

哪些证据还值得相信？

局部发现和全局规则冲突时，谁负责裁决？
```

当这些问题能够被系统化处理以后：

一个巨大的工程世界，就可以被投影成大量不同的小世界。

每个 Agent 只需要看清自己的世界。

同时这些世界仍然共享同一套可追踪的工程现实。

这可能是大型 Agent 系统能够真正扩展的一个关键条件。
