# 附录C — 实战速查表

[日本語](cheatsheet.ja.md) · [English](cheatsheet.md) · **简体中文**

这是一个**实战速查表**，回答的问题是：

> **我正在设计任务、运行 Agent Workflow、验证结果或做 Human × AI 决策时，应该检查什么？**

它覆盖 Part I / II / III，但不承担概念定义职责。想知道某个概念是什么意思、由哪一章定义，请查阅[附录E — 核心概念索引](concept-index.zh-CN.md)。

---

## 三条核心原则

```text
1. AI 是执行层。
2. 流程创造生产力。
3. 约束带来稳定性。
```

## Part I — 个人 AI 工程（01–07）

### 任务设计五原则

| # | 原则 | 自问 |
|---|---|---|
| 1 | 一个任务，一个目标 | 是否混合了多个结果？ |
| 2 | 定义完成 | 什么可观察证据代表完成？ |
| 3 | 定义边界 | 哪些内容不得修改？ |
| 4 | 保证可验证 | Agent 能否测试或检查结果？ |
| 5 | 闭合上下文 | 所需信息是否集中在一起？ |

### 最小任务契约

```text
summary:             预期结果
currentAction:       本次执行内容
acceptanceCriteria:  可观察的完成证据
boundaries:          禁止修改和非目标
```

四项完整之前，不要交接任务。

### 提示词质量四个维度

| 维度 | 检查 |
|---|---|
| 信息密度 | 每句话是否都会影响执行？ |
| 任务边界 | 范围和非目标是否明确？ |
| 上下文质量 | 是否删除了无关历史？ |
| 约束清晰度 | 隐含期待是否已经说清？ |

### 上下文隔离

职责变化、当前状态难以重述、反复回到旧话题或输出质量下降时，开启新会话。交接应包含目标、决策、规格、约束、证据和验收标准。

### 多 Agent 管理六要素

```text
1. 角色       → 谁负责什么
2. 约束       → 每个角色不得做什么
3. 汇报       → 变更、原因、证据、剩余工作
4. 验收       → 客观完成条件
5. 失败处理   → 停止、记录、升级、恢复
6. 交接       → 阶段间明确传递状态
```

### 工作流设计

| 原则 | 含义 |
|---|---|
| 模板驱动 | 遵循规定路径，异常时进入规定案例 |
| 压缩正常路径 | 替换和打磨规则，而不是无限增加 |
| 质量门 | 证据不完整时阻止状态转换 |
| 原子状态转换 | 同时记录原因、改变状态并交接 |
| 单一事实来源 | 在一个结构化系统中维护权威状态 |

## Part II — 可靠 Agent 软件工程速查

工作时可以直接问自己的问题。

```text
Truth 真相
□ 当前 Agent 应该相信什么？
□ 当前真相来源是什么？
□ 是否存在未解决的冲突？
→ 08

Scope 推理范围
□ 当前问题是否落在 Agent 的有效推理范围内？
□ 是否需要继续切分？
→ 09 / 10

Boundary 边界与契约
□ 允许修改什么？
□ 禁止修改什么？
□ 契约是否明确？
→ 10

Verification 验证
□ 完成声明需要哪些证据？
□ 自我验证和独立验证是否区分？
□ 证据是否仍然有效？
→ 11

Authority 决策权
□ 当前决定由谁拥有？
□ Agent 是否正在超过授权范围？
→ 12

Projection 投影
□ 当前局部范围真的需要看见全局吗？
□ 投影是否已经陈旧？
→ 13

Runtime 运行时
□ 当前状态是否有唯一权威来源？
□ Retry / Reexecution / Recovery 是否被正确区分？
□ 中断以后怎样恢复？
→ 14

Boundary Cost 边界成本
□ 当前切分是否已经得不偿失？
□ 边界协调成本是否超过收益？
→ 15

Governance 治理
□ 当前治理强度是否与风险匹配？
□ Human 是否正在成为审批瓶颈？
→ 16

Capability 能力
□ 这是「能实现」，还是「能够可靠交付」？
□ 有没有可靠的判断机制？
→ 17
```

## Part III — Human × AI 长期协作速查

```text
Personal Context 个人上下文
□ 当前判断真正需要哪些个人信息？
□ 是否正在使用无关或陈旧历史？
→ 19

Personal Truth 个人真相
□ 这是事实、自我描述还是 AI 推断？
□ 来源和时效是否清楚？
→ 20

Decision Support 决策支持
□ 机会要求和个人能力证据是否匹配？
□ 实现成本和交付风险是否被混淆？
□ 是否存在弱 Oracle？
→ 21

Authority 授权
□ AI 当前是在分析、建议、决定还是执行？
□ 理解是否被错误转换成授权？
→ 22

Execution 执行
□ Human 的决定是否已经转换成明确执行授权？
□ 决策上下文和执行上下文是否分开？
□ 是否存在现实提交点？
→ 23

Feedback 反馈
□ 最终现实发生了什么？
□ 结果与结果原因是否被区分？
□ 是否需要更新能力、个人真相或协作协议？
→ 24
```

概念定义与权威章节请查阅[附录E — 核心概念索引](concept-index.zh-CN.md)。

## 验证清单

```text
□ Agent 完成了适用的自我检查
□ 已审查变更文件和差异
□ 没有范围之外的修改
□ 可机器验证的检查已经自动化
□ 安全、架构和业务逻辑经过人工审查
□ 结论有官方资料或运行证据支持
□ 受阻 Agent 已停止并输出结构化报告
```

## 失败模式

六个高频基础失败模式，完整定义见[附录A](anti-patterns.zh-CN.md)。其余失败模式按章节分布，索引同样在附录A。

| # | 模式 | 对策 |
|---|---|---|
| 1 | 先改状态、后写日志 | 让转换成为原子操作 |
| 2 | 任务不完整就交接 | 强制四个字段 |
| 3 | 一个会话做所有事 | 每个会话一个职责 |
| 4 | 手工重复规则 | 对共享指令进行版本管理 |
| 5 | 把工作输出当档案 | 分离状态与证据 |
| 6 | 善意越界 | 明确禁止事项和非目标 |
