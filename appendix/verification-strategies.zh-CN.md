# 附录B — AI 产出验证策略

[日本語](verification-strategies.ja.md) · [English](verification-strategies.md) · **简体中文**

## 为什么验证能力重要

AI 生成数千行代码的速度，可能远快于人类审查它们的速度。因此，验证会成为 AI 辅助交付的瓶颈，也是最重要的控制面。

**生产力不仅受执行速度限制，也受“多快能够得出可信验收结论”限制。**

---

## 策略1：要求 Agent 自我验证

要求 Agent 实际执行适用检查，而不只是提出检查建议。

```text
实现用户表格排序。报告完成之前：
- 构建项目；
- 运行现有测试；
- 添加并运行三个字段的升序/降序测试；
- 确认 TypeScript strict mode 没有错误。
```

“编写测试”把执行留给审查者；“编写、运行并汇报结果”才能产生证据。

自我验证是第一道防线，不是独立验收。Agent 仍可能错误理解自己的输出，或遗漏相关检查。

## 策略2：审查变更差异

不要重新阅读整个仓库，应从声明的和实际的变更范围开始。

```text
1. 要求列出修改文件及每个文件的修改目的。
2. 检查 diff，并与任务边界比较。
3. 检查意外文件、依赖、生成产物和无意义格式变化。
4. 高风险逻辑即使差异很小，也要完整审查。
```

差异审查可以压缩检查范围，但不能证明未修改的依赖或假设就是正确的。

## 策略3：使用独立审查上下文

在独立会话或角色中审查实现。

```text
目的：[任务目标]
修改文件：[列表]
验收标准：[检查项]

审查：
- 是否满足验收标准；
- 是否符合现有架构；
- 是否存在范围外修改；
- 安全、隐私和失败行为；
- 是否缺少测试或证据。
```

独立上下文不会继承实现阶段的全部辩护和失败尝试，更容易提出挑战。但第二个模型仍然不是事实来源。

## 策略4：自动化质量门

机器能确定的事情，应由机器确定。

| 检查 | 常见方式 | 需要人工判断？ |
|---|---|---|
| 构建成功 | 构建命令 / CI | 否 |
| 现有测试通过 | 测试运行器 | 否 |
| Lint 与类型检查通过 | Linter / 编译器 | 否 |
| 没有未经批准的依赖 | 锁文件或清单 diff | 否 |
| 设计意图正确 | 审查 | 是 |
| 用户体验合适 | 检查和测试 | 是 |
| 业务行为有效 | 领域负责人 | 是 |

把确定性检查自动化，让人的注意力集中在意图、取舍和风险上。

## 策略5：分阶段验证

不要等到大型功能全部完成后才开始检查。

```text
数据模型 → 验证
API 行为 → 验证
UI 集成 → 验证
端到端行为 → 验证
```

小型质量门可以减少建立在早期错误之上的无效工作。阶段边界应对应有意义的职责，而不是随意拆成极小修改。

## 策略6：明确哪些判断必须由人负责

### 适合委派执行

- 成熟的实现模式；
- 测试生成和常规自动化；
- 基于明确规则的重构；
- 文档草稿；
- 确定性的错误处理。

### 必须由人明确负责

- **安全：**认证、授权、密钥和威胁模型；
- **架构：**会约束整个系统的设计决策；
- **业务正确性：**代码是否符合真实领域规则；
- **性能：**需要在代表性负载下测量的判断；
- **法律与合规：**解释与责任承担；
- **不可逆外部动作：**生产删除、付款、发布或通信。

边界不是“AI 能不能”，而是失败影响、不确定性和责任是否可以安全委派。

## 策略7：升级停滞问题

出现以下情况时停止重复执行：

- 多次尝试失败，且没有形成新假设；
- 输出引用不存在的事实或 API；
- 问题需要架构决策；
- 存在多个可行方向，而选择取决于任务之外的取舍。

### 结构化停止报告

```text
背景：       预期结果
当前状态：   已完成内容和准确阻塞点
相关代码：   文件和位置
观察到的问题：错误、矛盾或异常行为
已尝试方案： 尝试过什么、为什么失败
未完成工作： 尚未满足的验收标准
证据：       日志、测试、文档、测量数据
```

### 多模型讨论

困难问题可以交给多个推理模型：一个提出方案，另一个批评假设，前者再进行修正。人负责主持讨论，并决定何时已经足够收敛、可以进入验证。

```text
结构化问题报告
  ↓
模型A提出方案
  ↓
模型B攻击假设和失败模式
  ↓
模型A修正
  ↓
人选择可测试方向
  ↓
工作Agent根据代码和证据验证
```

模型达成一致并不代表事实成立。多个模型可能共享同一个错误前提。API、安全要求、法律主张和性能判断，必须回到官方文档、源代码、测试和测量结果。

## 三个验收问题

1. **所有预先定义的验收标准是否都有证据支持？**
2. **变更是否保持在批准范围之内？**
3. **是否记录了足够状态，供下一阶段或未来调查使用？**

Agent 的工作状态应保持精简，但发布和审计证据需要按相关版本与环境另行保留。

## 总结

可靠验证由以下内容组成：

1. 自我检查；
2. 差异审查；
3. 独立审查上下文；
4. 自动质量门；
5. 分阶段验收；
6. 人对高风险判断负责；
7. 结构化升级。

目标不是阅读每一行生成代码，而是构建足以支持验收决定的证据链。
