# 04 — 上下文隔离策略

[日本語](README.ja.md) · [English](README.md) · **简体中文**

## 每个会话都会逐渐受到污染

当需求、实现、测试设计、缺陷修复和无关讨论都放在一个长会话里时，上下文会逐渐失去可靠性。

旧假设仍然可见，失败方案与已确认决策相互竞争。Agent 必须猜测哪些信息仍然有效，输出因此变得不稳定，返工随之增加。

## 为什么会发生污染

模型会把当前会话中的大部分内容视为可能相关。人通常可以轻松判断某个早期想法已经失效；如果没有明确重述状态，模型却可能继续使用它。

因此，上下文不仅是容量限制，也是注意力和责任边界。

## 一个会话，一个职责

为不同职责打开独立会话。

| 会话 | 职责 | 包含 | 不包含 |
|---|---|---|---|
| A | 需求 | 范围、决策、边界 | 实现尝试 |
| B | 实现 | 技术契约、代码、约束 | 未解决的需求讨论 |
| C | 测试 | 用例、证据、预期行为 | 实现过程历史 |
| D | 审查 | 验收、设计质量、意外变更 | 新功能实现 |

## 隔离前后

### 隔离前

```text
需求 + 实现 + 测试 + 修复 = 混合上下文
→ 当前职责不清
→ 输出不完整
→ 返工增加
```

### 隔离后

```text
需求会话 → 稳定决策
实现会话 → 聚焦修改
测试会话 → 独立证据
审查会话 → 客观评价
```

## 连接会话

隔离会带来交接问题：怎样让下一个会话获得决策，又不继承所有噪声？

使用结构化桥接，而不是只说“前面讨论过”。

```text
目标：实现用户表格排序。
决策：只做客户端排序；服务端排序不在范围内。
规格：name、email、createdAt 可以排序。
约束：不修改 API，不新增依赖。
验收：三个字段的升序和降序排序均正确。
```

桥接的成本，远低于错误实现后重新构建上下文的成本。

## 何时开启新会话

出现以下情况时考虑切换上下文：

1. 职责发生变化，例如从需求转入实现；
2. 文件数量、未决事项或对话长度使当前状态难以重述；
3. 讨论反复回到旧话题；
4. 在相似指令下，输出质量明显下降。

15到20轮对话可以是预警信号，但不是通用上限。内容和职责比轮数本身更重要。

## 这会增加工作吗

开始时可能感觉更慢，但上下文隔离也会整理人的思考。需求保持为需求，实现可以收敛，测试也能独立挑战结果。

**上下文隔离既是模型控制策略，也是工作质量策略。**
