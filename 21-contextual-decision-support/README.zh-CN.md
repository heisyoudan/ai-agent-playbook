# 21 — 基于个人上下文的决策支持

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续研究（Research）** · **成熟度：工作假设（Working Hypothesis）**

---

# 为什么需要基于个人上下文的决策支持

很多 AI 决策分析都是通用的。

例如：

- 这个项目难不难？
- 这个岗位工资高不高？
- 这个技术有没有前景？
- 这个客户预算是否合理？

这些问题可以在不知道具体 Human 的情况下进行一定分析。

但现实中真正需要做决定时，问题通常会变成：

- 这个项目适不适合我？
- 这个岗位对我有没有价值？
- 这个机会值得我投入多少时间？
- 我能不能可靠交付？
- 这个风险对我来说是否可以接受？

这些问题无法只研究机会本身。

还需要同时理解：

> **这个具体的人。**

因此：

现实决策通常发生在两个世界的交叉处。

```text
外部现实
和
个人现实
```

---

# 两个世界

可以把一个决策简单理解成：

```text
机会世界
+
个人世界
↓
匹配判断
```

机会世界可能包含：

- 任务要求。
- 预算。
- 时间。
- 技术。
- 客户。
- 风险。
- 验收方式。
- 沟通方式。
- 长期价值。

个人世界可能包含：

- 能力。
- 经历。
- 作品。
- 时间。
- 目标。
- 约束。
- 偏好。
- 风险承受。
- 历史经验。

只有把两边连接起来：

AI 才能回答：

> **这个机会对这个人意味着什么。**

---

# 通用分析和个人化分析

例如，一个项目要求：

- Unity。
- C#。
- Particle System。
- 根据参考视频还原视觉效果。

通用分析可以得到：

```text
Unity Particle System 可以实现
代码复杂度不高
相关 API 清晰
技术上可行
```

个人化分析还需要继续问：

- 当前 Human 的 Unity 能力集中在哪里？
- 有没有 VFX 真实交付证据？
- 是否擅长视觉调参？
- 项目怎样验收？
- 客户能否给出客观标准？
- 最终效果是否高度依赖审美？
- 如果失败，时间成本有多大？

后面这些问题决定的：

> **才是项目是否适合承接。**

---

# 机会分析不能停留在技术可行性

技术可行性通常只是现实判断的一部分。

一个任务可能：

```text
技术上能完成
但商业上不值得
```

也可能：

```text
技术上简单
但验收风险很高
```

还可能：

```text
自己能完成
但需要投入大量不符合长期目标的时间
```

因此：

AI 决策支持需要从：

```text
Can it be done?
```

继续进入：

```text
Can this person reliably deliver it?
```

然后继续进入：

```text
Is it worth doing?
```

---

# 三个问题

可以把机会判断分成三个层级。

第一层：

> 能不能实现？

第二层：

> 能不能可靠交付？

第三层：

> 是否值得这个 Human 去做？

这三个问题需要完全不同的信息。

## 能不能实现

主要依赖：

- 技术。
- 工具。
- 模型能力。
- 资源。

## 能不能可靠交付

还需要：

- 能力证据。
- 任务边界。
- 验收标准。
- 验证能力。
- 失败风险。

## 是否值得做

进一步需要：

- 时间。
- 收益。
- 机会成本。
- 长期目标。
- 个人偏好。
- 合作方式。
- 风险承受。

长期个人上下文主要改变的是：

> **第二层和第三层。**

---

# 一个真实案例

曾经存在一个 Unity 粒子效果任务。

客户提供一个参考视频，希望最终效果尽可能接近视频中的表现。

Agent 阅读任务以后发现：

```text
代码实现并不复杂
Unity Particle System 本身也并不陌生
```

从纯工程角度：

```text
任务可以完成
```

如果分析停在这里：

结论很可能是：

> 这是一个简单任务。

但进一步拆解任务以后：

真正的交付目标并不是：

```text
代码能够运行
```

客户真正购买的是：

```text
视觉效果是否接近参考视频
```

因此任务实际依赖：

- Unity 工程能力。
- C#。
- Particle System。
- VFX 调参。
- Technical Art。
- 视觉观察。
- 审美判断。
- 反复迭代。
- 客户主观验收。

此时长期个人上下文提供了另一部分现实：

Human 的真实能力证据主要集中在：

- Unity 工程。
- C#。
- 系统设计。
- 逻辑实现。
- 调试。

而：

- VFX。
- Technical Art。
- 高度主观视觉还原。

缺少稳定交付证据。

于是：

技术可行性判断

和

交付风险判断

得到了不同答案。

可以表示成：

```text
代码复杂度              低
技术实现可行性          高
VFX 能力证据            弱
视觉验收确定性          低
客户验收主观性          高
返工风险                高
↓
最终交付风险            高
```

因此：

> 「代码简单」

不能直接推出：

> 「项目风险低」。

这就是个人上下文真正开始创造价值的地方。

---

# 需求应该拆成能力要求

一个现实机会不应该只被描述成：

- Unity 项目。
- Java 项目。
- AI 项目。

这些标签太粗。

更好的方法是把机会拆成具体能力要求。

例如：

Unity 粒子任务

可以拆成：

- Unity 工程实现。
- C# 编程。
- Particle System 使用。
- 视觉效果分析。
- VFX 参数调优。
- Technical Art。
- 主观视觉还原。
- 客户反馈迭代。

然后再与当前个人能力边界匹配。

---

# 能力匹配

可以形成：

```text
机会能力要求
↓
对照
↓
个人已证明能力
```

例如：

```text
Unity 工程实现   → 强匹配
C#               → 强匹配
Particle System  → 可执行
VFX              → 弱证据
Technical Art    → 弱证据
主观视觉还原      → 高不确定性
```

这样最终判断比：

> 会 Unity，所以能做

精确得多。

---

# 能力匹配需要区分等级

一个简单能力匹配可以使用：

- 已证明。
- 条件可靠。
- 有限证据。
- 未知。
- 已知不适合。

例如：

```text
任务要求 A
个人能力：已证明

任务要求 B
个人能力：条件可靠

任务要求 C
个人能力：未知
```

真正风险通常集中在：

> **未知和弱证据区域。**

---

# 能力缺口

一个机会和当前能力之间的差距，可以称为：

> **能力缺口。**

能力缺口不一定意味着拒绝。

它还可能意味着：

- 需要学习。
- 需要额外验证。
- 需要缩小范围。
- 需要寻找协作者。
- 需要提高预算。
- 需要增加时间。

因此：

AI 决策支持不应该只输出：

```text
适合 / 不适合
```

更有价值的是：

```text
缺口在哪里？
缺口是否可以弥补？
需要付出什么成本？
```

## 能力缺口的成本

例如，一个新技术：

可能只需要：

```text
2 小时学习
```

这属于低成本缺口。

另一个能力缺口：

需要数周训练。

属于高成本缺口。

还有一些缺口：

来自主观审美能力。

可能很难短时间补齐。

因此：

能力差距

还需要进一步转化成：

> **补足成本。**

---

# 验收方式

在机会判断中：

验收方式非常重要。

一个任务如果拥有：

- 明确输入。
- 明确输出。
- 自动测试。
- 可重复结果。

那么：

即使技术比较复杂，

仍然可能适合 Agent 化。

相反：

一个任务代码很简单。

但最终评价依赖：

> 看起来够不够好

那么交付风险可能更高。

因此：

机会评估必须问：

> **这个任务怎样知道完成？**

---

# Oracle

第 17 章已经引入：

```text
Oracle
```

即：

> 判断结果是否正确的机制。

在机会判断中：

Oracle 强度会直接影响交付风险。

例如：

```text
API 功能     → 自动测试可以验证
性能优化     → Benchmark 可以验证
数据库迁移   → 数据一致性验证
视觉效果     → 客户主观判断
文案风格     → 主观判断
```

后两类任务的：

Oracle 更弱。

```text
弱 Oracle + 弱能力证据
通常意味着：
高交付风险
```

```text
强 Oracle + 强能力证据
通常意味着：
更容易形成可靠交付
```

因此可以形成一个很有用的二维判断：

```text
个人能力证据
×
验收能力
```

例如：

```text
强能力 + 强验收   → 低风险
弱能力 + 强验收   → 可以受控尝试
强能力 + 弱验收   → 需要明确客户预期
弱能力 + 弱验收   → 高风险
```

这对项目选择非常有价值。

---

# 代码量不能代表风险

现实项目中：

代码多

不一定风险高。

代码少

也不一定风险低。

真正影响风险的是：

- 能力匹配。
- 依赖复杂度。
- 验收确定性。
- 客户期望。
- 失败成本。

因此：

Agent 不应该根据：

> 代码很简单

直接给出：

> 项目简单。

---

# 工作量和交付风险需要分开

可以区分：

```text
Implementation Cost
实现成本

Delivery Risk
交付风险
```

Unity 粒子案例中：

```text
实现成本可能不高
交付风险却很高
```

而一个大型后端任务：

代码量可能很大。

但如果：

- 需求明确。
- 测试完整。
- 能力匹配强。
- 结果客观。

Agent 可以承担大量执行。

整体交付风险反而可能更低。

---

# 任务选择应该看真实瓶颈

AI 决策支持需要找到：

真正决定项目成败的瓶颈。

有时瓶颈是：

- 代码。
- 需求。
- 领域知识。
- 验收。
- 沟通。
- 客户期待。

如果瓶颈不在代码：

AI 代码能力再强也无法消除项目风险。

---

# 个人约束

机会适配还需要考虑：

现实约束。

例如：

项目要求：

```text
每天实时会议
```

Human 更适合：

```text
书面异步协作
```

即使：

能力完全匹配。

项目仍然可能不适合。

因此：

> **能力匹配只是机会匹配的一部分。**

## 沟通适配

一个现实机会还可以拥有：

```text
沟通适配度
```

例如：

- 异步文字为主。
- 需求相对明确。
- 可通过文档交付。

这对某些 Human 非常适合。

而：

- 大量临时会议。
- 高度口头需求。
- 持续同步。

可能产生更高协作成本。

因此：

AI 可以结合长期协作上下文判断：

> 这个客户的工作方式是否匹配。

## 时间适配

同一个任务：

如果有两周时间。

风险可能可控。

如果要求：

```text
明天完成
```

结论可能完全不同。

因此：

个人上下文需要提供：

```text
当前可用时间
```

机会需要提供：

```text
截止时间
预期响应速度
工作负载
```

两者结合才能判断：

> 是否真实可行。

---

# 经济价值

机会判断还需要考虑：

收入

和

成本。

例如：

任务报价 20 美元。

预计：

```text
实现 1 小时
```

看起来还可以。

但如果：

```text
沟通 2 小时
主观修改 5 小时
客户可能无限返工
```

真实收益就完全不同。

因此：

报价不能脱离：

> **预计总投入。**

## 总投入

可以包括：

- 实现时间。
- 沟通时间。
- 学习时间。
- 验证时间。
- 返工概率。
- 后续维护。

AI 可以帮助估算：

> 真实工作成本。

## 机会成本

如果一个 Human 的时间有限：

做 A

意味着：

暂时不能做 B。

因此：

一个机会值不值得做

还应该考虑：

```text
机会成本
```

例如：

一个低收入小项目。

如果能快速获得：

- 新平台评价。
- 新能力证据。
- 新作品。
- 长期客户。

它可能拥有额外价值。

另一个项目：

收入更高。

但完全消耗关键产品开发时间。

真实价值可能不同。

---

# 长期目标

长期个人上下文最有价值的地方之一就是：

它知道当前机会应该放在哪条长期路径上理解。

例如：

一个任务可能产生：

- 收入。
- 能力证据。
- 作品。
- 行业经验。
- 客户关系。
- 职业信号。

AI 可以分析：

这些结果和当前长期目标之间是什么关系。

## 短期收益和长期收益

可以区分：

```text
短期收益
和
长期收益
```

短期收益例如：

- 现金。
- 快速评价。
- 立即成果。

长期收益例如：

- 能力积累。
- 作品。
- 专业定位。
- 长期合作。
- 目标行业经验。

因此：

一个机会的价值可能远远超过：

```text
本次收入
```

反过来也可能：

```text
收入不错
长期价值很低
```

决策支持需要保留这种区别。

---

# 历史经验

长期个人上下文还提供：

过去类似机会的真实结果。

例如：

过去某类项目：

```text
技术实现很快
但主观验收导致大量返工
```

下次看到类似任务：

AI 就可以提前提醒：

> 历史上存在同类风险。

因此：

决策支持不只依赖理论分析。

还可以调用：

```text
个人现实历史
```

## 失败模式匹配

可以建立：

```text
机会特征
↓
匹配历史失败模式
```

例如：

```text
高度主观验收
+
低预算
+
客户参考视频
+
需求模糊
```

如果过去类似组合产生过高风险：

这应该成为重要信号。

这就是长期协作相比一次性 AI 分析的重要优势。

## 历史不能直接决定未来

但也需要避免另一个极端：

因为过去失败过，

以后全部拒绝。

现实会变化：

- 能力会成长。
- 工具会增强。
- Agent 会变强。
- 预算会变化。

因此：

历史只能作为证据。

不能自动成为禁令。

---

# 机会匹配

一个完整机会匹配可以考虑多个维度：

- 技术匹配。
- 能力匹配。
- 验收匹配。
- 时间匹配。
- 沟通匹配。
- 风险匹配。
- 目标匹配。
- 经济匹配。

这些维度不应该简单平均。

## 关键失败项

有些维度属于：

```text
硬约束
```

例如：

- 没有必要权限。
- 无法满足截止日期。
- 法律不允许。
- 完全无法验证结果。

只要其中一个失败：

整个机会可能就无法可靠交付。

因此：

机会评估需要区分：

```text
硬约束
和
软权衡
```

## 硬约束

例如：

- 必须具备某认证。
- 必须在某时间在线。
- 必须使用无法访问的系统。
- 交付标准完全无法满足。

## 软权衡

例如：

- 预算略低。
- 需要学习一些技术。
- 长期价值一般。

AI 不应该把两者混成：

> 一个平均分。

## 避免单一评分

现实决策很复杂。

如果 AI 把机会压成：

```text
83 / 100
```

很容易制造虚假的精确感。

更有价值的输出通常是：

- 哪些条件明确匹配。
- 哪些地方存在风险。
- 哪些能力没有证据。
- 哪些约束无法满足。
- 哪些问题需要 Human 决定。

因此：

决策支持更适合：

```text
结构化判断
```

而不是：

```text
虚构一个精确总分
```

---

# 不确定性

AI 决策支持需要明确：

哪些内容自己不知道。

例如：

- 客户真实验收标准不清楚。
- 预计返工次数未知。
- 技术要求存在歧义。
- 历史能力证据不足。

这些不确定性应该：

```text
直接暴露
```

而不是：

```text
被一个确定答案掩盖
```

## 决策前补充信息

有些不确定性可以主动降低。

例如：

向客户询问：

- 是否要求像素级还原？
- 是否接受近似视觉效果？
- 是否提供可编辑资产？
- 有几轮修改？

这些问题可能直接改变项目风险。

因此：

好的决策支持系统不只分析已有信息。

还会发现：

> **为了做出更好判断，还缺什么信息？**

## 信息价值

如果某个问题的答案：

不会改变最终决定，

就没有必要大量调查。

如果一个问题：

可能直接决定是否承接，

它就拥有高信息价值。

这可以帮助 AI 决定：

> **下一步该问什么。**

---

# 反事实分析

AI 还可以帮助 Human 做：

```text
反事实分析
```

例如：

- 如果客户接受近似效果：风险如何变化？
- 如果预算提高一倍：是否值得？
- 如果任务只负责代码实现，不负责最终视觉还原：是否进入可靠能力范围？
- 如果有 VFX 专业人员合作：是否可交付？

这能够把：

```text
简单的接受 / 拒绝
```

转化成：

```text
怎样改变条件才能让机会变得可行
```

---

# 机会重构

有时最好的结果并不是：

```text
接
或
不接
```

可能是：

```text
修改范围
```

例如：

原任务：

```text
负责完整视觉效果交付
```

重构成：

```text
负责 Unity Particle System 工程实现
视觉效果由客户或 VFX Artist 最终调整
```

这样：

机会可能从：

```text
高风险
```

变成：

```text
能力匹配
```

因此：

> **决策支持可以帮助重新设计机会边界。**

# Human 的价值判断

即使所有分析都完成：

仍然存在 AI 无法代替的部分。

例如：

- 我愿不愿意冒这个险？
- 我是否真的想进入这个方向？
- 我愿意用多少时间换取这次经验？
- 这个合作关系对我有没有吸引力？

这些问题属于：

```text
Human 的价值判断
```

AI 可以提供：

- 事实。
- 风险。
- 历史。
- 可能结果。

Human 决定：

> **什么值得。**

# 决策支持不能变成自动决定

长期上下文越丰富：

AI 的建议会越来越有说服力。

这反而需要更强边界。

因为：

> 「AI 很了解我」

不能变成：

> 「AI 可以替我决定。」

长期个人上下文应该：

- 提高 Human 决策质量。
- 降低信息整理成本。
- 发现被忽视的风险。

最终责任仍然属于 Human。


这样 Human 不需要重新阅读所有原始信息。

```text
压缩个人决策表面
```

让 Human 把注意力集中在：

> **真正需要价值判断的地方。**

# 决策记录

重要决定做出以后：

可以保存：

- 当时是什么机会。
- 有哪些关键事实。
- 有哪些风险。
- Human 最终选择什么。
- 为什么。
- 之后结果如何。

这些记录会成为：

```text
下一次决策的经验
```

## 决策结果需要回流

例如：

最终决定：

```text
接项目
```

后来结果：

- 成功。
- 失败。
- 超时。
- 利润低。
- 客户满意。
- 形成长期合作。

这些现实结果应该回到：

```text
个人长期上下文
```

这样：

决策支持可以持续校准。

## 正确决策和好结果不是同一个东西

这里也需要避免一种误区。

一个决策可能：

- 当时依据充分。
- 过程合理。
- 最终仍然失败。

因为现实包含随机性。

反过来：

一个决策过程很差。

最终可能碰巧成功。

因此：

评估 AI 决策支持质量

不能只看最终结果。

还需要看：

- 当时是否使用了正确事实。
- 是否识别了关键风险。
- 是否暴露了不确定性。
- 是否遗漏了重要信息。
- 是否帮助 Human 做出有意识的选择。

## 决策过程也需要证据

这和前面的工程方法完全一致。

一条重要建议：

应该能解释：

```text
为什么会得到
```

否则长期 AI 很容易形成：

```text
黑盒个人判断
```

例如：

不应该只输出：

> 我觉得这个项目不适合你。

更好的输出是：

> 任务技术实现和你的 Unity 工程能力高度匹配。
>
> 但最终验收依赖 VFX 和高度主观视觉还原。
>
> 目前缺少这类能力的稳定交付证据。
>
> 同时缺少清晰 Oracle。
>
> 因此主要风险集中在验收，而不是代码实现。

这样的建议：

> **可以被 Human 检查。**

一个长期协作系统应该尽量允许：

```text
判断
↓
回到
↓

历史经验
```

这样：

Human 可以发现：

当判断错误以后：

也可以知道：

错误来自：

- 外部信息。
- 个人上下文。
- 能力模型。
- 还是推理过程。

这对长期校准很重要。

# 偏差放大

长期 AI 也存在一个危险：

过去某个错误理解

可能影响未来多个决策。

例如：

AI 错误认为：

```text
Human 不擅长某类任务
```

于是：

```text
不断建议避开
```

Human 因此没有新机会。

系统继续缺少新证据。

最后旧判断被不断强化。

这会形成：

```text
自我实现偏差
```

因此：

长期决策支持必须保留：

```text
探索
```

## 能力边界不应该变成能力牢笼

个人能力边界的作用是：

```text
识别当前可靠范围
```

它不能变成：

```text
永久限制
```

对于：

- 有长期价值。
- 但当前能力证据不足。

的任务，

系统可以建议：

```text
受控尝试
```

例如：

- 小项目。
- 低风险环境。
- 清晰验收。
- 额外 QA。

这样能力可以继续成长。

## Exploit 和 Explore

长期个人决策中存在一个经典平衡：

```text
利用已知能力
和
探索新能力
```

如果永远只选择：

```text
高匹配任务
```

Human 的能力可能停止增长。

如果总是选择：

```text
大量未知领域
```

风险又会很高。

因此：

长期 AI 可以帮助 Human 维持：

```text
可控探索
```

例如：

```text
主要时间投入
高确定性能力

少量时间投入
战略性未知领域
```

具体比例仍然需要 Human 决定。

3. 拆解真实要求。
4. 找出最终验收方式。
5. 把要求转换成能力需求。
6. 调用相关个人上下文。
7. 对照当前能力证据。
8. 找出能力缺口。
9. 检查现实约束。
10. 检查沟通和时间适配。
11. 分析失败路径。
12. 判断结果是否可验证。
13. 估算投入。
14. 识别短期收益。
15. 识别长期价值。
16. 调用相似历史经验。
17. 暴露不确定性。
18. 找出高信息价值问题。
19. 生成可选方案。
20. 压缩成 Human 需要做出的真正决定。
21. Human 决策。
22. 记录决定。
23. 现实结果发生以后回流。
24. 更新个人上下文和能力边界。



也可能来自：


> **把相关性过早解释成个人能力问题。**

不能让：

```text

```

# 核心原则

本章可以浓缩成几句话：

- 机会本身的质量和机会对某个人的适配度属于两个问题。
- 技术可行性不能自动推出可靠交付。
- 代码简单不能自动推出项目风险低。
- 机会要求应该拆成具体能力要求。
- 个人能力应该由真实能力证据支撑。
- 能力匹配之外，还需要检查验收、时间、沟通、目标和现实约束。
- 弱能力证据和弱 Oracle 同时出现时，交付风险通常很高。
- 能够实现和适合承接属于两个不同问题。
- 历史经验应该帮助未来判断，但不能永久限制新的探索。
- 长期个人上下文应该用于提高 Human 判断质量，而不是替代 Human 的价值判断。
- 重要建议应该能够追溯到事实、证据和推断。
- 现实结果必须回流，才能持续校准决策支持。

# 结语

长期个人 AI 真正有价值的地方：

可能并不只是：

```text
记得更多关于一个人的事情
```

更重要的是：

当新的现实机会出现以后，

它能够把两个过去长期分开的世界连接起来。

一个世界是：

```text
机会真正需要什么
```

另一个世界是：

```text
这个 Human 当前真实拥有什么
```

然后进一步分析：

- 哪里匹配。
- 哪里存在能力缺口。
- 哪里缺少可靠验收。
- 真正风险在哪里。
- 需要投入什么。
- 会得到什么。
- 和长期目标有什么关系。
- 哪些条件改变以后机会会变得可行。

在 Unity 粒子任务中：

AI 最初看到的是：

```text
代码简单
```

长期个人上下文让它继续看到：

```text
真正验收依赖 VFX 和视觉还原
```

于是：

判断从：

```text
可以实现
```

继续发展成：

```text
实现容易，但可靠交付风险较高
```

这个差异非常重要。

因为现实世界里：

Human 最稀缺的往往并不是：

```text
有没有事情可以做
```

真正稀缺的是：

```text
应该把有限的时间和注意力放在哪里
```

当 AI 能够使用长期个人上下文帮助筛选这些机会：

它开始从：

```text
回答问题的工具
```

进一步进入：

```text
决策支持系统
```

而接下来必须解决的问题就是：

这种越来越强的决策支持，

应该走到哪里停止？

- 哪些判断可以交给 AI？
- 哪些只能由 Human 做？
- 什么时候 AI 应该建议？
- 什么时候应该执行？
- 什么时候必须请求授权？

这就是下一章：
