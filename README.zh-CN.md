## 这是什么

更强的模型或更巧妙的提示词，并不会自动带来稳定的 AI 协作。

真正可持续的优势来自对工作本身的设计：选择合适的任务粒度、隔离上下文、明确约束、验证产出，并把一次成功的协作固化成可重复执行的流程。

本 Playbook 将这些实践整理为一套不依赖具体平台的方法论。

## 适合谁

- 已在工作中使用 AI，但结果仍不稳定的工程师
- 感觉“管理 Agent 还不如自己做得快”的实践者
- 希望在团队或组织层面引入 AI 协作的技术负责人
- 需要讨论实际 AI 使用能力的面试官与候选人

## 三条核心原则

```text
AI 只是执行层。
流程才创造生产力。
约束才带来稳定性。
```

编码能力依然重要：它支撑判断、调试、设计和验收。正在降低稀缺性的，是手工产出常规代码本身。目标不是丢掉工程基本功，而是把基本功与任务设计、上下文管理、验证和工作流工程结合起来。

## 一次完整协作循环

1. **划分风险等级。** 明确 Agent 可以直接做什么、什么需要审批、什么必须由人负责。
2. **定义单一目标。** 写清预期结果、本次动作、验收标准和边界。
3. **提供闭合上下文。** 只提供完成任务所需的文件、事实、决策和约束。
4. **让 Agent 执行并自检。** 要求提供构建、测试、Lint 或其他适用证据。
5. **审查变更。** 检查修改文件、越界变更、高风险逻辑，以及结论背后的证据。
6. **记录并交接。** 把决策与证据写入结构化的单一事实来源，再为下一个职责开启干净上下文。
7. **度量并改进。** 关注返工、漏出缺陷、审查耗时、成本和例外，而不是只看产出数量。

## 最小任务契约

```text
summary:             要达成什么结果？
currentAction:       本次具体执行什么？
acceptanceCriteria:  哪些可观察检查代表完成？
boundaries:          哪些内容不得修改或尝试？
```

四项缺少任何一项，任务都还不适合交给 Agent。

## 适用边界与责任

Agent 可以提出方案并执行，但不会转移人的责任。安全、权限、支付行为、隐私、合规、生产发布、破坏性操作和不可逆的外部动作，都需要明确负责人和审批规则。

多个模型达成一致不等于证据。可验证的事实必须回到官方文档、源代码、测试、运行结果或测量数据。供 Agent 使用的短期工作状态，应与必须留存的审计、发布证据分开管理。

## 背景

本 Playbook 的方法来自生产与个人开发实践，其中包括把任务契约、上下文隔离、质量门和结构化交接写进 Agent 协作框架。这里关注的是可迁移的方法，而不是绑定某个模型或平台的操作指南。
