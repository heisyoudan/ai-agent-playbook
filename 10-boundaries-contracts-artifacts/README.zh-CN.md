# 10 — 任务切分、边界与契约

[日本語](README.ja.md) · [English](README.md) · **简体中文**

**状态：持续演化（Evolving）**

---

# 为什么需要任务切分

当一个问题超过 Agent 的有效推理范围以后，最直接的方法通常是继续切分。

例如：

```text
支付平台
↓
支付业务域
↓
支付模块
↓
退款功能
↓
退款 API
↓
退款服务
↓
具体任务
```

随着问题不断缩小：

- 需要理解的上下文减少。
- 同时维持的约束减少。
- 依赖关系更加清晰。
- 验证范围更加有限。

Agent 的局部推理可靠性通常会提高。

因此，任务切分一直是 AI Agent 工作流中非常重要的能力。

但这里存在一个容易被忽略的问题：

> **切得越小，就一定越好吗？**

答案显然不是。

---

# 任务太大

一个过大的任务可能要求 Agent 同时理解：

- 大量文件。
- 多个业务域。
- 复杂架构。
- 多个外部系统。
- 大量历史决策。
- 多个数据结构。
- 大量测试。
- 多个失败场景。

这时容易出现：

- 遗漏约束。
- 错误理解依赖。
- 局部结论互相矛盾。
- 验证范围失控。

Agent 看起来完成了任务，但只能覆盖其中一部分现实。

因此：

> **任务太大的主要风险，是问题范围超过 Agent 的有效推理范围。**

---

# 任务太小

任务切得过小，同样会产生新的问题。

例如一个原本完整的功能被拆成几十个极小任务：

- 任务 A 修改 DTO。
- 任务 B 修改 Mapper。
- 任务 C 修改 Service。
- 任务 D 修改 Repository。
- 任务 E 修改测试。
- 任务 F 修改文档。

每个任务本身都非常容易。

但系统开始需要大量：

- 交接。
- 上下文重建。
- 契约。
- 状态同步。
- 依赖协调。
- 集成验证。
- 任务之间的等待。

最后，人或上层 Agent 可能花费大量精力，只是为了保证这些局部结果仍然能够重新组合成完整功能。

因此：

> **任务太小的主要风险，是边界协调成本过高。**

---

# 切分不会消灭复杂度

这里可以得到一个非常重要的结论：

> **切分不会消灭复杂度。它会转移复杂度。**

一个巨大的问题被切成多个小问题以后：

局部推理复杂度下降。

但同时：

- 边界数量增加。
- 契约数量增加。
- 跨边界依赖增加。
- 交接增加。
- 集成成本增加。
- 协调成本增加。

因此：

> 原本集中在一个大问题内部的复杂度，会有一部分转移到多个局部问题之间。

这也是为什么大型系统不能依靠“无限切小”来解决所有问题。

---

# 边界协调成本

每建立一个边界，系统都会产生一定成本。

这些成本可能包括：

- 重新构建上下文。
- 定义输入和输出。
- 定义双方责任。
- 记录依赖。
- 等待前置任务。
- 进行交接。
- 重新验证组合后的行为。
- 处理跨边界冲突。
- 维护多个局部状态。

这些成本可以统一理解成：

> **边界协调成本**

边界本身非常有价值。

它可以降低局部复杂度，限制修改范围，也可以保护不同模块之间的独立性。

但边界并不是免费的。

因此，工程目标应该同时考虑两个方向：

- 降低局部推理复杂度。
- 控制边界协调成本。

---

# 最佳推理边界

任务粒度存在两个极端。

一边是：

```text
任务过大
↓
推理复杂度过高
↓
超过 Agent 的有效推理范围
↓
可靠性下降
```

另一边是：

```text
任务过小
↓
边界过多
↓
契约和交接增加
↓
协调成本上升
↓
整体效率和一致性下降
```

因此，中间应该存在一个更合适的区域：

> **最佳推理边界**

它并不是一个固定大小。

也不是规定：

- 一个任务只能修改几个文件。
- 一个任务只能有多少 Token。
- 一个任务只能完成一个函数。

最佳推理边界更接近：

> 一个 Agent 可以完整理解当前问题。

> 同时又能闭合一个有意义的工程结果。

> 并且跨边界依赖保持在可控制范围内。

可以简单表达成：

```text
相关问题范围
≤
Agent 有效推理范围
```

同时：

```text
跨边界依赖
保持在完成任务所必需的最低合理水平。
```

---

# 最佳边界会变化

同一个任务大小，并不适合所有场景。

例如：

一个普通后台 CRUD 功能，可能可以直接作为完整任务交给 Agent。

一个支付账本修改，即使代码只有几十行，也可能需要拆得更加谨慎。

因为最佳边界受到很多因素影响：

- 业务复杂度。
- 风险等级。
- 依赖密度。
- 代码耦合程度。
- 模型能力。
- 可用工具。
- 测试能力。
- 验证成本。
- 失败是否可逆。
- 领域知识要求。

因此：

> **任务粒度不能只根据代码量判断。**

真正应该考虑的是：

- Agent 是否能够理解。
- 是否能够验证。
- 边界之间是否容易重新组合。

---

# 一个好的任务边界应该具备什么

一个稳定的任务边界至少应该回答几个问题。

## 第一，目标是什么

这个边界内部需要完成什么工程结果？

例如：

- 实现退款金额校验。
- 增加 Token 刷新逻辑。
- 支持某个新的国家配置。

## 第二，允许修改什么

Agent 可以修改哪些模块、文件或数据？

例如：

- 允许修改退款服务和对应测试。
- 不允许修改账本结构。

## 第三，不允许修改什么

边界同样需要明确禁止事项。

例如：

- 不能修改公共 API。
- 不能改变数据库结构。
- 不能改变外部系统契约。
- 不能修改其他支付方式。

## 第四，依赖什么

完成这个任务依赖哪些上游事实？

例如：

- 退款业务规则。
- 支付状态定义。
- 账本接口。
- 错误码规则。
- 幂等要求。

## 第五，输出什么

任务完成以后，需要留下什么？

例如：

- 代码。
- 测试。
- 变更说明。
- 验证结果。
- 工程产物。
- 证据。

## 第六，怎样证明完成

什么可观察结果可以证明任务成功？

如果这一点无法回答，任务边界本身可能还没有定义完整。

---

# 边界不仅是“范围”

在 Agent 工作流里，边界至少可以包含几种类型。

## 范围边界

定义当前任务负责什么，不负责什么。

## 修改边界

定义 Agent 可以修改哪些内容。

## 权限边界

定义 Agent 可以使用哪些工具和执行哪些操作。

## 数据边界

定义 Agent 可以读取、写入或传递哪些数据。

## 决策边界

定义 Agent 可以自主做哪些决定，哪些决定必须升级。

## 时间和资源边界

定义执行时间、重试次数、计算成本或其他资源限制。

## 风险边界

定义哪些行为即使技术上可以执行，也不应该自动执行。

例如：

- 生产数据删除。
- 真实付款。
- 安全配置修改。
- 不可逆外部操作。

---

# 契约

边界告诉 Agent：

> 你在哪里工作。

契约进一步告诉系统：

> 边界两侧的双方应该怎样合作。

一个契约至少需要明确：

- 输入是什么。
- 输出是什么。
- 双方分别负责什么。
- 哪些行为必须保持。
- 哪些失败是允许的。
- 失败以后应该怎样处理。
- 怎样判断契约仍然成立。

## 数据契约

定义：

- 字段。
- 类型。
- 必填项。
- 格式。
- 版本。
- 兼容性。

例如 API 请求和响应结构。

## 行为契约

定义：

> 输入某种状态以后，系统必须表现出什么行为。

例如：

- 已捕获金额不足时，不允许产生超额退款。

## 时序契约

有些系统即使数据结构完全匹配，也可能因为时序错误产生故障。

例如：

- A 必须先完成。
- B 才允许开始。

或者：

- 某个回调可能延迟数分钟。
- 某个状态改变以后需要等待最终一致性。

## 重试与幂等契约

如果一个服务允许自动重试，就需要明确：

- 重复请求会发生什么？
- 多久以内被视为同一个请求？
- 失败以后是否可以重新提交？
- 重复执行是否产生副作用？

这些动态行为通常比单纯的数据结构更加危险。

## 失败契约

一个可靠的边界还需要定义：

- 调用失败以后返回什么。
- 失败状态是否可恢复。
- 谁负责重试。
- 谁负责补偿。
- 什么时候必须停止。
- 什么时候需要人工介入。

## 所有权契约

还需要明确：

- 谁拥有这个数据？
- 谁拥有这个状态？
- 谁有权改变它？
- 谁负责最终一致性？

大型系统中的很多问题，根源并不在代码本身，而在所有权不清。

---

# 接口匹配不代表契约成立

两个模块的 API 数据结构完全一致，并不能证明它们能够安全协作。

例如：

- 请求字段完全正确。
- 返回结构完全正确。

但服务 A 默认请求失败以后可以重试。

服务 B 却没有幂等保证。

于是：

```text
服务 A
↓
第一次请求实际成功
↓
响应丢失
↓
自动重试
↓
服务 B 再次执行
↓
产生重复业务结果
```

静态接口完全正确。

动态行为仍然发生冲突。

因此：

> **契约需要覆盖真正影响系统行为的条件。不能只检查字段是否一致。**

---

# 切分本身就是架构

任务切分经常被理解成项目管理问题。

但当 AI Agent 开始依赖切分结果工作以后，切分本身已经成为架构的一部分。

因为切分决定了：

- Agent 能看到什么。
- Agent 看不到什么。
- 谁拥有某个状态。
- 哪些模块互相依赖。
- 哪些信息必须跨边界传播。
- 哪些决策可以局部完成。

如果最开始的切分方式存在问题，那么后续 Agent 即使全部正确完成任务，最终仍然可能得到一个错误系统。

例如：

```text
错误的架构
↓
非常清晰的任务切分
↓
非常准确的 Agent 执行
↓
完整测试
↓
全部通过
↓
整体设计仍然错误
```

因此：

> **完美执行无法修复错误切分。**

切分决定了 Agent 所看到的世界。

所以切分本身需要被当成高价值工程决策。

---

# 局部正确不等于整体正确

假设一个大型系统被拆成：

- 支付
- 账本
- 退款
- 清结算
- 对账

每个模块都有自己的局部真相。

每个 Agent 都能够证明自己的模块正确。

可能得到：

- 支付正确。
- 账本正确。
- 退款正确。
- 清结算正确。
- 对账正确。

但仍然不能自动推出：

> 整个系统正确。

因为模块之间可能存在：

- 语义冲突。
- 状态冲突。
- 所有权冲突。
- 时序冲突。
- 事务边界冲突。
- 失败恢复冲突。
- 数据一致性冲突。

因此：

> **局部正确不能自动推出全局正确。**

切分以后，系统必须保留跨边界验证能力。

---

# 工程产物作为边界接口

不同 Agent 或不同阶段之间，不应该依赖完整对话历史进行交接。

更可靠的方式是产生明确的工程产物。

例如：

- 设计决定。
- 任务契约。
- API 规格。
- 代码差异。
- 测试结果。
- 验证报告。
- 错误记录。
- 状态快照。

这些工程产物承担一个重要作用：

> 把上一个阶段已经确认的结果，作为下一个阶段可以直接使用的输入。

例如：

```text
需求分析
↓
形成设计产物
↓
开发 Agent 使用设计产物
↓
形成代码与测试
↓
QA 使用代码和验收标准
↓
形成验证证据
```

这样 Agent 之间传递的是：

> 已经形成的工程事实。

而不需要重新读取完整聊天历史。

---

# 工程产物需要最小化

工程产物也不能无限增长。

如果每个阶段都把全部推理过程、聊天记录和临时信息交给下一阶段，就会重新制造上下文污染。

因此高质量工程产物应该：

- 保留关键决定。
- 保留必要证据。
- 保留来源。
- 保留适用范围。
- 删除临时噪声。
- 明确下一阶段真正需要知道什么。

工程产物的目标，是成为稳定接口。

而不是成为历史垃圾场。

---

# 失败模式一：任务过大

例如：

> 实现完整支付系统。

这种任务虽然目标明确，但范围远远超过单个 Agent 可以可靠推理的世界。

结果往往是：

- 架构只覆盖主要路径。
- 隐藏约束被忽略。
- 大量假设被自行补全。
- 验证无法覆盖整个结果。

---

# 失败模式二：过度切分

例如：

- 修改一个字段一个任务。
- 修改一个 Mapper 一个任务。
- 增加一个测试一个任务。
- 修改一段文档一个任务。

每个任务都非常简单。

但整个功能需要十几个 Agent 交接以后才能完成。

这时候：

任务本身很可靠。

系统整体却被协调成本拖慢。

因此：

> **最小任务并不自动等于最佳任务。**

---

# 失败模式三：只有接口，没有行为契约

两个模块的数据结构完全一致。

但：

- 重试方式不同。
- 超时假设不同。
- 状态所有权不同。
- 错误处理不同。

最终仍然发生系统级错误。

这说明：

> 接口只是契约的一部分。

---

# 失败模式四：局部优化破坏全局规则

一个 Agent 发现本模块存在性能问题。

于是增加缓存。

局部性能显著提升。

测试也通过。

但系统中的另一个模块依赖实时数据。

于是全局一致性被破坏。

这说明：

> 局部 Agent 的上下文需要包含相关全局约束。

---

# 失败模式五：边界存在，但所有权不存在

多个模块都可以修改同一个状态。

出现错误以后，每个模块都认为另一个模块应该负责。

这种情况下，即使技术边界存在，工程边界仍然是模糊的。

因此：

> 边界还需要对应明确的责任和所有权。

---

# 一个可复用的切分流程

对于一个复杂问题，可以使用下面的过程。

1. **第一步** 明确最终目标。
2. **第二步** 识别真正的业务能力或工程责任。
3. **第三步** 找出必须保持的全局约束。
4. **第四步** 识别关键依赖和状态所有权。
5. **第五步** 形成候选任务边界。
6. **第六步** 检查每个任务：
   - Agent 是否能够完整理解？
   - 是否能够独立验证？
   - 需要多少跨边界信息？
   - 是否存在大量等待和交接？
7. **第七步** 如果任务太大：继续切分。
8. **第八步** 如果任务太小，并且多个任务高度耦合：重新合并。
9. **第九步** 为稳定边界定义契约。
10. **第十步** 定义工程产物和验证方式。

最终形成：

```text
复杂问题
↓
候选切分
↓
检查有效推理范围
↓
检查边界协调成本
↓
调整任务大小
↓
明确边界
↓
定义契约
↓
生成工程产物
↓
Agent 执行
↓
局部验证
↓
跨边界验证
```

# 一个工作假设

可以暂时把任务切分理解成一个优化问题。

总工程成本大致受到两个方向影响：

```text
推理复杂度
+
边界协调成本
```

任务越大：

> 推理复杂度增加。

任务越小：

> 边界协调成本增加。

因此最佳边界存在于两者之间的某个区域。

这个模型目前仍然属于工作假设。

它还不是一个可以精确计算的数学公式。

但它可以帮助我们避免两个极端：

- 所有问题都交给一个 Agent。
- 把所有问题无限切小。

# 仍在研究的问题

当前还有几个值得继续调查的问题。

第一，能不能设计一种实际可用的方法，帮助 Agent 自动判断任务应该继续切分还是合并。

第二，怎样衡量边界协调成本。

第三，任务边界应该优先按照 API、业务用例、模块、领域还是其他单位划分。

第四，怎样发现切分以后被隐藏的跨边界依赖。

第五，怎样验证多个局部正确结果重新组合以后仍然保持全局正确。

第六，Agent 是否可以根据历史执行结果逐渐学习某个项目最合适的任务粒度。

这些问题仍然需要更多实际观察，会继续在 [Research](../research/README.zh-CN.md) 中跟踪。

# 核心原则

本章可以浓缩成几句话：

> **任务太大，会超过有效推理范围。**

---

> **任务太小，会产生过高的边界协调成本。**

---

> **切分不会消灭复杂度，它会转移复杂度。**

---

> **切分决定 Agent 所看到的世界，因此切分本身就是架构决策。**

---

> **局部正确不能自动推出全局正确。**

---

> **契约需要描述真实行为，不能只描述数据结构。**

---

> **工程产物应该成为不同阶段和不同 Agent 之间的稳定接口。**

---

> **真正需要寻找的，是 AI 看得清，同时系统也付得起协调成本的最小完整世界。**

---

# 结语

AI Agent 工程很容易形成一种直觉：

> 任务越小，Agent 越可靠。

这个方向只对了一半。

缩小任务确实可以降低局部推理复杂度。

但每创建一个新的边界，系统也需要为它支付协调成本。

因此成熟的任务切分，不追求：

- 最大的任务。

也不追求：

- 最小的任务。

它寻找的是：

```text
一个 Agent 可以完整理解。

可以独立执行。

可以明确验证。

同时又不会制造过多跨边界协调成本的任务世界。
```

最终，真正重要的问题是：

```text
这个边界是否让 Agent 看清了自己需要解决的问题？

这个边界是否保留了必要的全局约束？

边界两侧是否拥有明确契约？

局部结果重新组合以后，整个系统是否仍然正确？
```

当这些问题可以被回答时，任务切分才真正从简单的项目管理手段，升级为 Agent 软件工程中的架构能力。
