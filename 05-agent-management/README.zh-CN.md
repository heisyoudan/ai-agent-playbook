# 05 — 管理多个 Agent

[日本語](README.ja.md) · [English](README.md) · **简体中文**

## 会话隔离之后的问题

当职责被拆到不同会话后，新的成本会出现：同一组规则必须反复告诉每个 Agent、每个会话。

这些规则包括执行顺序、失败汇报、文件边界、文档要求以及何时需要批准。依靠人工重复会产生规则漂移和准备成本。

## 问题发生变化的时刻

问题因此从“怎样提示这个 Agent”转变为：**“怎样把多个 AI 执行者作为一个系统来管理？”** 这已经是团队设计问题。

## 必须定义的六个要素

### 1. 角色

为每个角色分配清晰职责。

```text
Sage：发布任务、决定交接、处理例外、完成收口
Dev： 理解任务、实现逻辑、记录工作、通过质量门
QA：  设计并执行测试、判断结果、报告证据
Design：使用模拟数据实现 UI、进行视觉迭代、定义接口
```

Design 被独立出来，是因为 UI 工作天然具有探索性：比较、视觉判断和反复调整都很正常。逻辑工作则需要收敛，追求正确、稳定、闭环和可验证。

混合这两种认知模式会同时损害两者。因此 Design 不处理业务逻辑，只使用模拟数据；Dev 负责把确认后的接口连接到真实行为。

### 2. 约束

定义禁止行为，应当和定义职责一样认真。

- Dev 不擅自改写需求。
- QA 不在没有记录的情况下直接修复实现。
- Design 不实现业务逻辑。
- 所有角色都不修改无关文件。
- 高风险或不可逆操作需要人工批准。

Agent 常常会出于善意扩大范围。明确非目标能让变更范围保持可预测。

### 3. 汇报格式

使用稳定的结果结构：

```text
Changed：修改的文件和行为
Why：决策与原因
Verified：执行的检查及结果
Remaining：风险、限制、未完成项
Next：下一步交接或动作
```

固定格式可以降低理解结果和继续交接的成本。

### 4. 验收标准

“看起来不错”不是验收标准。完成必须可观察：构建通过、场景符合规格、变更没有越界，或规定证据已经存在。

如果无法客观判断完成，任务就还不适合执行。

### 5. 失败处理

预先定义 Agent 受阻后的行为：

- 达到重试或费用上限后停止；
- 记录错误和证据；
- 列出尝试过的方案和发生变化的假设；
- 不把部分完成伪装成完成状态；
- 将控制权交给指定角色或人工负责人。

### 6. 交接

交接传递的是状态，而不是对会话记忆的期待。

交接内容应包括目标、已确认决策、变更产物、验证证据、剩余风险，以及接收方的确切职责。

## 怎样向 Agent 注入规则

不要依赖每次手工粘贴相同指令。把共享规则保存在有版本管理的配置或模板中，再添加当前任务的特定上下文。

```text
共享角色与安全规则
        +
任务契约与局部上下文
        =
可执行指令
```

共享层应尽量小、稳定，并保持平台无关。

## 它带来的变化

当角色、约束、汇报、验收、失败处理和交接都被定义后，Agent 协作就不再是一连串即兴会话，而更像一个工作的操作系统。

目标不是最大程度自治，而是可预测执行、可见状态、受限权限和可恢复失败。
